# La Voce ／ 活動と曲目の複数入力 実装パッチ仕様

**2つの複数化**をまとめた差分仕様です。

1. **1日に複数の活動**（自主練 → リハ → 本番）を記録できるようにする
2. **1つの活動に複数の曲目**を、順序つきで記録できるようにする

この2つは入れ子の関係にあります。**活動が入れ物で、曲目がその中身**です。

## 1. 背景

1日1曲は現実的ではありません。

| 場面 | 実際の曲数 |
|---|---|
| レッスン | 3〜5曲 |
| 自主練習 | 2〜6曲 |
| リサイタル | 10〜20曲 |
| ライブ（ポップス/ロック） | 15〜25曲 |
| 声優の収録 | 1日に複数作品 |
| オペラの本番 | 1演目（ここだけ1つで足りる） |

複数化は単なる利便性の話ではなく、**負荷計算の前提そのもの**です。
5曲を90分歌った日を「1曲を90分」として扱うと、負荷が大きく歪みます。

### 1.2 活動も1日1つでは足りない

同じことが、その上の階層でも起きています。

```
ある本番当日
  09:30  自主練習   60分   発声＋当日の曲さらい
  14:00  リハーサル 120分  本番の演目
  19:00  本番       90分   本番の演目
```

**活動の種類が変われば、曲目も活動係数も変わります。**
これを1つの活動としてまとめると、次の2つが同時に壊れます。

- **活動係数が1つしか使えない** — 自主練 1.0 と本番 1.6 が混ざり、負荷が歪む
- **曲目を活動に紐づけられない** — 「自主練で歌った曲」と「本番で歌った曲」が
  区別できず、レパートリー分析の精度が落ちる

**同じ曲でも本番のほうが重い**、という当たり前のことが、
活動を分けて初めてデータに出ます。

声優（午前アニメ／午後ゲーム）、アナウンサー（朝の放送／夕方の収録）、
ポップス（サウンドチェック／本番）も同じ構造です。

## 2. UI 仕様

### 2.0 入れ物：活動ブロックの繰り返し

**活動を1つのブロックとして、いくつでも追加できる形にします。**
曲目リストは、各ブロックの中に入ります。

```
●  活動

┌─────────────────────────────────────┐
│ 自主練習              60分       ✕ │  ← ブロック1
│                                     │
│ 曲目                  [前回と同じ]  │
│ ┌─────────────────────────────────┐ │
│ │ ⠿ カロ・ミオ・ベン      20分  ✕ │ │
│ │ ⠿ 私のお父さん          20分  ✕ │ │
│ │ ⠿ ある晴れた日に        20分  ✕ │ │
│ └─────────────────────────────────┘ │
│   ＋ 曲を追加                       │
│   負荷 78                           │
└─────────────────────────────────────┘

┌─────────────────────────────────────┐
│ 本番                  90分       ✕ │  ← ブロック2
│                                     │
│ 演目・曲目                          │
│ ┌─────────────────────────────────┐ │
│ │ ⠿ 蝶々夫人              90分  ✕ │ │
│ └─────────────────────────────────┘ │
│   ＋ 曲を追加                       │
│   負荷 318                          │
└─────────────────────────────────────┘

  ＋ 活動を追加

  今日の合計  150分 ・ 負荷 396
```

**要点**

- **1つ目のブロックは最初から展開されている。** 多くの日は活動1つで終わる
- 「＋ 活動を追加」は控えめな見た目にする。**2つ以上の日だけコストが増える**設計
- 各ブロックに**その活動の種別・時間・曲目リスト・種別固有の項目**が入る
- ブロックごとに負荷を表示する（どの活動が重かったかが、その場でわかる）
- ブロックの並びは時系列。**開始時刻は任意**（入れれば時系列に並べ替え、なければ入力順）

### 2.0.1 テンプレートの役割を降格する

記録項目v2 §4.4 の日別テンプレートは「1日1種類」を前提にしていました。
**この前提を外します。**

| | 変更前 | 変更後 |
|---|---|---|
| テンプレート | その日の種別。1つだけ | **1つ目の活動の種別を選ぶショートカット** |
| 表示される欄 | テンプレートが決める | **各活動ブロックが、自分の種別に応じた欄を持つ** |

つまり、記録画面の冒頭で「今日は？」と聞いて休養／練習／レッスン…を選ぶ動作は残しますが、
それは**1つ目の活動ブロックを作る操作**になります。あとから種別の違うブロックを足せます。

「休養」を選んだ場合だけは例外で、活動ブロックを作らず休養方法の欄を出します。

### 2.0.2 種別固有の項目はブロックの中に入る

職業別設計で定義した項目は、**その活動ブロックの中**に置きます。
1日にアニメ収録とゲーム収録があれば、叫びテイク数はそれぞれのブロックに入ります。

| 活動種別 | ブロック内の固有項目 |
|---|---|
| 収録（声優） | 収録種別、役名、**叫びテイク数**、ブース湿度 |
| 放送（アナウンサー） | 番組名、発話時間の内訳、生放送トグル |
| ライブ（ポップス/ロック） | セットリスト（順序必須）、モニター環境、連戦日目 |
| 本番（声楽・ミュージカル） | 演目、会場 |

### 2.0.3 上限

**1日10ブロックまで。** それ以上は現実的でなく、UIも破綻します。

### 2.1 基本の形（画面レイアウト仕様 §4.2 の曲目欄を差し替え）

チップではなく**行のリスト**にします。曲ごとに時間の個別入力と並べ替えが必要なためです。

```
曲目・演目                      [前回と同じ]
┌─────────────────────────────────────┐
│ ⠿  蝶々夫人                 18分  ✕ │
│ ⠿  ある晴れた日に            18分  ✕ │
│ ⠿  私のお父さん              18分  ✕ │
│ ⠿  カロ・ミオ・ベン          18分  ✕ │
│ ⠿  О mio babbino caro       18分  ✕ │
└─────────────────────────────────────┘
  ＋ 曲を追加        [保存したリスト ▾]

  合計 90分（等分）        ▸ 個別に調整
```

| 部品 | 仕様 |
|---|---|
| `⠿` ドラッグハンドル | 並べ替えが必要なテンプレートでのみ表示（§2.6） |
| 曲名 | タップでサジェスト付き入力に戻る（レパートリー負荷パッチ §2.3） |
| 分の表示 | **自動配分値はグレー**、個別入力は通常色。見分けがつくこと |
| `✕` | 削除。取り消せるようトースト＋Undo を出す |
| 「▸ 個別に調整」 | 押すと各行の分が編集可能になる。既定は閉じる |

**上限は1日50曲。** 超えたら追加ボタンを無効化し、理由を表示する。

### 2.2 「前回と同じ」ボタン（最も効きます）

レッスンは同じ曲を数週間続け、ツアー中のセットリストはほぼ固定です。
**同じテンプレートの直近の記録**から、曲リストをそのままコピーする。

- コピーするのは曲リストと個別時間の配分のみ
- コピー後は「前回から」の小さなラベルを出し、編集を促す
- 直近の同テンプレート記録が14日以上前ならボタンを出さない（もう別の曲のはず）

### 2.3 保存したリスト（セットリスト・プログラム）

名前を付けて保存し、次回はワンタップで呼び出す。定期公演・ツアーで効きます。

```ts
interface SetlistPreset {
  id: string
  userId: string
  name: string            // 「◯◯ツアー 2026」「発表会プログラム」
  itemIds: string[]       // 順序つき repertoireId
  createdAt: string
  lastUsedAt: string
}
```

- 現在のリストから「このリストを保存」で作成
- 呼び出しは `lastUsedAt` の新しい順に並べる
- 呼び出した後の編集は、プリセットに影響しない（コピーとして入る）

### 2.4 改行区切りの貼り付け

セットリストをメモアプリで作る人は多いので、**貼り付けたら自動で行分割**する。

```
貼り付けテキスト
  → \n で分割 → trim → 空行を除去 → 上限50件で切る
  → 各行を normalizeTitle() で照合
     完全一致  → 既存のレパートリーに紐づける
     不一致    → 未登録のまま行として追加
```

**未登録が複数出ても、登録プロンプトを連続で出さないこと。**
まとめて1回だけ知らせる。

```
┌───────────────────────────────┐
│ 12曲を追加しました              │
│ うち5曲が未登録です             │
│ （登録しなくても記録は保存されます）│
│                               │
│ ┌─────────────┬─────────────┐ │
│ │ まとめて登録  │  あとで      │ │
│ └─────────────┴─────────────┘ │
└───────────────────────────────┘
```

### 2.5 曲が0件でもよい

**曲目は任意です。** 0件のまま保存できること。
0件の日は `songFactor = 1.0` として扱い、従来どおり `L = minutes × actW` になります
（既存データとの後方互換）。

### 2.6 活動種別ごとの出し分け

**判定はテンプレートではなく、その活動ブロックの種別で行います**（§2.0.1）。
1日の中で種別が違えば、ブロックごとに違う欄が出ます。

| 活動種別 | 曲目欄 | ラベル | 並べ替え |
|---|---|---|---|
| 休養 | **非表示**（ブロック自体を作らない） | — | — |
| 自主練習 | 表示 | 曲目 | 不要 |
| レッスン | 表示 | 曲目 | 不要 |
| リハーサル | 表示 | 曲目・演目 | 不要 |
| 本番（声楽・ミュージカル） | 表示 | 演目・曲目 | 不要 |
| **ライブ（ポップス/ロック）** | 表示 | **セットリスト** | **必須** |
| 収録（声優） | 表示 | 作品・役 | 不要 |
| 放送（アナウンサー） | 表示 | 番組・案件 | 不要 |

**ライブで並べ替えが必須なのは、セットリスト診断が曲順に依存するため**です
（職業別設計 §ポップス/ロック）。曲順を変えたときに負荷の偏りがどう変わるかを見せる機能なので、
順序が保持されないと成立しません。

ラベルは職業別の用語翻訳テーブルに従うこと（職業別設計 §UIの方針）。

### 2.7 「前回と同じ」は活動ブロック単位で

§2.2 の「前回と同じ」は、**同じ種別のブロックの直近の記録**から曲リストをコピーします。
自主練のブロックには直近の自主練から、本番のブロックには直近の本番から。

**種別をまたいでコピーしないこと。** 自主練の曲リストが本番のブロックに入ると、
レパートリー分析の精度が落ちます。

## 3. 時間配分

### 3.1 3段階で決める

曲ごとに分数を聞くのは重すぎます。**既定では聞かない。**

**配分は活動ブロックごとに独立して行います。** ブロックをまたいで按分しないこと。

```
入力（1つの活動ブロックについて）:
  total   = activity.minutes        // そのブロックの活動時間
  items[] = { repertoireId, minutesOverride? }

手順:
  1. minutesOverride があるものはその値で確定
  2. remaining = total − Σ(minutesOverride)
  3. remaining を、override のない曲に配分する
     a. 標準演奏時間 standardMinutes を持つ曲が1つ以上あれば
          w_i = standardMinutes_i ?? median(登録済みの standardMinutes)
          minutes_i = remaining × w_i / Σw
     b. どの曲にも standardMinutes がなければ
          minutes_i = remaining / (override のない曲数)     // 等分
```

**`remaining < 0` のとき**（個別入力の合計が活動時間を超えた）は、
黙って歪めず、確認する。

```
個別に入力した時間の合計（110分）が、
活動時間（90分）を超えています。

[ 活動時間を110分にする ]  [ 個別時間を直す ]
```

### 3.2 レパートリーに `standardMinutes` を追加

登録画面（レパートリー負荷パッチ §3.1）に、**任意項目を1つだけ**足す。

```ts
interface Repertoire {
  // ... 既存
  standardMinutes?: number   // 追加（任意）：標準的な演奏時間（分）
}
```

```
▸ くわしく（任意）
   テッシトゥーラ   [ F4  ▾ ]
   だいたいの長さ   [ − ] 18 分 [ + ]
```

**これがあると、20分のアリアと3分の歌曲が同じ重みになる問題が解けます。**
未入力でも等分で動くので、必須にしないこと。

## 4. 負荷計算の更新

レパートリー負荷パッチ §1.2 の式を、**その日の全曲の合算**に拡張します。

```
■ 活動ブロック a の中の、曲 i
  L_{a,i} = minutes_{a,i} × actW_a × songFactor_i

  actW_a       は活動 a の種別で決まる（休養0 / 自主練1.0 / レッスン1.2 /
                リハ1.3 / 本番1.6）★ブロックごとに違う
  songFactor_i はレパートリー負荷パッチ §1.2 のとおり
  minutes_{a,i} は本書 §3.1 でブロックごとに決めた値

■ 活動ブロック a の負荷
  L_a = Σ_i L_{a,i}

  そのブロックに曲が0件なら： L_a = minutes_a × actW_a   // songFactor = 1.0 相当

■ その日の発声負荷
  L_day = Σ_a L_a
```

**二重の合算になります。** 活動ごとに係数が違うことが、この式の要点です。

`L_day` を既存の ACWR（急性:慢性負荷比）にそのまま渡します。**接続部分は変わりません。**

### 4.1 その場でフィードバックを返す

曲を入れた直後に内訳を見せると、記録の動機になります。

```
  合計 90分（等分）        ▸ 個別に調整

  今日の負荷 198
  ┌────────────────────────────┐
  │ ある晴れた日に  ▓▓▓▓▓▓▓ 61 │  ← 重い順
  │ 蝶々夫人        ▓▓▓▓▓  44 │
  │ 私のお父さん     ▓▓▓▓   38 │
  │ ほか2曲         ▓▓▓    55 │
  └────────────────────────────┘
```

**この表示は「重い曲を入れた実感」を生みます。** 分析を待たずに価値が出る数少ない場所です。

## 5. 帰属の問題（複数化で新しく生じます）

### 5.1 何が問題か

1日に5曲歌った翌日にコンディションが落ちたとき、**どの曲のせいなのか**。
単一フィールドのときは考えなくてよかった問題です。

**単純に「その曲を歌った日の翌日の平均」を取ると、常に一緒に歌われる曲が
すべて同じ値になり、ランキングが意味を失います。**

### 5.2 段階1：寄与率による按分（データが少ないうち）

```
その日の曲 i の寄与率
  share_{i,d} = L_{i,d} / L_day_d

曲 i の帰属落ち込み
  drop_i = Σ_{d ∈ D_i} ( share_{i,d} × Δ_d ) / Σ_{d ∈ D_i} share_{i,d}

  D_i : 曲 i を記録した日の集合
  Δ_d : 翌日の喉コンディション − その人の平常値（偏差で見る。生の平均ではない）
```

粗いですが動きます。**表示条件は `|D_i| ≥ 3`。**

### 5.3 段階2：リッジ回帰（データが貯まったら）

```
目的変数  Δ_d          （翌日の喉コンディションの偏差）
説明変数  L_{i,d}       （曲 i のその日の負荷。歌っていない日は 0）

  Δ_d ≈ a + Σ_i b_i · L_{i,d} + c · 前日の睡眠時間

リッジ回帰（λ = 1.0、標準化後）で b_i を推定

有効化の条件:
  総観測日 ≥ 30  かつ  曲 i の出現日 ≥ 8
  条件を満たさない曲は段階1のまま表示する
```

### 5.4 分離できない曲を、正直に伝える

**いつも一緒に歌われる曲は、原理的に分離できません。**
「蝶々夫人」と「ある晴れた日に」を常に同じ日に歌っていたら、
どちらが重いのかはデータからは絶対にわかりません。

黙って適当な数字を出さず、検出して明示します。

```
検出:
  曲 i と曲 j の出現ベクトル（0/1 の系列）の相関 r_ij を計算
  |r_ij| ≥ 0.95  かつ  共起日数 ≥ 5
    → 同一グループとして扱う

扱い:
  グループとしてまとめて1つの係数を推定し、まとめて1行で表示する
```

表示：

```
┌───────────────────────────────┐
│ 蝶々夫人 ＋ ある晴れた日に      │
│    翌日 −1.8  ▓▓▓▓▓▓▓░░       │
│    この2曲は常に同じ日に        │
│    記録されているため、         │
│    どちらの影響かは            │
│    区別できません              │
└───────────────────────────────┘
```

**この正直さは、機能の信頼性そのものです。**
片方だけを「重い役」として名指しすると、根拠のない結論を押し付けることになります。

## 6. データモデル

```ts
interface ActivityItem {
  repertoireId: string
  minutesOverride?: number     // 個別入力があればこれ
  order: number                // 0 始まり。セットリストの順序
}

type ActivityKind =
  | 'practice' | 'lesson' | 'rehearsal'
  | 'performance'   // 本番（声楽・ミュージカル）
  | 'recording'     // 収録（声優）
  | 'broadcast'     // 放送（アナウンサー）
  | 'live'          // ライブ（ポップス/ロック）

interface Activity {
  id: string
  kind: ActivityKind
  startAt?: string             // 'HH:mm'（任意。あれば時系列に並べる）
  minutes: number              // ★このブロックの時間。1日の合計ではない
  items: ActivityItem[]        // ★ 0件でもよい
  order: number                // ブロックの並び順

  // 種別固有（§2.0.2）
  screamTakes?: number         // 収録
  isLive?: boolean             // 放送
  monitorType?: 'iem' | 'wedge' | 'none'   // ライブ
  tourDay?: number             // ライブ
  venue?: string
}

interface DayRecord {
  // ...
  activities: Activity[]       // ★ 0件（休養日）〜10件
  recovery?: { methods: RecoveryKey[]; note?: string }   // 休養日はこちら
}
```

**2つの禁止事項を、依頼時に明示してください。**

1. **`repertoireIds: string[]` と `minutesPerItem: number[]` の2本持ちにしないこと。**
   2つの配列を添字で対応させる設計は、並べ替えと削除で必ずずれます
2. **`DayRecord` に `activityKind` や `activityMinutes` を単数で持たせないこと。**
   「その日の主たる活動」が要る場面では、`activities` から**負荷の最も大きいブロック**を
   導出してください（保存しない）

```ts
// 「その日の主たる活動」が必要なとき（分析の絞り込みなど）
const primary = activities.length
  ? activities.reduce((a, b) => loadOf(a) >= loadOf(b) ? a : b)
  : null

// 「本番のあった日」の判定（ピーキング曲線などで使う）
const hasPerformance = activities.some(
  a => a.kind === 'performance' || a.kind === 'live'
)
```

## 8. 実装の順番

| 順 | 内容 | 規模 |
|---|---|---|
| 1 | `Activity[]` ＋ `ActivityItem[]` へのスキーマ移行（マイグレーション込み） | 2〜3日 |
| 2 | 活動ブロックのUI（追加・削除・種別ごとの欄）（§2.0） | 2〜3日 |
| 3 | 曲目リストUI（追加・削除・並べ替え）（§2.1） | 2〜3日 |
| 4 | 時間配分ロジック（§3.1）＋ `standardMinutes` の追加 | 1〜2日 |
| 5 | 負荷計算の二重合算（§4）＋ブロックごとのフィードバック表示 | 1日 |
| 6 | 「前回と同じ」（種別単位）＋保存したリスト | 2日 |
| 7 | 改行貼り付け＋まとめて登録 | 1日 |
| 8 | 帰属の段階1（按分）＋共起グループの検出 | 2日 |
| 9 | 帰属の段階2（リッジ回帰）※ n ≥ 30 で有効化 | 2〜3日 |

**1〜5 までで実用になります。** 6以降は使い勝手と精度の向上です。

**1 と 2 を先に、必ずこの順で。** 活動が入れ物なので、
先に曲目リストを作ると、あとで全部やり直しになります。

### マイグレーション

既存データは2段階で移します。**読み取り互換レイヤーを先に作ってください。**

```
■ 段階1：活動を配列に
  DayRecord.今日の活動（単数） + 活動時間
    → activities: [{ id, kind, minutes, items: [], order: 0 }]

  「休養」だった日
    → activities: []  かつ  recovery に休養方法を移す

■ 段階2：曲目をアイテムに
  曲目・演目（単一テキスト）
    空文字       → items: []
    テキストあり → normalizeTitle() で Repertoire を検索、なければ作成
                    items: [{ repertoireId, order: 0 }]
                    minutesOverride は設定しない（全時間がその1曲に配分される）
```

移行した `Activity` には `source: 'migrated'` を立て、
`startAt` が推定であること（実際には未記録であること）を分析側で区別できるようにします。

## 9. Sonnet 5 への依頼のコツ

- **活動ブロック（§2.0）を先に作らせる。** 入れ物が先、中身が後。
  曲目リストから作らせると、あとで全部やり直しになります
- **`DayRecord` に活動種別を単数で持たせないこと**（§6）。
  「その日の活動」は `activities` からの導出にする
- **`repertoireIds` と `minutesPerItem` の2本持ちにしないこと**（§6）。
  並べ替えと削除で添字がずれます。明示的に要件として書いてください
- 負荷計算は**活動係数がブロックごとに違う**ことを明示する（§4）。
  1日1つの係数で実装されがちです
- 時間配分（§3.1）は**純関数として切り出し、単体でテスト**させる。
  境界のテストを必ず入れること：全曲 override ／ 一部 override ／ `remaining < 0` ／
  `standardMinutes` が一部だけ登録済み ／ 曲0件 ／ **活動が複数で係数が違う**
- 並べ替えは `dnd-kit` などのライブラリでよいが、**モバイルのタッチ操作で確実に動くこと**を
  確認させる。長押し開始（250ms程度）にしないと、スクロールと干渉します
- §5.4 の共起検出は、**実装を飛ばさせない**。これがないとランキングが嘘をつきます
- 貼り付け時に登録プロンプトを連続表示させない（§2.4）

## 注意書き

帰属の推定は記録上の傾向であり、因果関係を示すものではありません。
共起により分離できない曲は、必ずその旨を表示してください。
`standardMinutes` は任意項目であり、未入力でも機能が成立することを保ってください。
