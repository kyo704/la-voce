# La Voce ／ 管理画面（運営者専用）実装仕様

運営者が全ユーザーの利用状況を把握するための管理画面 `/admin` の仕様。
実装は Claude Sonnet 5 を想定。

---

## 0. 設計の原則（最初に読む）

### 原則1 ｜ 「行動」と「健康データ」を分ける

管理画面で見たいのは**プロダクトの判断材料**であって、個々人の体調ではありません。

| | 見るもの | 個人単位で見てよいか |
|---|---|---|
| **行動** | どの項目を埋めたか、どこで離脱したか、いつ開いたか、記録日数 | **よい** |
| **健康データ** | 喉のスコア、症状の内容、体重、音名、メンタルの日記 | **見ない**（集計のみ・§5） |

**「どの項目を埋めたか」は行動、「何を入力したか」は健康データ**です。
この線を守れば、管理画面の大半は要配慮個人情報を扱わずに作れます。

### 原則2 ｜ 個人の健康記録は、管理画面に表示しない

**ユーザー一覧から個人ページを開いても、記録の中身は出しません。**
出すのは「12日記録した」「睡眠の欄は8割埋めている」「食事の欄は0%」といった
行動の情報だけです。

プロダクトの判断には、これで十分です。そして、
**ユーザーが「運営に体調が見られている」と感じるサービスは、正直に記録されなくなります。**
記録の質が落ちれば、このアプリの価値そのものが落ちます。

### 原則3 ｜ 集計には人数の下限を設ける

ユーザーが少ないうちは、**属性で絞り込むと個人が特定できます。**
「山梨県在住のテノール」が1人しかいなければ、それは匿名ではありません。

**n < 5 のセル・グループは、数値を出さず「—」と表示する。**（§5.2）

## 1. 認可とセキュリティ（最重要）

**管理画面は、このシステムで最も価値の高い攻撃対象になります。**

### 1.1 管理者の判定

```ts
// 環境変数で管理する。DBのフラグに依存しない
// ADMIN_USER_IDS="uid_abc,uid_def"
const ADMIN_IDS = (process.env.ADMIN_USER_IDS ?? '').split(',').filter(Boolean)

function isAdmin(userId: string): boolean {
  return ADMIN_IDS.includes(userId)
}
```

**DBの `is_admin` カラムにしないこと。** DBへの書き込み経路が1つでも漏れると、
自分で自分を管理者にできてしまいます。環境変数なら、デプロイ権限がなければ変更できません。

### 1.2 二重にガードする

- `middleware` で `/admin` と `/api/admin/*` をまとめてガード
- **加えて、各APIハンドラの先頭でも `isAdmin()` を再チェック**する

ミドルウェアの設定漏れやマッチャーの誤りは実際によく起きます。**両方やってください。**

### 1.3 ユーザーIDは匿名化して表示する

管理画面でも、生の `userId` やメールアドレスを一覧に出さない。

```ts
// 表示用の短縮ID（自分専用でも習慣として）
const displayId = sha256(userId + SALT).slice(0, 8)   // 例: 'a3f19c02'
```

サポート対応で特定が必要なときだけ、**明示的な操作**（検索ボックスにメールを入力）で
照合できるようにします。一覧に並べない。

### 1.4 監査ログ

**管理画面で何を見たかを記録してください。**

```ts
interface AdminAuditLog {
  id: string
  adminUserId: string
  action: string          // 'view_dashboard' | 'view_user' | 'search_email' | 'export'
  targetUserId?: string   // 個別ユーザーを見たとき
  at: string
  ip?: string
}
```

万一の事故のときに「何にアクセスされたか」を示せます。
**自分だけが使う画面でも、健康データを扱うサービスでは標準的な備えです。**

## 2. 画面構成

```
/admin
  ├─ 概要        既定のタブ
  ├─ 定着        ファネルと継続率
  ├─ 記録項目    項目ごとの入力率  ← 最も判断に効く
  ├─ 機能        分析カードの使用状況
  ├─ ユーザー    一覧と個別の行動タイムライン
  └─ 統計        健康データの集計（同意者のみ・§5）
```

**「統計」タブだけが健康データを扱います。** 他のタブは行動のみです。

---

## 3. 各パネルの仕様

### 3.1 概要

数字を4つだけ。**ダッシュボードにしない。**

```
登録             42人
直近7日に記録     18人
記録が3日以上     27人
有料              3人
```

### 3.2 定着（ファネル）

```
登録              42人  100%
初回の記録        31人   74%
3日目まで到達     22人   52%
7日目まで到達     14人   33%
14日目まで到達     9人   21%
28日目まで到達     5人   12%
```

**実数を必ず併記してください。** 割合だけだと、n=42 で1人動いただけの変化を
「改善した」と読み違えます。

**到達の定義**：登録日から数えて N 日目までに、通算 N 日分の記録があること
（連続でなくてよい）。

### 3.3 記録項目（最も重要なパネル）

**このセッションの「項目を減らす」判断を、データで裏づけるためのものです。**

| 項目 | 入力率 | 入力した人数 | 直近30日の入力率 |
|---|---|---|---|
| 喉の状態 | 98% | 31 | 99% |
| 睡眠時間 | 91% | 30 | 93% |
| 水分 | 62% | 24 | 58% |
| 体重 | 24% | 9 | 18% |
| 食事（詳細PFC） | 8% | 3 | 4% |
| 体質・既往症メモ | 2% | 1 | 0% |

**並び順は入力率の低い順**（＝削除・簡易化の候補が上に来る）。

読み方の目安を、画面に注記として書いておきます。

```
・入力率 10% 未満 …… 削除または詳細モード送りの候補
・入力率が二極化（入れる人はほぼ毎日、他は0%）…… 詳細度で出し分ける候補
・直近30日の入力率が全期間より大きく低い …… 飽きられている項目
```

**このパネルは、既存の記録テーブルだけで計算できます。**（§7 の第1版に含む）

```sql
-- 疑似SQL。実際のスキーマに合わせて調整すること
SELECT
  '睡眠時間' AS field,
  COUNT(*) FILTER (WHERE sleep_hours IS NOT NULL)::float / COUNT(*) AS fill_rate,
  COUNT(DISTINCT user_id) FILTER (WHERE sleep_hours IS NOT NULL) AS users
FROM day_records;
```

項目ごとに書くと長くなるので、**項目名 → カラム名の対応表を1つ持って、
ループで生成**してください。

### 3.4 機能（分析カードの使用状況）

| 指標 | 表示回数 | 「詳しく」到達 | 見た人数 |
|---|---|---|---|
| ウォームアップ効率 | 214 | 38 | 19 |
| 偏差値 | 198 | 12 | 18 |
| 症状カレンダー | 87 | 9 | 11 |
| 音域マップ | 41 | 2 | 6 |
| **効いた習慣** | **0** | **0** | **0** |

**一度も開かれていない指標を、目立たせてください。** 作った意味がありません。

このパネルは `events` テーブルが必要です（§7 の第2版）。

### 3.5 ユーザー（一覧と個別）

**一覧**

| ID | 登録 | 記録日数 | 最終記録 | 記録率 | プラン | 職業 |
|---|---|---|---|---|---|---|
| a3f19c02 | 7/12 | 31日 | 昨日 | 68% | 個人 | 声楽家 |
| b81d40f5 | 8/03 | 4日 | 12日前 | 17% | 無料 | 声優 |

- **ユーザーIDは匿名化（§1.3）**
- 並べ替え：最終記録が古い順（＝離脱した人が上に来る）

**個別ページ（行動のみ）**

```
a3f19c02 ・ 声楽家 ・ 登録 7/12 ・ 31日記録

項目ごとの入力率
  喉の状態    100%  ▓▓▓▓▓▓▓▓▓▓
  睡眠         97%  ▓▓▓▓▓▓▓▓▓▓
  水分         71%  ▓▓▓▓▓▓▓░░░
  食事          0%  ░░░░░░░░░░

記録のカレンダー（記録の有無のみ。中身は表示しない）
  ■■■□■■■ ■■■■■□□ ■■□□□□□ ...

直近の行動
  8/25 09:12  記録を開いた → 保存（47秒・簡易モード）
  8/24 21:40  分析を開いた → ウォームアップ効率を展開
  8/23 09:05  記録を開いた → 保存せず離脱（食事セクション）
```

**記録の中身は、いかなる場合も表示しないこと。**
カレンダーは「記録があったか」の有無だけです。

## 4. 「統計」タブ以外は、健康データに触れない

§3.1〜3.5 のすべてのクエリは、**健康データの値を SELECT しません。**
`IS NOT NULL` の判定と件数だけを使います。

**実装時に、この点をレビュー観点にしてください。**
「便利だから」と平均スコアを足したくなりますが、それは §5 の領域です。

## 5. 統計タブ（健康データの集計）

### 5.1 対象は同意した人だけ

```ts
// 記録項目v2 §6.2 の Consents
const eligible = users.filter(u => u.consents.statsUse != null)
```

**`statsUse` に同意していないユーザーのデータは、集計にも含めない。**
要配慮個人情報は、オプトアウトによる第三者提供が認められていません。
自社での統計利用も、**利用目的に明記したうえで同意を得た範囲**に留めます（§6）。

画面上部に必ず表示：

```
統計対象：同意済み 18人 / 全 42人
```

### 5.2 人数の下限（k匿名性）

**n < 5 のセル・グループは、数値を出さず「—」と表示する。**

```ts
const K = 5
const show = (n: number, value: string) => n >= K ? value : '—'
```

対象になるのは、職業別・声種別・地域別・年代別など、
**属性で絞り込むすべての表示**です。

### 5.3 出す内容

まずは3つだけ。

**① 症状の出現率**

```
乾燥      42%
嗄れ      18%
喉の張り感 15%
...
```

**② 職業別のコンディション分布**（n ≥ 5 の職業のみ）

平均ではなく**分布**（四分位）で見せてください。平均は外れ値に弱く、
n が小さいうちは誤読を招きます。

**③ 指標の分布**

自分で設計した指標（偏差値、ACWR、ウォームアップ効率）が、
**実際にどんな分布になっているか**。設計時の想定と合っているかの検証になります。

例：偏差値が 45〜55 に集中しすぎているなら、σ の下限クリップ（記録項目v2 §3.2）が
効きすぎている可能性があります。

## 6. プライバシーポリシーへの追記（必須）

**管理画面を作る前に、これを済ませてください。**

個人情報保護法では、取得時に示した**利用目的の範囲内**で使う必要があります。
「サービスの提供のため」しか書いていない場合、
**プロダクト改善のための分析は目的外**と読まれる余地があります。

利用目的に、次の趣旨を追加してください（ドラフト）。

> ・サービスの提供、維持、および**改善のための利用状況の分析**
> ・（同意いただいた方のみ）**統計情報の作成**。統計情報は個人を識別できない形に
>   加工したうえで作成し、個人が特定されうる少人数の集計は行いません

**既存ユーザーがいる場合は、改定の通知が必要です。**
内容の妥当性は専門家に確認してください。

## 7. 実装の段階

### 第1版：既存テーブルだけで作る（events 不要）

**これだけで、判断に必要な情報の大半が揃います。**

| パネル | 第1版 |
|---|---|
| 概要 | ✅ |
| 定着（ファネル） | ✅ |
| **記録項目（入力率）** | ✅ **最も効く。ここから作る** |
| ユーザー一覧 | ✅ |
| ユーザー個別（入力率・記録カレンダー） | ✅ |
| 機能（分析カードの使用状況） | ❌ 第2版 |
| ユーザー個別（行動タイムライン） | ❌ 第2版 |
| 統計タブ | ✅（同意者がいれば） |

**規模：2〜3日**

### 第2版：events テーブルを足す

```ts
interface AppEvent {
  id: string
  userId: string
  name: string           // 下記の15種類のみ
  props: Record<string, unknown>   // ★健康の値を入れない
  at: string
  sessionId?: string
  platform?: 'web' | 'pwa'
}
```

記録するイベントは**15種類まで**。増やすと、どれも見なくなります。

```
signup_completed
record_opened          { date, isToday }
record_saved           { fieldsFilled: string[], durationMs, mode, template }
record_abandoned       { lastSection }
voice_entry_added
analysis_opened
analysis_card_viewed   { metricId }
analysis_card_expanded { metricId }
unlock_reached         { level }
notification_clicked   { channel }
install_prompt_shown
install_prompt_accepted
checkout_started
checkout_completed
support_form_submitted
```

**`props` に健康の値を入れないこと。**
`fieldsFilled` は**項目名の配列**であって、値ではありません。

```
✓ record_saved { fieldsFilled: ['bodyFeel','sleep'], durationMs: 47000 }
✗ record_saved { bodyFeel: 2, symptoms: ['乾燥'] }
```

**規模：3〜4日**

## 8. n が小さいうちの使い方（画面に注記として書く）

ユーザーが5〜20人のとき、**「完了率68%」のような数字はノイズ**です。
1人の行動で10ポイント動きます。

管理画面の「概要」タブの上部に、次の注記を常時表示してください。

```
ユーザーが少ないうちは、割合より個別の軌跡を見てください。
「ユーザー」タブから、離脱した人が何日目に、どのセクションで
止まったかを1人ずつ追うほうが、多くのことが分かります。
```

**n=20 の平均は無意味ですが、n=20 の個別の物語は金脈です。**

## 9. Sonnet 5 への依頼のコツ

- **§3 のパネルで、健康データの値を SELECT させない。**
  `IS NOT NULL` の判定と件数のみ。レビュー観点として毎回渡してください
- **管理者判定を DB のフラグにさせない。** 環境変数 `ADMIN_USER_IDS`（§1.1）
- **ミドルウェアと各APIハンドラの両方でガード**させる（§1.2）。
  「ミドルウェアがあるから不要」と省略させない
- 項目ごとの入力率は、**項目名→カラム名の対応表を1つ持ってループで生成**させる。
  項目ごとにクエリを手書きさせない
- **第1版に `events` テーブルを含めさせない。** 既存テーブルだけで作り、
  動いてから第2版に進む
- 統計タブは **`statsUse` 同意者のみ**、**n < 5 は「—」**。
  この2つを実装から漏らさせない
