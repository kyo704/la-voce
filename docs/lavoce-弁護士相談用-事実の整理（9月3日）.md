## 2　何が起きたか

### 2-1　仕組みの説明（前提）

本サービスはデータベースに Supabase（PostgreSQL）を使用し、
行単位アクセス制御（RLS）で、誰がどの行を読めるかを制御しています。

★RLSは「行」単位でしか制御できません。
　ある行が読める相手には、**その行の全ての列**が読めます。

### 2-2　問題のあった設定

`profiles` テーブルに、次のポリシーが設定されていました。

```
名称    profiles_connected_display_name
対象    SELECT（読み取り）
条件    are_connected(auth.uid(), id)
```

★この `are_connected()` という関数は、**開発用リポジトリのどこにも存在せず**、
　本番データベースに直接適用されたまま、記録が残っていませんでした。
　関連するコードの記述から、**先生と生徒のつながりを判定するもの**と
　強く推定されます。

### 2-3　その結果、何が可能だったか

```
つながりのある先生アカウントから、生徒の profiles 行の
★全ての列が取得可能でした
```

`profiles` に含まれる列（主なもの）

```
表示名 / 職種
★既往症（逆流性食道炎・声帯結節などから選択）　← 要配慮個人情報
★常用薬
★アレルギー
★18歳未満かどうか
★健康に関する自由記述
★女性の周期に関する設定
LINEの利用者ID
```

### 2-4　アプリの画面では、何が見えていたか

```
アプリからこのポリシーに依存する呼び出しは3箇所
　　いずれも「表示名」と「職種」の2列しか要求していません
　　★通常の画面操作では、既往症等は表示されません
```

★ただし、APIを直接呼び出せば、全ての列を取得できる状態でした。
　**この2つは、両方が事実です。**

## 5　実際に読まれたか

```
結論  ★「確認できる唯一の期間（直近24時間）には形跡がなかったが、
　　　　それ以前の期間は原理的に確認不能」
```

理由

```
・利用しているサービス（Supabase）のログ保持期間は、
　★選択できる上限が24時間である
・ポリシーが存在した期間の大半は、その範囲外である
・直近24時間のログには、該当する記録が0件だった
　　★ログ機構そのものが該当の読み取りを記録することは、
　　　実地に確認した（★確認結果を記入）
```

★「調べていない」のではなく、「制度上、調べられない」ものです。
　そのため、3（誰が読める状態にあったか）で範囲を特定する方法に
　切り替えています。
