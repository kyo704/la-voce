# La Voce 職業別プロファイル 設計案

作成日: 2026-08-27
関連: `La_Voce_改善タスク_v2.md`（4-1 レイアウト / 3-1 発声量の実測）、`la-voce-learn-content`（職業ID の定義）

扱う論点は3つです。

- **A. 活動記録（練習・公演）を職業で出し分ける**
- **B. 会場の響きの用語と尺度を直す**
- **C. 身体データの整理**（Sonnet との議論を受けて。第4章）

---

## 0. 設計の中心原則

**正規化した値を保存し、表示ラベルだけを職業で切り替える。**

これを全体の原則とします。理由は3つあります。

1. **職業を変えても過去データが死なない。** ラベルだけの切り替えなら、声楽家として記録した半年分が、
   ミュージカルに軸足を移した後も同じ意味で読めます。選択肢そのものを職業ごとに別テーブルで持つと、
   切り替えた瞬間に過去が読めなくなります
2. **職業をまたいだ分析ができる。** 「本番の翌日は喉が落ちる」という傾向は職業を問わず成立します。
   保存値が共通なら、この分析は全ユーザーで動きます
3. **兼業に対応できる。** 声楽家がミュージカルもやる、声優が歌う、演者が指導もする。
   実際には珍しくありません

**やってはいけないのは、職業ごとに別々の選択肢文字列をそのまま保存することです。**
「本番」「ライブ」「アフレコ」を生の文字列で保存すると、分析側が職業の数だけ分岐します。

## 1. 職業IDの定義

`la-voce-learn-content` の職業タブと**同じIDを使ってください。** 「学ぶ」の記事出し分けと、
記録項目の出し分けが同じキーで動くようにするためです。

| professionId | 表示名 |
|---|---|
| `classical-musical` | 声楽家・ミュージカル |
| `announcer` | アナウンサー・ナレーター |
| `voice-actor` | 声優 |
| `pops-rock` | ポップス／ロック |

### 指導者は「5つ目の職業」にしないでください

ボイストレーナー・声楽教師は、上の4つのいずれかを兼ねているのが普通です。
5つ目の職業タブにすると、「声楽家でもあり指導者でもある」人がどちらかを選べなくなります。

**`teaches: boolean` というフラグで持ってください。** これがオンのとき、活動タイプに「指導する」が追加され、
レッスンタブが表示されます。

### プロフィールの持ち方

```
primaryProfession: professionId        // 1つ。UIのラベルはこれで決まる
alsoWorksAs: professionId[]            // 兼務。0個以上
teaches: boolean                       // 指導もしているか
```

**「職業ボタン一つで分けられる」という要件は `primaryProfession` が担います。**
`alsoWorksAs` は、その職業の記録項目を追加で表示するためのものです（例: 声楽家が声優も兼ねる場合、
叫びテイク数の欄が出る）。デフォルトは空で構いません。

## 2. A. 活動記録の職業別出し分け

### 2-1. 現状の問題

現在の選択肢は **休養 / 自主練習 / レッスン / リハーサル / 本番** の5つです。舞台系の語彙で統一されています。

**問題1: 「本番」が職業によって指すものが違いすぎる。**
声楽家の「本番」は2時間の公演です。声優の「本番」は1テイク、数十秒のこともあります。
同じラベルで負荷が10倍以上違うのに、発声負荷の計算では同じ重みで扱われます。

**問題2: レコーディングという区分がない。**
ポップスと声優にとっては主要な業務ですが、現在は「本番」か「リハーサル」に押し込むしかありません。
レコーディングは本番と負荷の形が違います（テイクを重ねる、長時間、しかし1テイクは短い）。

**問題3: ポップス・声優の現場語が一つもない。**
スタジオリハ、ライブ、アフレコ、ゲーム収録、ナレ録り。いずれも該当する選択肢がありません。

**問題4: 指導する側の区分がない。**
「レッスン」は受ける側の語です。指導者は一日に何コマも声を出しますが、記録する場所がありません。

### 2-2. 正規化された活動タイプ

保存するのはこの `activityType` です。表示ラベルは職業で切り替えます。

| activityType | 意味 | 声を使うか |
|---|---|---|
| `rest` | 休養 | 使わない |
| `self_practice` | 一人での練習 | 使う |
| `lesson_taking` | レッスン・指導を受ける | 使う |
| `lesson_giving` | 指導する（`teaches: true` のときのみ表示） | 使う |
| `rehearsal` | 合わせ・稽古・リハーサル | 使う |
| `performance` | 本番 | 使う |
| `recording` | 収録・レコーディング | 使う |
| `speaking_work` | 発話業務（放送・司会・会議） | 使う |
| `other` | その他 | 任意 |

職業別のラベルは、この9つのうち**その職業で使うものだけを、その職業の言葉で**出します。

### 2-4. 負荷の重みについて（重要）

現在の発声負荷は、活動の種類から推定していると思われます。ここに落とし穴があります。

**職業共通の係数を使わないでください。** 声優の「アフレコ1本」と声楽家の「本番1回」を同じ重みにすると、
発声負荷バランスが機能しません。

対応は2段階です。

**段階1（暫定）:** 職業ごとの既定係数を持つ。`professionId × activityType` で係数を引きます。
`profession-presets.json` に初期値を入れてあります。あくまで暫定値であることを、
分析画面の注記に書いてください。

**段階2（本命）:** 改善タスク v2 の 3-1「発声量の実測」が入ったら、**実測の発声時間を優先**します。
係数は実測がない日のフォールバックに降格します。

実測が入るまでは、発声負荷の分析に「活動の種類からの推定値です」と明示してください。

### 2-5. 職業固有の追加項目

活動タイプとは別に、**その職業でだけ意味のある記録項目**があります。
`primaryProfession` または `alsoWorksAs` に該当する職業が含まれるときだけ表示してください。

| 職業 | 追加項目 | 備考 |
|---|---|---|
| `voice-actor` | 叫び・悲鳴のテイク数 | **既存機能。** 現在は全職業に出ていると思われるので、出し分けの対象にする |
| `voice-actor` | その日の現場数 | 掛け持ちの負荷を拾う |
| `classical-musical` | 公演の出来 | **既存機能**（本番ピーキング曲線が参照） |
| `classical-musical` | 演目・役 | ノートと接続 |
| `pops-rock` | セットリスト曲数 | 発声量の代理指標 |
| `pops-rock` | モニター環境（イヤモニ / 転がし / なし） | 第3章の響きと合わせて負荷を説明する |
| `announcer` | 連続発話時間 | 3-1 の発声セッションで代替できるなら不要 |

**逆に、出し分けで隠すべき既存の分析カードもあります。**

| カード | 表示対象 |
|---|---|
| 叫びテイク数の閾値 / 回復曲線（叫び・悲鳴） | `voice-actor` のみ |
| パッサッジョの安定度 | `classical-musical`, `pops-rock` |
| 話声位の日内変動 | `announcer`, `voice-actor` を優先。他職業は任意表示 |
| ツアー耐久曲線 | `classical-musical`, `pops-rock` |
| 本番ピーキング曲線 | `speaking_work` 中心の `announcer` では意味が薄い。任意表示 |

現在これらは全ユーザーにロックカードとして並んでいます（v2 の 4-1(a) 参照）。
**職業に関係ないカードが「あと14日で解放されます」と表示され続けるのは、待たせているだけで永久に使われません。**
出し分けを入れると、ロックカードの数自体が減ります。

## 3. B. 会場の響き

### 3-1. 現状の問題

現在の選択肢は **デッド / 普通 / ライブ** です。4つ問題があります。

**問題1: 「ライブ」が二義的です。**
音響用語の live（よく響く）と、公演を指す「ライブ」が同じ語です。
ポップス歌手にとって「ライブ」は圧倒的に後者です。しかも同じ記録画面に
「活動＝ライブ本番」が並ぶ設計になるので、**同一画面で同じ語が2つの意味で使われます。**

**問題2: 声楽家の語彙ではありません。**
ご指摘のとおりです。声楽の現場で「デッド」は通じますが、その反対を「ライブ」と呼ぶ人は多くありません。
「よく響く」「残響が長い」「響きが返ってくる」といった言い方をします。

**問題3: 3段階では足りません。しかも直線に見えます。**
これが一番大きい問題です。現在の並びは「デッド ← → ライブ」という直線で、
暗黙に**デッドが悪くてライブが良い**と読めます。

しかし実際には、**響きすぎる会場も歌いにくい**はずです。石造りの教会、大聖堂、体育館。
残響が長すぎると、自分の直前のフレーズが返ってきて次が聞こえない、アンサンブルが合わない、
子音が潰れる。ポップスなら音が濁ります。

つまり響きは**両端が難しく、真ん中が扱いやすい**という非直線の軸です。3段階の直線表現では、
この構造が表せません。

**問題4: 声優・アナウンサーにはほぼ意味がありません。**
ブースは意図的にデッドに作られているので、ほぼ常に同じ値になります。
毎日「デッド」を選ばせるのは記録負荷の無駄です。

### 3-2. 提案: 5段階の中立尺度

保存値は `reverberance` として **1〜5の整数**を持ちます。

| 値 | 中立の意味 | 歌いやすさ |
|---|---|---|
| 1 | ほとんど響かない | 難しい |
| 2 | 響きが少ない | やや難しい |
| 3 | ふつう | 扱いやすい |
| 4 | よく響く | 扱いやすい |
| 5 | 響きすぎる（残響が長い） | 難しい |

**UI上で、両端が難しい側であることが分かる表現にしてください。** 左右対称に配置する、
両端の色を揃える、など。直線のスライダーで端に行くほど良さそうに見える表現は避けてください。

### 3-3. 職業別のラベル

| 値 | 声楽家・ミュージカル | ポップス／ロック | 声優・アナウンサー |
|---|---|---|---|
| 1 | 響かない | デッド | ブース（無響に近い） |
| 2 | 響きが少ない | ややデッド | 吸音された部屋 |
| 3 | ふつう | ふつう | ふつうの部屋 |
| 4 | よく響く | よく響く | 響きのある部屋 |
| 5 | 響きすぎる | 響きすぎる | かなり響く |

**ポップスでも「ライブ」という語を使わないことを推奨します。** 業界語としては自然ですが、
同じ画面の活動記録に「ライブ本番」が並ぶ以上、避けたほうが安全です。
どうしても使う場合は「よく響く（ライブ）」と併記してください。

### 3-4. 場所プリセット（記録負荷を下げる仕組み）

5段階を毎日考えさせるのは負担です。**場所の種類をタップすると値が入り、後から微調整できる**形にしてください。

**声楽家・ミュージカル**

| プリセット | 既定値 |
|---|---|
| 練習室・レッスン室 | 2 |
| スタジオ | 2 |
| 小ホール | 3 |
| 大ホール | 4 |
| 教会・大聖堂 | 5 |
| 屋外 | 1 |

**ポップス／ロック**

| プリセット | 既定値 |
|---|---|
| リハスタ | 2 |
| ライブハウス | 2 |
| ホール | 3 |
| アリーナ・大箱 | 4 |
| 野外 | 1 |
| レコーディングブース | 1 |

**声優・アナウンサー**

| プリセット | 既定値 |
|---|---|
| アフレコブース | 1 |
| ナレーションブース | 1 |
| 会議室・仮設ブース | 3 |
| イベントホール | 4 |
| 屋外 | 1 |

**前回と同じ場所を1タップで再入力できるようにしてください。** 同じ現場が続く時期は、
これだけで入力が消えます（「前日をコピー」と同じ思想）。

### 3-5. 屋外は別フラグにしてください

屋外は響き1ですが、**同時に気温・湿度・風・声を張る必要が効きます。** 響きの値だけで屋外を表すと、
「響かない部屋」と「野外」が同じ値になり、分析が混ざります。

`isOutdoor: boolean` を別に持ってください。

### 3-6. 分析側の扱い

**「環境の快適帯」に響きを足さないでください。**

現在この分析は 絶対湿度 × 喉のコンディション の2軸です。ここに響きを足すと3軸になり、
1マスあたりの件数が激減します。今でも「まだ明確な快適帯は見えていません」と表示される段階です。

響きは**独立したカードとして持ってください。** 「響きごとの声の傾向」として、
5段階それぞれの喉・声・心の余裕の平均を出します。当然、P0-1 の件数ゲートに従わせてください。

### 3-7. 追加提案（任意・優先度は低め）

響きだけでは負荷を説明しきれません。同じデッドな会場でも、モニターが良ければ楽に歌えます。
逆にモニターが返ってこないと、無意識に張ります（ロンバード効果。学ぶの C5-3 / P-2 で扱っています）。

**「声を張る必要があったか」を1〜5で1項目**足すと、この機構を直接拾えます。
響きより素直に負荷と相関する可能性があります。

ただし項目が増えるので、**詳細層（任意入力）に置いてください。** 最小記録セットには入れません。

## 4. C. 身体データの整理

Sonnet との議論を踏まえた回答です。

### 4-1. Sonnet の整理への評価

**①「恒久的な情報を畳む」— 賛成です。**
**②「入力欄すべてを最小化することへの慎重論」— 完全に同意します。**

②の指摘は正しいです。改善タスク v2 で問題にしたのは「**長い説明文が入力欄の間に挟まっていること**」であって、
入力欄そのものではありませんでした。毎日触る欄を畳めば、毎日タップが増えます。
「30秒で終わる記録」（v2 の P1-1）と正面から衝突します。ここは Sonnet の判断が正しいです。

### 4-2. ただし、折りたたみは半分の解です

**恒久的な設定は、畳むのではなく「今日の記録」から出してください。**

根拠があります。アプリ自身が「もっと」画面にこう書いています。

> プロフィール・記録項目
> 現在は「今日の記録」タブの「身体データ」欄にまとまっています。
> **専用の設定画面への切り出しは今後の対応予定です。**

つまりこれは、もともと予定されていた作業です。折りたたみは、その手前の暫定策にあたります。

畳んだ場合、毎日の記録画面に「開かない何か」が残り続けます。切り出せば、
**今日の記録には毎日の入力だけが残り、そもそも畳む必要がなくなります。**

推奨する順序:

1. **今すぐ:** 恒久的な設定をアコーディオンに畳む（Sonnet の提案どおり。低リスク・即効）
2. **その次:** 畳んだ塊を「もっと > プロフィール・記録項目」へ移設し、今日の記録から消す
3. 記録画面には、設定画面への小さなリンクを1つだけ残す

1をやってから2に進めば、途中で止まっても状態が悪化しません。

### 4-3. 分類の基準

項目リストを渡すより、**基準を渡すほうが確実です。** 新しい項目が増えたときにも判断できます。

| 層 | 判定基準 | 置き場所 | 折りたたみ |
|---|---|---|---|
| **恒久** | 1年経ってもほぼ変わらない | もっと > プロフィール・記録項目 | — |
| **半恒久** | 数ヶ月〜シーズン単位で見直す | 同上。記録画面から1タップで飛べる | — |
| **毎日** | その日固有の値がある | 今日の記録 | **畳まない** |

**判定に迷ったときの問い:「昨日と今日で、値が変わりうるか」**

変わりうるなら毎日の入力。変わらないなら設定です。この問いだけでほぼ分類できます。

### 4-4. 想定される分類（**要確認**）

**注意: 私は身体データ欄の中身を直接確認できていません。** ブラウザ接続が切れているためです。
以下は他の画面から推定したものです。**Sonnet に実物の項目一覧を出させて、突き合わせてください。**

| 層 | 想定される項目 |
|---|---|
| 恒久 | 身長 / 生年月日・年齢 / 性別 / 職業 / 声種・Fach / 既往症 / 常用薬 / アレルギー |
| 半恒久 | 目標タンパク質係数（現在「破線が身体データで設定した目標係数です」と分析に出ている）/ 目標カロリー / 活動レベル |
| 毎日 | 体重 / 体脂肪率 / その日の服薬 / 症状 / 食事 / 水分 / 睡眠 / 心の余裕 / 気持ちタグ |

**判断が割れそうな項目を2つ挙げておきます。**

- **体重** — 毎日です。分析に「体重の推移（直近30日）」があり、日々の値が使われています。
  ただし v2 の C4-8 で書いたとおり、このアプリは体重を目標として扱わない立場です。
  毎日入力欄に置きつつ、目標値や理想レンジは表示しないでください
- **常用薬 と 今日の服薬** — **分けてください。** 常用薬のリストは恒久設定です。
  「今日それを飲んだか」「今日だけ飲んだ薬があるか」は毎日の入力です。
  受診用サマリーの「既往・服薬」欄は、この両方を参照します

### 4-5. Sonnet への依頼文（差し替え版）

Sonnet が用意したたたき台に、上記を反映したものです。こちらを送ってください。

```
一日の記録タブの「身体データ」セクションを見直してほしいです。

現状、恒久的な設定情報（既往症・常用薬のリスト・身長など、ほぼ変更しない情報）と、
毎日入力する情報（今日の体重・体脂肪率・今日の服薬・症状など）が、同じセクション内で
混在してスクロールが長くなっている可能性があります。

まず、次の2つを出してください。実装はそのあとで相談させてください。

(1) 「身体データ」セクションの現在の項目一覧
(2) 各項目を「恒久」「半恒久」「毎日」のどれかに分類した案

分類の基準は「昨日と今日で、値が変わりうるか」です。
変わりうるなら毎日、変わらないなら恒久としてください。
目標値の設定（目標タンパク質係数など）は、シーズン単位で見直すものなので半恒久です。

実装方針は次のとおりです。

・恒久／半恒久の項目は、折りたたみ（アコーディオン）にして、変更したい人だけが開く形に
・毎日入力する項目は、これまで通り展開したままにしてください
  （これらまで畳むと毎日タップして開く手間が増え、「30秒で終わる記録」という方針に
  反するため、畳まないでください）

なお、折りたたみは暫定策と考えています。「もっと」画面に
「現在は『今日の記録』タブの『身体データ』欄にまとまっています。専用の設定画面への
切り出しは今後の対応予定です」という記述があるとおり、最終的には恒久／半恒久の項目を
「もっと > プロフィール・記録項目」へ移設し、今日の記録から消すのが本来の形です。
折りたたみの実装時に、あとで移設しやすい構造にしておいてください。

分類で判断に迷いそうな点を2つ補足します。

・体重は「毎日」です。分析タブの「体重の推移」が日々の値を使っています。
  ただし目標体重や理想レンジは表示しないでください（このアプリは体重を目標として
  扱わない立場を取っています）
・「常用薬のリスト」と「今日の服薬」は分けてください。前者は恒久、後者は毎日です。
  受診用サマリーの「既往・服薬」欄は両方を参照します
```

## 5. データ移行

既存データがあるので、移行の指示です。

### 5-1. 活動タイプ

現在の値を canonical へマップします。

| 現在の値 | activityType |
|---|---|
| 休養 | `rest` |
| 自主練習 | `self_practice` |
| レッスン | `lesson_taking` |
| リハーサル | `rehearsal` |
| 本番 | `performance` |

すべて1対1で対応するので、欠損は出ません。subtype は空のままで構いません。

### 5-2. 会場の響き

3段階から5段階への移行です。

| 現在の値 | reverberance |
|---|---|
| デッド | 2 |
| 普通 | 3 |
| ライブ | 4 |

**1と5は、移行後の新規記録にしか現れません。** 移行前のデータには両端が存在しないことになります。

このことを分析の注記に書いてください。「◯月以前の記録は3段階で記録されていたため、
両端の値を含みません」といった形です。書かないと、「響きすぎる日が一度もない」という
誤った傾向として読まれます。

## 6. 実装順序

1. **プロフィールに `primaryProfession` / `alsoWorksAs` / `teaches` を追加**（既存ユーザーは職業欄から推定して初期値を入れる）
2. **活動タイプの正規化とデータ移行**（5-1）— 表示ラベルはまだ変えない
3. **職業別ラベルの出し分け**（2-3）
4. **分析カードの出し分け**（2-5 後半）— ロックカードが減るので効果が大きい
5. **響きの5段階化とデータ移行**（3-2 / 5-2）
6. **場所プリセット**（3-4）
7. **身体データの折りたたみ**（4-2 の段階1）
8. 職業固有の追加項目（2-5 前半）
9. 身体データの設定画面への移設（4-2 の段階2）
10. 「声を張る必要があったか」（3-7・任意）

2 と 5 はデータ移行を伴うので、バックアップを取ってから実行してください。
なお改善タスク v2 の P0-3（データ書き出し機能）が先に入っていると、この作業が安全になります。

## 7. 同梱ファイル

`profession-presets.json` に、以下を機械可読な形で入れてあります。

- 職業ID の定義
- activityType の定義と、職業別の表示ラベル・subtype
- 職業 × activityType の暫定負荷係数
- reverberance の職業別ラベル
- 場所プリセットと既定値
- 分析カードの表示対象職業
- 移行マッピング

このファイルをそのまま設定として読み込めるようにすると、後から職業を追加するときに
コードを触らずに済みます。
