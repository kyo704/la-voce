## §1 論点3 ── 軸は「職業」ではありません ★先に決められます

★Sonnet の立てた問いは、こうです。

```
「歌唱」と限定するか、「レッスン・本番での発声」と広く取るか
　　→ 声楽家には歌唱が中核だが、落語家・声優は話し声が本業
```

★**この問いの立て方を、1つ直させてください。**

```
（誤った軸）歌唱 ／ 話し声
　　　　　　→ ★職業ごとに意味が変わります
　　　　　　→ 職業が増えるたびに、列の意味を問い直すことになります

（正しい軸）★意図して負荷をかけた発声 ／ 日常の発声
　　　　　　→ ★職業に依存しません
```

★当てはめてみてください。

```
声楽家の歌唱          ★意図して負荷をかけた発声
声優の収録            ★同じ
落語家の高座          ★同じ
アナウンサーの本番    ★同じ
ナレーターの録音      ★同じ

打ち合わせ・電話・雑談  ★日常の発声
```

★**どの職業でも、同じ線で切れます。**

★そして、この軸は**分析の上でも正しい**です。

```
体にかかる負荷が違うのは「歌ったか話したか」ではなく、
★「意図して大きく／長く／高く出したか」です
```

★したがって

```
★職業設計を待たずに、この列は決められます
★職業設計が来ても、この列は壊れません
```

★「#34の最小の形」と「職業再設計後の本来の形」を分ける必要は、**ありません。**
　**最初から、本来の形で作れます。**

★命名について

```
既存が offStageVoiceMinutes（舞台の外）なら、
対になるのは「舞台の上」ですが、★レッスンが入りません

★意味で名づけてください（場所ではなく）
　　例：professionalVoiceMinutes ／ loadedVoiceMinutes

★正確な名前は、既存列の定義を見てから決めてください（§3）
```

★★**列の名前が、意味を決めます。**場所で名づけると、レッスンが入らなくなります。

## §2 論点2 ── 当面は記録のみ。★中核に加えないでください

```
（採用）★当面は記録のみ
（採用しない）新列を、いま中核項目に加える
```

★理由は3つです。

```
1  ★既存の利用者に、この列の過去分がありません
　　　→ n が足りません
　　　→ 3ゲートの1つ目（各群 n≥10）を、当分は通りません

2  ★項目が増えると、BH-FDR が厳しくなります
　　　→ 多重比較の補正は、比較の数で効きます
　　　→ ★いまの4〜5項目でも通りにくいところに、1つ増やす
　　　→ ★既存の項目の発見が、遅くなります

3  ★中核5項目は、実装・確認済みです
　　　→ いま変えると、過去の分析結果と比べられなくなります
```

★**加えるかどうかは、あとで実測で決めてください。**

```
・この列が半年たまったところで、
　★「この列を入れたときと入れないときで、発見の数がどう変わるか」を実測する
・増えるなら、そのとき中核に加える
　　→ ★勘で決めない
```

★これは「何日で発見が出るか」の実測と、同じ枠組みです。

## §3 論点1 ── 独立の新列に賛成。★ただし理由を1つ足します

★Sonnet の推し（独立新列／既存データの移行を避ける）に賛成です。
　**理由を、もう1つ足させてください。**

```
（Sonnet の理由）既存データの移行を避けるため
（★足す理由）  既存の列の意味を、あとから変えないため
```

```
既存列を「話し声」と「歌唱」に再編すると
　　→ ★過去に記録された値が、どちらだったか分かりません
　　→ 分けようがないので、★全部を片方に寄せることになります
　　→ ★その時点で、過去のデータが汚れます
```

★**過去のデータは、意味を変えないでください。**
　新しい列を足せば、過去は過去のまま残ります。

★ただし、**条件が2つあります。**

```
条件1  ★既存列の定義が「舞台の外での発声すべて」なら、
　　　 レッスンの分は★これまで既存列に入っていた可能性があります
　　　 → 新列を足すと、★同じ時間が2か所に入る危険があります
　　　 → ★既存列の定義を確認してから（これが Code への確認です）

条件2  ★7つの台帳に登録すること
　　　 そして★分析のコードが、この列を（当面）無視することを確認すること
```
