# 仕様 ── 教室の表示肩書き（display_title）

全 373 行 / 末尾は「肩書きは、その人のものではなく、教室がその人に向ける呼び方です。」

作成 2026年9月4日 ／ slot ⑥・急ぎではありません

---

## §0 先に、事実を3つください

仕様を書きますが、**次の3つが確認できるまで、当てないでください。**
前提（「既存の判定を流用するだけ」）が崩れるとしたら、ここです。

```
① memberships の UPDATE ポリシー全文（USING と WITH CHECK の両方）
   ポリシー名ではなく、句を見てください

② memberships への GRANT が、★表単位か列単位か
   SELECT * FROM information_schema.column_privileges
     WHERE table_name='memberships' AND privilege_type='UPDATE';
   行が列ごとに出れば列単位、出なければ表単位です

③ いま先生の呼び名を返している関数（get_connected_names など）の定義
```

**②の結果で、この仕様の半分が変わります。**

```
列単位だった場合  新しい列は誰も書けません（fail-close）。
                  ★GRANT UPDATE (display_title) を明示的に足す必要があります。
                  「ポリシーの新設は不要」は正しいが、
                  ★「権限の追加は不要」は正しくありません

表単位だった場合  ★列を足した瞬間に、UPDATE ポリシーを通る人全員が書けます。
                  誰が通るかを ① で確かめてから足してください
```

`memberships` のポリシーは、9月3日に1本壊れていました
（`m.org_id = m.org_id` で常に偽）。**この表は一度信用を落としています。**
名前で判断せず、句を読んでください。

## §1 列の形

```sql
-- 形だけ示します。実行は Sonnet の側です
ALTER TABLE memberships
  ADD COLUMN display_title text,
  ADD COLUMN display_title_updated_by uuid,
  ADD COLUMN display_title_updated_at timestamptz;

ALTER TABLE memberships
  ADD CONSTRAINT display_title_shape CHECK (
    display_title IS NULL
    OR ( char_length(display_title) BETWEEN 1 AND 20
         AND display_title = btrim(display_title)
         AND display_title !~ '[[:cntrl:]]' )
  );
```

### なぜ `updated_by` / `updated_at` を足すのか

**他人の見え方を、他人が変えられる機能だからです。**

履歴の表を1本作るのは、20字の肩書きには重すぎます。
でも「最後に誰が変えたか」が無いのは弱すぎます。2列で折衷します。

`updated_by` は `auth.uid()` を入れます（★台帳03に登録が要ります）。

## §2 端の場合 ── 6つ

### ① 20字を超えたとき

**サーバ側で拒否します。** 画面だけの制限にしないでください。
CHECK 制約で落とします。画面は先に止めますが、それは親切であって、守りではありません。

### ② 空文字と null

**空文字を保存させないでください。** これがいちばん大事な端です。

```
入力が空、または空白だけ  → ★null にする（空文字を入れない）
```

理由。空文字が入ると、

```
「未設定」なのか「明示的に空にした」のか、★区別できなくなります
```

これは「明示的に選ばれた値とシステムの既定値を区別する」という
既存の裁定を、そのまま壊します。

保存前に `btrim` して、長さ0なら null。CHECK 制約でも二重に落とします。

### ③ 前後の空白

`btrim` してから保存します。CHECK でも弾きます（`= btrim(...)`）。

### ④ 改行・制御文字

**禁止です。** 一覧の行が壊れます。CHECK の `[[:cntrl:]]` で落とします。

### ⑤ 絵文字

**許可します。** ただし数え方を決めておきます。

```
char_length()      = コードポイント数で数える（PostgreSQL の既定）
```

絵文字は1文字に見えて複数コードポイントのことがあります
（肌色つき、家族の絵文字など）。20の枠に3つしか入らない場合があります。
**それでよい**とします。ここを厳密にすると、実装が重くなるだけです。

画面側の文字数カウンタも `Array.from(s).length` ではなく
サーバと同じ数え方に合わせてください。★ずれると「20字なのに保存できない」が起きます。

### ⑥ 同じ肩書きが複数

**許可します。** 「講師」が5人いてよい。一意制約は付けません。

## §3 ★入れられない語（追加の裁定）

これは相談に無かった点です。**足してください。**

自由入力の肩書きは、**名乗りの経路**です。2つ危ないものがあります。

### ① 資格の名称

```
医師  医者  ドクター  Dr  Doctor  歯科医
看護師  薬剤師  言語聴覚士  理学療法士  作業療法士
管理栄養士  栄養士  保健師  助産師  公認心理師
```

医師法18条は「医師でなければ、医師又はこれに紛らわしい名称を用いてはならない」
と定めています。他の名称独占資格も同じ形です。

**本当に医師である先生もいるでしょう。** それでも入れません。理由は1つです。

```
アプリが、それを確かめられないからです。
```

★「確かめられないことを、表示しない」──これを規則にしてください。
9月4日に決めた「今日の目安」の線とも、同じ考え方です。

拒否したときの文言：

```
「資格の名前は、こちらで確かめられないため、お使いいただけません。」
```

「あなたが医師ではないから」ではありません。**確かめられないから**です。

### ② 運営を装う語

```
運営  公式  Woolsong  ウールソング  サポート  事務局  管理者  システム
```

生徒が「運営からの連絡」と誤認します。
`org_event_requests` の連絡機能と組み合わさると、実害が出ます。

### 置き場所

`lib/linkConsent.js` の `FORBIDDEN_LINK_PHRASES` と**同じ作法**で、
1つのファイルに配列で置いてください。★サーバ側でも同じ配列を見ること。
画面だけで止めると、API を直接叩かれます。

## §5 文言

### プレースホルダー

例文を置かないでください。**空欄のときに実際に表示される語**を、薄く出します。

```
坂本 梓   [ 講師            ]  ← 薄字。これが今の表示です
```

「例）講師」より正直です。空欄のままだとどうなるかが、そこに見えています。

### 欄の下（常設・1行）

```
ここで決めた呼び方は、教室の中と、つながっている生徒に見えます。
```

★これがいちばん大事な1行です。他人の見え方を変えているのだと分かる場所に置きます。

### もう1行（権限との分離）

```
呼び方を変えても、できることは変わりません。
```

owner が自分を「講師」にしても権限は落ちない。teacher を「教授」にしても増えない。
★これを書かないと、肩書きで権限を変えようとする人が出ます。

### 保存したあと

```
✕ 「保存しました」
◯ 「坂本 梓さんの表示を「教授」にしました」
```

誰の、何を、どうしたか。他人に触った操作なので、そこまで返します。

### 空欄に戻したとき

```
「坂本 梓さんの表示を、権限の名前（講師）に戻しました」
```

「削除しました」ではありません。**戻した**のです。

### 未設定の表示（フォールバック）

```
owner   → 責任者
admin   → 管理者
teacher → 講師
```

★この語を、列に書き込まないでください。**表示のときだけ当てます。**
書き込むと「明示的に選ばれた値」に化けます。

## §6 RLS と GRANT

前提は §0 の②次第です。ここでは**列単位だった場合**の形を書きます。

```
読み取り   既存の memberships SELECT ポリシーのまま。★新設不要
           （同じ教室の中で見えているものに、1列足るだけ）

書き込み   ★GRANT UPDATE (display_title, display_title_updated_by,
                          display_title_updated_at) ON memberships TO authenticated;
           ポリシーは既存の owner/admin 判定を使う
```

### 確かめてほしいこと

既存の UPDATE ポリシーが **owner/admin だけを通しているか**。
「memberships を更新できる」ポリシーが、本人にも開いていないか。

```
もし本人が自分の行を UPDATE できるなら、
★自分で自分の肩書きを名乗れます。方針（運営側が割り当てる）が崩れます。
```

ここが「前提が崩れる点」の本命です。①の句を読んでから決めてください。

本人に開いている場合、**ポリシーを直さないでください。**
列単位の GRANT で `display_title` を外し、
owner/admin 用の経路を1本の関数（SECURITY DEFINER）にするほうが、既存を壊しません。
どちらにするかは、①が届いてから決めます。

```

               （新しい削除処理は要りません）

02 バックアップ  変更なし

               新しい参照点です

04 データ書き出し ★登録が要ります。
               display_title は「その人について、他人が付けた値」ですが、
               ★その人に関する情報です。本人の書き出しに含めてください

05 外に出る経路  変更なし（アプリの中だけです）

06 起きたことの記録 変更なし（今回は事故ではありません）

07 利用者に示している約束
               ★1行。先生に対して「肩書きは教室の運営側が設定し、

```

★04 と 07 を落とさないでください。この2本が、いつも忘れられます。

### B-3 §5 との関係

**B-3 の一覧は変えなくてよいです。**
あの一覧は「利用者 → 教室」の向きです。肩書きは逆向き（教室 → 利用者）で、
しかも先生の情報であって利用者の情報ではありません。

ただし**先生向けの説明**は要ります（§5の1行と、07の1行）。

## §8 見張り検査

7つ。全部、**別のアカウントで実際にやってください。**（9月3日の作法）

```
① teacher の人が、他人の display_title を書き換えられないこと
② ★本人が、自分の display_title を書き換えられないこと
③ ★別の教室のメンバーの display_title を書き換えられないこと
④ ★同じ UPDATE 文で role を一緒に送ったとき、role が落ちること
   （列単位 GRANT が効いているかの確認。ここが本命です）
⑤ 21字がサーバで拒否されること（画面を通さず API を直接叩く）
⑥ 空文字を送ったとき、★null になること（空文字が入っていないこと）
⑦ 未設定の人が「講師」と表示され、★かつ列が null のままであること
   （既定値が書き込まれていないこと）
```

④と⑦が、この機能の見張りの中心です。

⑤⑥は SQL ではなく、★アプリの経路で試してください。
CHECK 制約が効いていても、保存前の btrim が無ければ ⑥ は落ちます。

## §9 前提が崩れる点（まとめ）

ご質問への直接の答えです。

```
「ポリシーの新設は不要」        ★おそらく正しい
「権限の追加は不要」            ★正しくありません。GRANT が要ります（列単位の場合）
「既存の判定を流用するだけ」    ★①の句を読むまで、確定できません
                                本人が自分の行を UPDATE できるなら、崩れます
```

そして、相談に無かったもの。

```
★入れられない語（§3）      ── 資格の名称と、運営を装う語
★updated_by / updated_at    ── 他人の見え方を他人が変えるので
★空文字を null にすること    ── 既存裁定を守る唯一の方法
★台帳 03 / 04 / 07          ── 登録が要ります
```
