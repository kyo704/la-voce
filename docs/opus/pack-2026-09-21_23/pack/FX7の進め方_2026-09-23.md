# FX7（試しの台帳を本番に合わせる）── ㋐か㋑か

2026-09-23 ／ Opus。Code の問い「㋐ 試し環境への流し直し／㋑ 入れ物ごと作り直し」への答え

## 答え：★㋑（入れ物ごと作り直し）

```yaml
理由:
  - いま試しにある「本番に無いもの」が、㋐では消えない。実測（2026-09-21 twin）:
      ・security definer の関数のうち anon で実行できるものが 本番5 に対し 試し40超
      ・本番に無い関数（can_view_ops など）・古い引数の形の関数（create_org_event の4引数）
      ・org_messages の TRUNCATE・DELETE・REFERENCES の権限
      ・裁定160 の表に付いた TRUNCATE ほか
    → 移行を流し直しても「足りないものを足す」だけで、「余分なもの」は残る
  - 余分なものが残った試しで証明しても、「本番でも同じ」とは言えない（今日までの証明が弱かった原因）
  - ㋑ なら「移行だけで作れること」も同時に確かめられる（移行の抜けがあれば、その場で分かる）

条件（この2つが済んでいれば ㋑ を始めてよい）:
  1 記録の外にあった本番の変更が、すべて移行として記録されていること（S1・S2・裁定160・束2 ほか13本）
  2 試しの利用者を作り直す種（seed）が、1本の SQL か1本のスクリプトになっていること
    ★これまでの証明は「実在の試しの利用者」で行ってきた。作り直すと消えるので、種が無いと証明が止まる
```

## 手順

```yaml
1 種を書く（Code。半日）:
   test_seed.sql（または seed スクリプト）
   - 学校2つ（片方は教室くらいの大きさ）
   - 役職: 学長・事務長・課長・先生・先生（別の門下）・学生3・保護者1
   - 札の組み合わせ: master / post / meibo / sched_all / sched_mine / gyoji / renraku_all / monka_write / monka_read（切った状態も）
   - 名簿・担当・レッスン・連絡・行事を最小限
   ★利用者の作成は Supabase の管理の API で（パスワードは環境変数）。SQL に書かない
2 新しい入れ物を作る（Code）:
   Supabase の新しいプロジェクト（名前 la-voce-test2・東京）。★Free のまま（止まっても困らない）
3 移行を頭から当てる（apply_migration）。エラーが出たら、それが「移行の抜け」→ Opus に返す
4 種を流す → 証明の試験（これまでの S1・S2・束0〜3 の VERIFY）を一度すべて通す
5 twin（ledger_inventory）を Opus が走らせて 0件を確かめる
6 0件になったら、古い試し（la-voce-test）を止める。名前と接続先の差し替えを1か所に
```

## ㋐ を選ぶ場合（もし ㋑ が間に合わないとき）

```yaml
- 余分なものを消す SQL を Opus が書く（関数の削除・権限の revoke・表の削除）。ただし「消し忘れ」は twin でしか見つからない
- 当面の証明には使えるが、「移行だけで作れること」は確かめられない
- 出発の前に ㋑ をやり直す前提で（二度手間になる）
```
