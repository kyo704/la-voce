# 設計 ── 仕事の予定を持つこと

全 273 行 / 末尾は「予定表を作るのではありません。声を使う日を、先に数えるのです。」

作成 2026年9月4日 ／ 「レッスンだけの予定でよいのか」への回答

---

## §0 結論

```
やるべきか      ★はい。しかも、これは追加ではなく★修正です
どこまでやるか  ★カレンダーにはしないでください
何を持つか      予定ではなく、★「声を使う日」だけ
```

いま気づかれたことは、正しいだけでなく、**すでに片側では実装されています。**

---

## §1 いま、非対称になっています

記録の側を見てください。

```
活動係数    休養 0 ／ 自主練 1.0 ／ レッスン 1.2 ／ リハ 1.3 ／ ★本番 1.6
中核5項目   ★offStageVoiceMinutes（練習以外で話した時間）
```

**記録の側は、とっくに仕事を見ています。**
本番に係数がついていて、練習以外で話した時間を数えている。
これは「レッスンを受ける人のアプリ」の作りではありません。

一方、予定の側は。

```
org_events  ★教室の中の予定しかありません
lessons     ★レッスンしかありません
```

**予定の側だけが、教室に縛られています。**

だから、これは新しい機能を足す話ではありません。
**片側だけ遅れているのを、揃える話です。**

そして今日、私はすでに同じ裁定を1つ出しています。

```
「本番日は★個人の登録が正。org_events からは取り込み」
```

ご質問は、その裁定の**一般形**です。答えは同じです。

---

## §2 ただし ── カレンダーと戦うと、負けます

ここが分かれ目です。「予定を柔軟に」を素直に伸ばすと、カレンダーアプリになります。
それは避けてください。理由は3つ。

```
① 誰も、カレンダーを2つ持ちません
   移し替える手間は、★機能の魅力を必ず上回ります

② 「予定を全部入れてください」と言った瞬間、多くの人が脱落します
   いま「毎日の記録が続かない」問題を抱えているのに、
   ★入力をもう1種類増やすことになります

③ カレンダーは競合が強すぎます
   Google も Apple も無料で、既に全員が使っています
```

**カレンダーの代わりにはなりません。カレンダーが答えない問いに答えます。**

```
Google カレンダー   「10:00 リハーサル」と表示できます
このアプリ          ★「そのリハは1.3。今週はふだんの1.4倍になります」
```

これは既存のカレンダーには**原理的に出せません**。声の負荷を知らないからです。
ここだけを取りに行ってください。

## §3 何を持つか ── 「予定」ではなく「声を使う日」

全部の予定は要りません。**負荷になる日だけ**です。

```
本番            1.6
リハーサル      1.3
レッスン（受）  1.2
レッスン（教）  ★係数は要検討。教えるのは話す時間が長い
稽古・合わせ    1.2〜1.3
録音・収録      ★1.4前後。やり直しが効くぶん、回数が積み上がります
オーディション  1.5前後。1回きりの緊張が乗ります
```

★係数の数値は、運営者が決めてください。私は歌っていません。
形だけ用意します。

### もう1種類、足してください

```
★移動（長距離・前泊・時差）
```

声を使いません。**でも回復を削ります。**
係数を 0 にすると、「休養」と同じ扱いになってしまいます。それは違います。

```
声の負荷    0
回復        ★削る（睡眠と、乾燥）
```

**負荷と回復を、別の軸にしてください。** 移動はこの2軸でしか表せません。
これは、いまの1軸の活動係数では持てない情報です。★ここが設計の要ります点です。

飛行機の乾燥は、絶対湿度の話に直結します。中核5項目に `absoluteHumidity` がある以上、
移動を持たないのは、もったいない。

### 持たないもの

```
✕ 会場名（自由記述）
✕ 曲目
✕ 共演者
✕ ギャラ
```

自由記述を作らない、という決まりを守ってください。
名前は任意にして、**無くても全部の機能が動く**ようにします。

「どこで歌うか」は公表前の情報であることがあります。
持たないほうが、こちらの責任も軽くなります。

## §4 入れさせない工夫

いちばん大事なところです。**入力を増やさずに、予定を持つ。**

```
① 本番日を1つ入れる            ← ★今日決めた課金の入口。1件で価値が出る
② 繰り返しで入れる              ← 「毎週火19時レッスン」。1回入れれば以後不要
③ 教室の予定から取り込む        ← org_events から。#34 と同じ形
④ .ics ファイルを読み込む       ← ★後回し。ただし作るならこの形
```

★④について。Google カレンダーとの連携（OAuth）は**作らないでください、当面は。**
新しい外部接続を1本増やすことになります。台帳が増えます。鍵が増えます。

代わりに、**.ics ファイルを、ブラウザの中だけで解析する**形なら、
経路は1本も増えません。サーバに送らず、拾った予定だけを利用者が選んで入れる。
これは後回しでよいですが、やるならこの形です。

★そして、**予定を1つも入れなくても、アプリは全部動くこと。**
予定は「あれば効く」ものです。必須にしないでください。

## §5 何が返るか ── ここが本体です

予定を持つこと自体には価値がありません。**返るものに価値があります。**

```
① 先の見通し
   「来週は、ふだんの1.4倍です」
   ★いまの ACWR は過去しか見ていません。
     予定があれば、★先が見えます。これは大きい

② 次の休みはいつか
   「本番まで12日。休養の日が★1日もありません」
   ★歌い手がいちばん知りたいのは、これだと思います

③ 本番からの逆算
   ★今日決めた本番モード。予定が入っていれば、自動で始まります

④ 積み上がりの見え方
   「今月は本番が3つ。先月は1つでした」
```

②が本命です。予定表は「何があるか」を見せますが、
**「何も無い日がいつか」を見せるものは、ありません。**

歌い手にとって、何も無い日は「空き」ではなく**回復**です。
そこを名前で呼べるのは、このアプリだけです。

## §6 教室との関係

```
正      個人の予定
従      org_events からの★取り込み（自動で入れない。断ったことは先生に見えない）
```

今日の裁定と同じです。**2つの形を作らないでください。**

そして、予定が終わったあと。

```
予定  →  ★「やりましたか」  →  activities[] に入る
```

これも #34（レッスンの取り込み）と同じ形にしてください。
**予定は予定のままでは記録になりません。** 変換の1歩を、必ず利用者に押させます。

キャンセルと延期は必ず起きます。予定を実績として自動で数えると、
本番が無かった日に 1.6 が立ちます。★それは分析を壊します。

## §7 売り物としての意味

ここが、ご質問の本当の答えかもしれません。

```
レッスンだけのアプリ   → 客は★生徒です
仕事の予定も持つアプリ → 客は★働いている歌い手です
```

**払うのは後者です。**

そして今日決めた「本番モードが有料の中核」は、
**本番が有る人＝働いている人**を客に選ぶ、という決定でした。
ご質問は、その決定と同じ向きを向いています。

言い方を1つ提案します。

```
「レッスンの記録アプリ」ではなく
★「声で仕事をする人の、負荷の管理」
```

前者は学習者向けの道具に聞こえます。後者は職業の道具に聞こえます。
中身はほとんど同じで、**値段が変わります。**

---

## §8 やらないこと（歯止め）

```
✕ 通知・リマインダー         催促しない、という決まりを壊します
✕ 他人との予定の共有          経路が一気に増えます
✕ 会場・曲目などの自由記述
✕ Google カレンダーとの双方向同期
✕ 「予定を入れないと使えない」形
```

★とくに1つめです。予定を持つと、通知を付けたくなります。
**付けないでください。** 予定を持つ理由は、思い出させるためではなく、
**先の負荷を数えるため**です。ここを混ぜると、製品の性格が変わります。

## §9 順番

```
いま         本番日の個人登録（★今日決めた分。有料の入口）
そのすぐ後   繰り返しの予定（レッスン・稽古）
その次       ★移動と、回復の軸
その次       「次の休みはいつか」の表示
後回し       .ics の読み込み
やらない     OAuth 連携・通知・共有
```

最初の1つは、もう決まっています。**そこから伸ばすだけです。**
新しい設計を1から起こす必要はありません。
