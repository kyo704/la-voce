## 1. 結論

```yaml
★「本番で利用者が使える状態」に届く見込み:
  ◎ 届く（自信あり）: 安全の直し（台帳）・値段の台帳・レッスン割・ポートフォリオ／ホームページ
  ○ 届きうる（Code の速さ次第）: 公演の本体（作る・香盤表・稽古・当日・出欠）
  △ 危ない: 公演の子ども（保護者・緊急の連絡先）・学校向けの一式（導入期間・請求の実運用）
  ✕ 届かない: 「全部を公開して、全部の安全を証明し終える」
理由は変わっていない: 詰まるのは「書く」ではなく「確かめる」と「承認」。
  台帳は 01〜25 まで揃った（Opus の側の山は越えた）。ここから先は Code の実装と証明の時間で決まる
```

## 5. 出発の日に「動いていない」ものが出たときの備え

```yaml
- 出発前に、機能ごとの切り替え（隠す／出す）を1か所にまとめておく
- 動いていない機能は 切ったまま出発する（利用者には見えない）
- 欧州から直すときの条件: ①見張りの通知が届く ②戻す練習が済んでいる ③時差の確認が済んでいる
  ★この3つが揃っていなければ、機能を足すより「切ったまま」を選ぶ
```

## 6. いちばん危ないところ

```yaml
★1つだけ挙げるなら「公演の子ども」。
  未成年の情報・緊急の連絡先・保護者への見せ方。急ぐと、今日の「門下を開いた記録」と同じ形の事故が起きる
  → 台帳（13・18・22）は守りを入れて作った。画面をつなぐときに、記録が残ることを先に確かめる
★次に危ないのは「値段」。
  お金は、間違えると取り返しがつかない（二重に取る・取れない・返しすぎる）。
  → my_entitlements（使えるかの判定を1か所）と、返金の上限の検査を必ず通す
```
