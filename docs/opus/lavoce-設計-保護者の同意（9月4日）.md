# 設計 ── 18歳未満と先生の連携／保護者の同意

全 485 行 / 末尾は「入るのを厳しくするのではなく、出るのを易しくすることで守る。」

作成 2026年9月4日 ／ Opus ／ ★弁護士確認を要する箇所を明示します

## §0 5つの論点より先に、決めるべきことが3つあります

★いただいた論点(1)〜(5)は、どれも「同意をどう取るか」に寄っています。
　**本当の問題は、そこではありません。**

### 判断1 ★包括の同意にしない

```
（誤）「先生との連携を許可します」          ← 誰とでも、という意味になります
（正）★「この先生（◯◯）との連携を許可します」
```

★理由

```
教室を移れば、先生は変わります
　　→ 包括で同意すると、★保護者が知らない大人と、子どもがつながります
　　→ ★1回の同意が、将来の全部に効いてしまいます
```

★**先生1人ごとに、同意を取ってください。**

### 判断2 ★完璧な本人確認は、個人事業では不可能です

```
メールを送る       → ★子どもが親のメールを使えます
SMSを送る          → ★同じ
本人確認書類       → ★個人事業で預かるべきではありません
```

★**「確認の強さ」で守るのは、諦めてください。**

```
代わりに守るもの
　　1  ★記録を残す（誰が、いつ、どの方法で同意したか）
　　2  ★取り消しを、極端に簡単にする
　　3  ★見えるようにする（§7）
```

★**「入るのを厳しくする」のではなく「出るのを易しくする」**で守ります。
　これが、個人事業で取れる唯一の現実的な形です。

### 判断3 ★保護者に、子どもの健康記録を見せない

★これは、いちばん議論になるところです。**先に立場を書きます。**

```
保護者が同意したのは、★「連携」です
　　→ ★「記録を見る権利」ではありません
```

```
保護者に見せるもの   ★つながりの事実（いつ、誰と、つながっているか）
保護者に見せないもの ★体調の記録・既往症・服薬・周期の設定・分析の結果
```

★理由（非対称ハーム原則）

```
見せない害   保護者が、子どもの体調を把握できない
　　　　　　 → ★保護者は、子どもに直接聞けます

見せる害     ★15〜17歳の子が、正直に記録しなくなります
　　　　　　 → 月経周期・体重・気分・服薬を、親に見られると分かれば
　　　　　　 → ★記録をやめるか、嘘を書きます
　　　　　　 → ★このアプリの目的そのものが、壊れます
```

★**見せないほうの害は、他の手段で埋められます。見せるほうの害は、埋められません。**

★ただし例外があります。

```
親権者は法定代理人なので、★法に基づく開示請求はできます
　　→ ★それは「請求」として、個別に処理します
　　→ ★画面に常時出す、という形にはしません
```

★**この判断は、弁護士に確認してください（§10）。**

## §1 ★前提の確認 ── 年齢を、どう知っていますか

```
確認1  生年月日（または年齢）を、いま取得していますか
確認2  profiles.is_under_18 は、★何をもとに立っていますか
確認3  規約第2条は「生年月日等の必要事項を届け出て」と書いています
　　　 ★実装は、それに追いついていますか
```

★**年齢が分からなければ、この機能は始まりません。**

★そして、年齢の取得そのものが、15歳未満の問題を引き起こします。

```
15歳未満から生年月日を取ること自体が、★個人情報の取得です
　　→ ★保護者の同意が要ります
　　→ ★鶏と卵になります
```

★解き方は §2 にあります。

---

## §2 二段の線 ── 15歳と18歳

```
15歳未満   ★登録そのものに、保護者の同意が要ります（個人情報の取得）
15〜17歳   ★登録は本人。★連携のときに、保護者の同意が要ります
18歳以上   本人だけで完結
```

★§1の「鶏と卵」の解き方

```
登録の入口で、★年齢の帯だけを聞きます（生年月日ではなく）

　　「15歳未満です」   → ★保護者の同意の画面へ（登録の前）
　　「15〜17歳です」   → 登録できます。★連携のときに同意が必要
　　「18歳以上です」   → 登録できます
```

★帯だけなら、個人情報として軽くなります。
　**生年月日は、必要になった時点で聞きます。**

★★ただし、**15歳未満をいま受け入れるかは、別の判断です。**

```
（推奨）★当面、15歳未満は受け入れない
　　　　→ 15〜17歳の連携だけを、先に解禁する
　　　　→ ★音楽教室・養成所の生徒の多くは、中学生以上です
```

★理由

```
15歳未満を受け入れると、★登録の入口から保護者の同意が要ります
　　→ 作るものが2倍になります
　　→ ★営業に必要なのは、15〜17歳のほうです
```

★**規約第2条は「別途お知らせします」のままにできます。**
　「15歳未満はご利用いただけません」と書くのは、
　★15歳未満を受け入れる仕組みを作るときに、書き換えます。

## §3 論点(1) ── 保護者の同意の取り方

★**教室経由と、個人の場合で分けてください。**

### 3.1 教室・学校経由（★こちらを先に作る）

```
教室は、★保護者を知っています（入会時に連絡先を取っています）
　　→ ★教室が「保護者の同意を得た」と記録します
　　→ 責任は、★教室にあります
```

```
流れ
　1  生徒（15〜17歳）が、教室の先生と連携しようとする
　2  ★止まる。「保護者の方の確認が必要です」
　3  教室の運営者（owner/admin）の画面に、確認の依頼が出る
　4  運営者が、保護者に確認する（★アプリの外・電話や書面）
　5  運営者が「保護者の同意を確認しました」を記録する
　　　★保護者の氏名／確認した方法／確認した日
　6  連携が成立する
```

★**アプリは、保護者と直接やり取りしません。**教室が間に入ります。

★これで

```
・本人確認は、★教室が対面で行っています（アプリより確実です）
・責任の所在が、はっきりします
・★契約書に、この条項を入れられます（教室の義務として）
```

★★契約書に足す条項

```
　教室は、18歳未満の生徒について、
　保護者の同意を得たうえで、本サービス上に記録するものとします。
```

### 3.2 個人の先生と生徒（★あとで作る）

```
教室に属さない先生と、15〜17歳の生徒
　　→ ★間に入る人が、いません
```

```
流れ（推奨）
　1  生徒が、保護者のメールアドレスを入力する
　2  ★1回限りのトークン付きリンクを送る
　3  保護者が開き、次を入力して同意する
　　　・保護者の氏名
　　　・生徒との続柄
　　　・「私は◯◯の保護者です」のチェック
　4  ★同意のメールに、★撤回用のリンクを必ず含める（永続）
　5  連携が成立する
```

★**弱い確認です。それを承知で使います。**
　§0-判断2のとおり、**取り消しの易しさで補います。**

★推奨：**3.2 は、教室プランの営業には不要です。あとで作ってください。**

## §4 論点(2) ── データの形

★consent_records には入れないでください。

```
consent_records   ★本人の同意（owner_id ＝ 本人）
guardian_consents ★★保護者の同意（主体が違います）
```

★**主体が違うものを、同じ表に入れないでください。**
　入れると、「誰が同意したか」を毎回条件で分けることになり、必ず取り違えます。

```sql
guardian_consents
　　id             uuid
　　student_id     uuid   ★生徒（15〜17歳）
　　teacher_id     uuid   ★★この先生との連携に対する同意（包括にしない）
　　action         text   'granted' | 'withdrawn'
　　method         text   'org'（教室が確認）| 'email'（保護者が直接）
　　org_id         uuid   ★method='org' のとき、確認した教室
　　confirmed_by   uuid   ★method='org' のとき、記録した運営者
　　guardian_name  text   ★保護者の氏名（教室が聞き取った／保護者が入力した）
　　relation       text   続柄
　　occurred_at    timestamptz
　　created_at     timestamptz
```

★**追記のみ。**UPDATE と DELETE は、ポリシーを作らず、権限も落とす。

★権限

```
SELECT  ★生徒本人 ／ ★その教室の owner・admin
　　　　★先生は、この表を読めません
INSERT  ★教室の owner・admin（method='org'）
　　　　★トークン経由のサーバー関数（method='email'）
UPDATE  ★無し
DELETE  ★無し
```

★**先生に読ませない理由**

```
先生が「保護者の同意があるか」を見られると
　　→ ★保護者に働きかける経路ができます
　　→ 連携は、★先生が求めるものではなく、生徒と保護者が決めるものです
```

★7つの台帳に登録してください。

## §5 論点(3) ── 撤回と、既存の連携

```
保護者が撤回したら
　　→ ★その先生との連携を、★止めます（削除ではありません）
　　→ ★teacher_student_links の行は残し、無効の状態にします
　　→ ★過去のレッスンの記録は、消しません
```

★理由：**消すと、その子が受けたレッスンの記録まで消えます。**

★先生への表示

```
（×）「保護者の同意が取り消されました」
（○）★「連携が終了しました」
```

★**理由を、先生に見せないでください。**
　撤回の理由は、生徒と保護者のものです。
　理由が見えると、**先生から生徒に問い合わせが行きます。**

★生徒への表示

```
★「保護者の方の確認が取り消されたため、この先生との連携を止めました」
　　→ ★生徒には、理由を伝えてください。自分のことだからです
```

★撤回の経路（3つとも用意してください）

```
1  ★同意のメールに含まれる、撤回用のリンク（永続）
2  ★教室の運営者から（method='org' の場合）
3  ★お問い合わせ（手作業）
```

★**1がいちばん大事です。**同意した本人（保護者）が、
　いつでも自分で切れることが、§0-判断2 の要です。

## §6 論点(5) ── 書き込みパスの分離

```
★保護者に、アカウントを持たせないでください
```

★理由

```
アカウントを作ると
　　→ 権限の管理が1つ増えます
　　→ ★「保護者は何を見られるのか」が、際限なく広がります
　　→ ログイン・パスワード・退会・削除が、全部ついてきます
```

★保護者ができることは、**2つだけ**です。

```
1  同意する
2  撤回する
```

★どちらも、**1回限りのトークン付きリンク**で行います。

```
保護者は、生徒のデータに★一切書き込めません
保護者は、生徒のデータを★一切読めません（§7の一覧を除く）
```

★これで、非対称ハーム原則に沿います。
　**保護者が持つのは「止める力」だけで、「見る力」も「変える力」も持ちません。**

## §7 ★私からの追加論点 ── 保護者に、何を見せるか

★論点に無かったので、足します。**これが抜けると、あとで必ず問題になります。**

```
保護者が同意したあと、★何も見えない状態にしないでください
```

★見せるもの（撤回用リンクの先のページ）

```
　◯◯さんは、いま次の先生とつながっています

　　・△△先生（□□教室）　2026年9月10日から
　　・（連携が終わったもの）××先生　2026年5月〜7月

　　　［この連携を終了する］
```

★見せないもの

```
★体調の記録 ／ 既往症 ／ 服薬 ／ 周期の設定 ／ 分析の結果
★レッスンの内容 ／ 先生のメモ
```

★**「誰とつながっているか」だけです。**それ以上は見せません。

★このページには、ログインを求めないでください（§6）。
　★トークンで開きます。**トークンは、その保護者・その生徒に限定します。**

## §8 画面の文言

★いまの文言は「保護者の方の確認の仕組みを準備しています」です。
　**これも、実物ができるまで変えないでください。**（撤回ボタンと同じです）

★できたあとの文言（草案）

```
【生徒の画面】
　先生とつながるには、保護者の方の確認が必要です。
　★通っている教室の先生に、お伝えください。
　（教室に属していない場合は、保護者の方のメールアドレスを入力してください）

【教室の運営者の画面】
　◯◯さん（15〜17歳）が、△△先生とつながろうとしています。
　保護者の方に確認して、下の欄にご記入ください。

　　保護者のお名前　［　　　　　］
　　続柄　　　　　　［　　　　　］
　　確認した方法　　［電話／書面／対面］

　　　［確認しました］

　★この記録は、あとから変更できません。

【保護者へのメール（method='email' の場合）】
　◯◯さんが、△△先生と Woolsong でつながろうとしています。

　つながると、△△先生には次のものが見えます。
　　・◯◯さんのお名前と職種
　　・レッスンの予定と、レッスンをやったかどうか

　★体調の記録は、先生からは見えません。
　　（Woolsong には、先生が生徒の体調の記録を見る機能がありません）

　　　［同意する］

　※ 同意されたあとも、いつでも取り消せます。
　　 このメールの下のリンクから、いつでも確認・取り消しができます。
```

★最後の1行が、いちばん大事です。**メールを保存してもらうためです。**

## §10 ★弁護士に聞くこと（有料化の相談と、まとめて1回）

```
1  ★保護者に、子どもの健康記録を見せない設計は、成り立ちますか
　　　（親権者の法定代理人としての立場との関係）

2  ★教室が「保護者の同意を確認した」と記録する形で、
　　個人情報保護法上の「法定代理人の同意」を満たしますか

3  ★メールのリンクによる同意で、民法5条の同意を満たしますか
　　　（未成年者の契約の取消しとの関係）

4  15歳未満を受け入れない、という設計に問題はありますか

5  ★保護者の氏名・続柄を記録することは、必要かつ十分ですか
```

★1がいちばん大事です。**ここが否定されたら、設計が変わります。**
