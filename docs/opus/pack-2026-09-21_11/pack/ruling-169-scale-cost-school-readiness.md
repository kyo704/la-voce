## P5 規模と費用

```yaml
いまの大きさ: 台帳 18MB（Free の上限 500MB の 4%）。利用者 53・記録 118。大きい表は events 864kB・entries 320kB
  → 容量・人数は当分の間 心配ない。問題は「バックアップが無い」「止まる」の2つ（★1・★2）
Supabase（2026年の公開の料金）:
  Free: 台帳 500MB・転送 5GB・月の利用者 5万・2プロジェクト。1週間 使われないと止まる。バックアップ・SLA なし
  Pro: 月25ドル〜。止まらない。毎日のバックアップ。使いすぎの上限（spend cap）が既定で入る
  → 本番（xxjtplvpcneksrofkjmf）と試し（la-voce-test）は同じ組織。Pro は組織ごと。試しは Free のままにできるか Code が確かめる（止まっても困らない）
Vercel: Hobby は個人・非商用だけ。支払いを受ける・商品を売る案内をするのは商用 → Pro か Enterprise
500人の名簿: 既知（全部描き直しの作り・総合評価 §2）。学校の iPad で実機（フェーズ6）
同時の書き込み（一意の制約の点検）:
  守られている: entries（本人×日）・memberships・enrollments（学校×学生・学籍番号）・my_periods・my_timetable・org_event_participants・applications・
    character_inventory・item_acquisitions・portfolios（slug）・purchases（session）・user_notices・evaluation_judge_done
  守られていない: assignments（有効な担当）★5・org_billing ★6・Stripe の通知 ★7
戻し方（Pro にしたあと）: 戻すのは「日単位」。戻すと、その日以降の記録が消える → 戻す前に、残すべき表（*_log・請求）を書き出してから
  手順書（誰が・どこから・何分で）を docs/ に（フェーズ5）
```

## P6 学校に売るとき

```yaml
確認票でよく問われる項目 × いまの実装:
  データの置き場: 東京（Supabase ap-northeast-1）。契約の相手はシンガポール（ポリシー7項）→ 答えられる
  通信・保存の暗号化: Supabase の既定（通信の暗号化・保存時の暗号化）→ 各社の公開の資料で文言を確かめてから書く（次の回）
  アクセスの制御: 全部の表に RLS（無効は _a13_policy_backup だけ → 裁定163 で消す）。役職の「できること」で絞る → 答えられる
  管理者の多要素の認証: recovery_codes の表がある → Code が、学校の管理者（事務長など）に多要素を求められるかを確かめる
  操作の記録と保存の期間: ★8。Free の約1日では足りない
  バックアップ・復旧: ★1。いまは「無い」と答えることになる
  障害時の連絡: 裁定168 ★5（見張りの通知の道）
  委託先の管理: ポリシー7項と大学向け_法的整理書 §3 の再委託先の一覧
  退職者・卒業生のアカウント: 退会の流れ（裁定168 ★1〜3）と、名簿から外すと学校の画面から消えること（enrollments の状態）
安全管理措置の38の空欄: 台帳から埋められる所（アクセス制御・記録・バックアップ・暗号化・置き場）の下書きは、★1・★8 を決めてから（いまは「無い」を書くことになる）
年度の切り替え（4月）:
  enrollments に学年（grade_label）・状態がある。進級・卒業を一度に直す関数・画面は台帳に無い → 名簿の読み込み（meibo）でやる前提か、Code が確かめる
  卒業で消さない（状態を変えるだけ）。学生の記録は学校と結びついていない（entries に学校への外部キーなし）→ 卒業後も本人に残る（裁定138 S2）★台帳で確認済み
3者の総当たり: 画面は perm-matrix（5-2）、台帳は束5（試しの作り直し）の後に実在の試しの利用者で
領収書（D14）: 学校は Stripe の請求書・領収書（登録番号つき）。個人は Stripe の領収書のメール。台帳には payment_records（7年）
```
