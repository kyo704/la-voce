# 復旧訓練 ── 10月16日の凍結のあとに1回（所要 2〜3時間）

2026-09-23 ／ Opus。「バックアップがある」ではなく「戻せる」を確かめるための訓練

## 0. なぜやるか

```yaml
- 取れているだけのバックアップは、戻せるまで「無い」のと同じ
- 欧州に居る間は、坂本さんが1人で判断して戻すことになる。初めてやるのが本番では遅い
- ★戻すときにいちばん困るのは「どこまで戻すか」。訓練で先に決めておく
```

## 1. 想定する3つの場面

```yaml
S1_移行を1本まちがえた（いちばん起きやすい）:
  例: 列を消す移行を当ててしまった／制約で全部の書き込みが止まった
  戻し方: ★台帳ごと戻さない。逆の移行を1本当てる（列を戻す・制約を外す）
  訓練: 試しの環境で、わざと列を1つ消して、逆の移行で戻す
  目標: 10分以内
S2_データを消しすぎた:
  例: 消す移行の条件を間違えて、本物の行まで消えた
  戻し方: その日の書き出しから、★その表だけを戻す（全体を戻さない）
  訓練: 試しの環境で1つの表を空にし、書き出しからその表だけ戻す
  目標: 30分以内
  ★確かめる: 戻したあと、外部キーで矛盾が出ないか（子の行が親を失っていないか）
S3_台帳が丸ごと壊れた・入れなくなった:
  例: プロジェクトが止まった／誤って消した
  戻し方: 新しいプロジェクトを作り、移行を頭から当て、書き出しからデータを入れる
  訓練: ★ここまではやらない（2〜3時間かかる）。手順書だけ作り、S1・S2 で部分を確かめる
  目標（手順書に書く）: 半日
```

## 2. 訓練の手順（Code が実施・坂本さんが1回は自分で操作）

```yaml
準備:
  - 試しの環境（FX7 のあとの新しいもの）を使う。★本番では絶対にやらない
  - 当日の書き出しを1つ用意（本番の書き出しの複製でよい。★中身は試しに入れない・形だけ使う）
S1 の訓練:
  1 試しに「列を1つ消す」移行を当てる（わざと）
  2 画面が壊れることを見る（どんなエラーが出るかを目で見ておく）
  3 逆の移行（列を戻す）を書いて当てる
  4 かかった時間・詰まった所を記録
S2 の訓練:
  1 試しの1つの表を空にする
  2 書き出しから その表だけを戻す（pg_restore の表指定、または SQL で流し込む）
  3 外部キーの矛盾が無いかを数える（親を失った子の行が0件）
  4 かかった時間を記録
共通:
  - ★戻す前に、いまの状態の書き出しを1つ取る（戻しに失敗したときのため）
  - 戻したあと、ledger_inventory audit を走らせて、権限が元どおりかを見る
```

## 3. 手順書に必ず書くこと（docs/ に残す）

```yaml
- 書き出しの置き場所と、開け方（暗号を解く手順）
- 戻すときに使うコマンド（そのまま貼れる形で）
- ★「どこまで戻すか」の決め方:
    1本の移行の間違い → 逆の移行（データは戻さない）
    1つの表のデータ   → その表だけ
    丸ごと            → 新しい入れ物＋移行＋書き出し
- 戻したあとに必ず確かめること: 退会が通る／学校が閉じられる／記録が消えていない／値段が MATCH
- 欧州から行うときの注意: 接続が遅い。長い処理を画面から実行せず、移行として当てる
- 誰に伝えるか: 利用者への告知の文（止まっていた時間・影響・復旧）
```

## 4. 訓練の合格

```yaml
○ S1 を10分以内で戻せた
○ S2 を30分以内で戻せた。戻したあと矛盾0件
○ 手順書が、見ながら操作できる形になっている（坂本さんが1人で読んで分かる）
○ 訓練でかかった実際の時間が書いてある（「30分」ではなく「23分かかった」）
×が出たら: 出発前にもう1回。2回とも駄目なら ★Supabase を Pro にして、毎日のバックアップと復元の仕組みを使う
```
