# RULING 184 — 書き換える関数の「返し方」を そろえる

```yaml
ruling: 184
date: 2026-09-23
version: design-v36
from: Opus が本番の関数81本を 洗って（2026-09-23）
related: sql/32 の事故（★表で返したため、画面が 常に失敗と読んだ）／sql/66（同じ型）
```

## 1. 何が起きているか

```yaml
本番の「書き換える関数」（security definer・volatile）は ★81本。
返し方が ★15通りに 散らばっています:
  boolean 4本（set_member_post ほか）／void 8本／integer 15本／uuid 4本／text 4本／jsonb 4本
  ★TABLE(ok boolean) 2本／★TABLE(ok boolean, reason text) 2本／そのほか TABLE が 12通り
★これが 事故のもと:
  2026-09-11 sql/32 ── 私が ★表の形で返し、画面は done!==true で ★常に失敗と読んだ
  2026-09-23 sql/66 ── ★同じ名前の関数が2つ。画面が引数を省くと ★古い方に当たる
  ★どちらも エラーにならず、★静かに 間違った結果になります
```

## 2. 決めたこと（★これから書くものに 当てる）

```yaml
★新しく書く「書き換える関数」は、次の3つのどれかで返す:
  ① ★void      ── 成否だけで 呼ぶ側が 何も使わない（失敗は raise exception で 伝える）
  ② ★integer   ── 件数を返す（掃除・一括の処理）
  ③ ★uuid      ── 作ったものの id を返す
★TABLE(ok boolean) の形は 使わない
  理由: 呼ぶ側が [{ok:true}] と true を ★取り違えます（sql/32 がまさにこれ）
  ★失敗は「返り値」ではなく ★raise exception で 伝える（理由は 文言に入れる）
★同じ名前の関数を 2つ 置かない（引数の数だけ違う形は ★作らない）
  ★引数を足したいときは、★古いほうを 落としてから 1本にする（sql/66 のように）
★引数には ★必ず既定（default）を置く。無いと「関数が 見つかりません」になります
```

## 3. いま本番にあるもの（★直さない）

```yaml
★いま動いているものは 直しません。★画面が それに合わせて 書かれているためです
  （返し方を変えると、画面が 静かに 壊れます。10月19日の 26日前に やることでは ありません）
★例外: sql/66 の search_works は ★2つあることが 事故のもとなので 1本にします
★2027年の 大きな手入れのときに、★上の3つに 寄せます（そのときは 画面と 一緒に）
```

```yaml

  G7 ★引数に 既定が無い 関数 → 注意（NG にはしない。要る場合もあるため）
★当面は この裁定を 読んで 守ります（道具は 次の手入れで）
```
