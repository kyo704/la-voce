# RULING 160 — 役職の「できること」を変えた履歴を残す（org_posts の perms）

```yaml
ruling: 160
date: 2026-09-21
version: design-v20
from: Code（裁定159 STEP_2 の調べで、monka_read が過去に一時でも役職に付いていたかを確かめられなかった）
same_shape_as: 裁定159（約束・必要はあるのに、記録する仕組みが無い）
related: 仕様シート③「役職を 変えた記録：消せない。誰が・いつ・誰を」（人に役職を渡した記録）
```

```yaml
DECISION: 作る。トリガーで（画面や RPC からの呼び出しに任せない）
  reason:
    - 役職の「できること」を1つ入れると、その役職の人全員の権限が変わる。人に役職を渡すより影響が大きい
    - 門下を読む（monka_read）は「普段は切ってある」前提。入れた・切ったの記録が無いと、その前提を確かめられない
    - 呼び出す側に任せると、裁定159 と同じく「呼ばれなければ残らない」になる

WHAT:
  表: org_post_perm_log（*_log の決まり：update・delete のポリシーを作らない）
  引き金: org_posts の insert・update（perms か名前が変わったときだけ）・delete の後に1行
  列: いつ／誰が（auth.uid()。台帳の処理なら null と「仕組み」）／org_id／post_id（連鎖削除なし）／役職名（その時点の文字列）／変える前の perms／変えた後の perms／増えたもの・減ったもの（配列）／操作（作った・変えた・消した）
  関数: security definer・search_path 固定・anon から実行できない
  見られる人: その学校で post か master を持つ人（select のみ）。利用者が直接 insert できるポリシーは作らない
  画面: 見本の「役職の中身」に「変えた記録」（誰が・いつ・何を入れた／切った）。★門下を読む（monka_read）を入れた・切ったは強調しない ── 並べて出すだけ（見張りの画面にしない）

PAST（引き金を置く前の分）:
  - Supabase のログが残っている範囲で、org_posts の更新の跡を探す（STEP_2 と同じ調べに足す）
  - 見つからなくても「履歴の無い期間：〜（引き金を置いた日）」を修正の記録に1行。STEP_2 の結論は「判別できない範囲がある」と正直に書く

VERIFY:
  - 役職の「できること」を1つ入れる・切る・役職の名前だけ変える → それぞれ1行（名前だけの変更は perms の差が空）
  - 役職を消す → 1行（その時点の perms が残る）
  - log の update・delete が拒否される
  - post も master も無い人は log を読めない
  - 試しは実在の試しの利用者で（なりすましは使わない）。報告は tools/権限変更の型.md の形で、decision_needed_check.py を通してから

ALSO（約束の台帳）:
  仕様シート③の「役職を 変えた記録（誰が・いつ・誰を）」が、実装で本当に書かれているかを、試験で確かめる（裁定159 と同じ型の穴がないか）
```
