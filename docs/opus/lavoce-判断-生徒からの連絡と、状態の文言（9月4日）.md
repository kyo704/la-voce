# 判断 ── 生徒からの連絡と、状態の文言

全 219 行 / 末尾は「アプリの中だけの出来事は伝えない。外でも起きることは伝えてよい。」

作成 2026年9月4日 ／ 案Bの詳細設計への回答

---

## §0 結論

```
生徒の連絡  ★乗せてよいです。ただし★宛先を2つに分けます
文言        ★「対応済み」を使わないでください。理由は §5
```

---

## §1 先生の連絡と、生徒の連絡は、性質が違います

```
先生 → 責任者   ★予定を「変えてほしい」    ← 処理を求める依頼
生徒 → 先生     ★予定に「行けない／遅れる」← 事実の通知
```

★**生徒の連絡は、処理を求めていません。伝わればいいのです。**
　だから、先生の連絡と同じ形にしなくて構いません。

---

## §2 懸念(2)への答え ★新しい原則を1つ立てます

```
#34   「生徒が取り込みを断ったこと」は、先生に見せない
今回  「生徒が休むこと」は、★先生に伝えてよい
```

★矛盾しません。**区別する線は、これです。**

```
★アプリの中だけの出来事      → 先生に伝えない
★アプリの外でも起きる出来事  → 先生に伝えてよい
```

```
取り込みを断った  ★アプリの中だけの出来事
　　　　　　　　  → 先生が知る必要はありません
　　　　　　　　  → 知れば、生徒が断れなくなります

休む・遅れる      ★現実に起きること
　　　　　　　　  → ★先生は、どのみち知ります
　　　　　　　　  → アプリが増やす害は、ゼロです
```

★**この原則を、規則に足してください。**

---

## §3 懸念(3)への答え ── 宛先を2つに分けます

```
生徒 → ★担当の先生     欠席します ／ 遅れます        ★2種のみ
生徒 → ★責任者         相談したいことがあります      ★1種のみ
```

### 3.1 欠席・遅刻が「担当の先生」宛てである理由

```
「今日行けません」は、★その先生に届かないと意味がありません
　　→ 責任者を経由させると、遅れます
　　→ ★遅刻の連絡が、遅れて届いたら、意味がありません
```

★先生間の連絡を責任者経由にしたのは、
　**先生同士の会話が育つと、生徒の体調の話になるから**でした。
　生徒→先生は、**もともとレッスンの当事者どうし**です。同じ危険はありません。

### 3.2 ★「相談したいことがあります」を、先生に開かない理由

```
（危険）未成年の生徒が、大人の先生に「相談したい」を直接送れる経路
```

★中身を書く場所は無いので、先生は「何だろう」となります。
　**そして結局、LINE で聞くことになります。**
　★アプリが、1対1の相談のきっかけだけを作って、中身は外に流れる。
　**いちばん悪い形です。**

★だから、生徒の「相談したい」は**責任者（教室）宛て**にしてください。
　教室が、生徒に直接聞きます。

★これで

```
・大人と子どもの1対1の相談経路を、★作らずに済みます
・教室が、生徒の困りごとを把握できます（教室として、そうあるべきです）
```

### 3.3 責任者は、生徒→先生の連絡を見られます

```
SELECT  ★送った生徒本人 ＋ ★宛先の先生 ＋ ★その教室の owner/admin
```

★理由

```
・教室の運営として、欠席の把握は必要です
・★先生が見落としたときに、気づけます
```

★**見えるだけです。責任者は介入しません。**

## §4 懸念(1)への答え ── 追加の同意は要りません

```
欠席の連絡は、★連携が成立している前提です
　　→ 連携には、既に保護者の同意が要ります（設計中）
　　→ ★連携の範囲の中の出来事です
```

★ただし、**書き足すものが1つあります。**

```
consent-scope（A-2 と規約 第5条の正本）に、1行足してください

　　先生から見えるもの
　　　・お名前（表示名）と職種
　　　・レッスンの予定と、レッスンをやったかどうか
　　　・★あなたが送った連絡（欠席・遅れます）
```

★**「見えるものは、実装より多めに書く」**── 9月4日の規則です。

## §5 「対応済み」を、使わないでください

```
（現状案）「対応済みになりました」
（運営者）「対応済みです」
（★私の答え）どちらも使わないでください
```

### 5.1 理由 ── 「対応」は、何をしたか言っていません

```
責任者がしたこと  ★見て、閉じた
「対応済み」が言っていること  ★何かをした
```

```
実際に予定を変えたかどうかは、★予定を見れば分かります
　　→ 状態のラベルが、それを保証してはいけません
　　→ ★「対応した」と書くと、していないときに嘘になります
　　→ ★断言の禁止に触れます
```

★そして「対応済み」は、**事務の言葉**です。この製品の文体ではありません。

### 5.2 推奨

```
送ったあと      ★「伝えました」        ← 現状のまま。良い文言です
責任者が閉じた  ★「確認されました」
```

★「確認されました」なら、**責任者がしたこと（見て、閉じた）と、一致します。**

### 5.3 ★「〜です」と「〜ました」の使い分け

★運営者の感覚（「〜です」のほうが自然）は、**半分正しいです。**

```
★状態のラベル（画面に常時出るもの）      → 「〜です」
★出来事の知らせ（1回きりの変化）          → 「〜ました」
```

```
（例）
　一覧の中のラベル      「確認済み」ではなく ★「確認されました」
　　　　　　　　　　　  ※ここは出来事の記録なので「〜ました」で正しい

　プロフィールの状態    ★「連携しています」（〜です系）
　トーストの通知        ★「伝えました」（〜ました系）
```

★今回の「伝えました／確認されました」は、**どちらも出来事の記録**です。
　**「〜ました」で揃えてください。**

★★そして、いちばん大事なこと

```
★どちらの言い方でも、no-nagging には触れません
　　（催促していないので）

★触れるのは「対応済み」という語です
　　→ ★していないことを、したと言ってしまうため
```

## §6 設計への賛意（記録として）

★いただいた設計は、裁定の制約をすべて満たしています。

```
・自由記述の列が★存在しない構造        ← 構造で塞ぐ。正しい
・他の先生からは見えない                ← 「直接つながせない」の実装形
・status は open→closed の★一方向のみ   ← 上書きを最小に
・DELETE なし                           ← 追記のみ
・バッジ・件数表示を出さない            ← 催促の禁止
・通知メールを作らない                  ← ★外に出る経路を増やさない
```

★最後の1つが特に良いです。**機能を足しながら、経路を増やさなかった。**

アプリの中だけの出来事は伝えない。外でも起きることは伝えてよい。
