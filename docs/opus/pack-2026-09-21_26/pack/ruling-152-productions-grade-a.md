## 1. A_CONDITIONS（採用）

```yaml
S1: 稽古の変更が、数分でカレンダーに届く（知らせは送らない。鳴るのはカレンダー）
S2: 作品を選ぶと香盤表の下書きが出て、10分で公演が立つ
S3: 本番当日の進行表・集合・楽屋まで、同じ道具で回る
S4: 学生の授業・レッスン・稽古が、1つのカレンダーでぶつからない
判断: 4文とも採る。機能の数でなく、この4文で測る
```

## 2. DECISIONS（Fable の5問への回答）

```yaml
Q1_R2の作品雛形: 採る
  scope: 初期20作品（フィガロ・魔笛・ボエーム・椿姫・カルメン・レクイエム類 など）
  who: 坂本さん＋Fableが 場面×役の表を用意。★実装を待たず、いま作り始めてよい
  reason: 場面・役の一覧は事実（誰が何幕に出るか）であり、著作権の対象ではない。台本のセリフや楽譜と違う
  裁定144との違い: 144は「公演の使い回し」禁止（同じ公演を延長して別公演に流用しない）。雛形は「作品の構造」で、誰の公演でもない。矛盾しない

Q2_R1のICSの数分化: 採る。教室機能のICSと同じ工事に入れる
  方向: 「更新の合図」＋短いキャッシュ。ICS取得側の間隔そのものは変えられないので、拾われた瞬間の値が最短で正しいものになる形にする
  技術の設計（TTL秒数など）: Codeが実装のときに決める。ここでは方向だけ決める
  アプリ内の「変わったもの」一覧: 採る（裁定87と両立。開いたときに見える。数は出さない）

Q3_R4を学校向けAと同じ工事に: 採る
  reason: 授業（裁定139の自動×）・レッスン・稽古を同じ衝突検出にかけるのは、どちらのA条件にも要る同じ仕組み。別に作ると「同じ決めが2か所」になる

Q4_R6の試用先: 音楽院のオペラ公演（イタリア滞在中に関係が作れる場）を第一候補とする
  reason: P1（2027-07）が動いてから測る実績。2026年10月11日の坂本さんご自身の公演は、実装が無いので測れない（裁定141の「観察」の対象のまま）
  決定は保留にしない: 候補は決めるが、確定は坂本さんが2027年に入ってから

Q5_公演をあらゆる形に広げる件（引き継ぎ§6・裁定148）: 一部、裁定148 を訂正する
```

## 3. 裁定148 の訂正（★ここが今回の実質）

```yaml
問題: 裁定141 Q5「最初はオペラと合唱」と、裁定148 の時期表「オペラ・オーケストラ・合唱・ガラを2027-07」が食い違っていた
     Fable の今回の提案は、141 Q5 に近い、より絞った案
決定: 141 Q5 を採る。148 の時期表を訂正する

訂正後の 出す時期:
  2027-07（P1・第1群）: オペラ・ミュージカル・演劇 ／ 合唱
  2027-10（P2・第2群）: オーケストラ・吹奏楽 ／ ガラ・発表会・フェス ／ 室内楽・リサイタル ／ バンド・ライブ ／ ダンス ／ そのほか
    ★オーケストラと ガラは、148 では 第1群だったが、ここで 第2群へ 移す

reason:
  - R2（作品の雛形）・R1（ICSの数分化）を まず 2つの種類で 仕上げる方が、4種類に 同時に 広げるより 早く「A」に届く
  - オーケストラの 降り番・トラ、ガラの 出番順・当日の進行は、それぞれ もう1段 複雑。合唱の あとに 回すほうが 安全
  - 音楽大学・市民オペラでの 最初の 実績（R6）は オペラで 取る。合唱は 同じ 仕組みで すぐ 出せるので 一緒に 出す

見本（design-v13）は 変えない:
  reason: 見本は 設計全体を 見せる 場であって、リリースの 順番の 表明ではない。オペラ・オーケストラ・ガラの 3種の 見本を 消す 必要は ない
  ただし: 「どんな公演ですか」の 選択肢で、まだ 出さない 種類には 出す時期を 添える（design-v11で すでに その形。オーケストラ・ガラの 印を 1→0 に 直すだけ）
```
