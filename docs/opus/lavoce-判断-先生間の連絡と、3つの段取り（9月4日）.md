## §1 先生間の連絡 ── 案B

### 1.1 なぜ C（持たない）ではないか

★Sonnet の見立てが正しいです。

```
連絡経路が無ければ、★LINEに流れます
　　→ そこでは Woolsong の設計は何も守れません
　　→ 「持たない」は、守りを外部に丸投げしているだけです
```

★ただし、**LINEに流れること自体は、悪ではありません。**

```
雑談・世間話          ★LINEでよい。むしろそのほうが安全です
　　　　　　　　　　　 （Woolsong が健康情報を保持しません）
予定に対する操作      ★Woolsong が受け持つ
```

★**この線引きを先に決めると、Bの範囲が決まります。**

### 1.2 なぜ A（自由チャット）ではないか

```
・自由記述は、制御できません（今日、health_notes で確認したとおり）
・保持期間・削除・退会時処理・未成年保護・通報・見張りが、全部ついてきます
　　★個人事業で持てる重さではありません
・そして★#003 で確立した原則の、裏口になります
```

### 1.3 案B の設計 ── 厳密にしてください

★**自由記述欄を、1つも作らないでください。**
　1つでも作れば、そこに全部書かれます。

```
連絡は、必ず★予定に紐づく（予定のない連絡は作れない）

送れるもの（★選択肢のみ）
　　変更希望   ／ 代講をお願いしたい ／ 欠席の連絡
　　遅れます   ／ 部屋を変えたい     ／ ★相談したいことがあります

　　★「相談したいことがあります」だけを用意し、★中身は書かせない
　　　（責任者が、別の経路で本人に連絡する）
```

★宛先について ── **先生同士を、直接つながせないでください。**

```
先生A → ★責任者（owner/admin）→ 先生B
```

```
理由1  先生同士の会話が育つと、必ず生徒の体調の話になります
理由2  ★責任の所在が、はっきりします
理由3  責任者が、予定を実際に変えられる唯一の人です（権限分離のとおり）
```

★生徒の名前は出て構いません（予定に紐づくので必然です）。
　**生徒の体調は、書く欄がありません。**構造で塞ぎます。

### 1.4 営業のときの説明

```
　「Woolsong は、連絡ツールではありません。
　　予定に対する変更希望だけを、★記録に残る形で受け取ります。
　　雑談は、これまでどおりの手段でお願いします」
```

★学校の情報システム部門には、**これがそのまま強みになります。**
　「チャットがない」ことを、弱みとして説明しないでください。

## §2 G5 #34 ── 裁定します

### 2.1 答え

```
★先生の操作で、生徒の entries を書き換えてはいけません
```

★理由

```
・entries は「本人だけのもの」です（A-2の同意で、そう伝えています）
・先生が書き込めるなら、★その約束が崩れます
・そして生徒は、★自分が入れていない数字を見ることになります
```

★今日の午前に profiles で見つけたのと、**同じ形の裏口です。**

### 2.2 代わりの形

```
1  先生がレッスンの開始・終了を記録する
　　　→ ★lessons に入る（先生のデータ）

2  生徒の画面に出る
　　　「きのうのレッスンは60分でした。発話時間に足しますか？」

3  ★生徒が押して、はじめて entries に入る
```

```
★生徒の記録に入るものは、★生徒が押したものだけ
```

★これは「取り込み先の再判断・複製をやめる」で決めた形と同じです。
　**複製しない。参照して、本人が確定する。**

### 2.3 自動反映にしたかった理由は、正しい

★「生徒が入力を忘れる」という問題意識は、正しいです。
　**だから通知は出してください。書き込みだけをやめます。**

★そして、押されなくても分析は困りません。
　lessons 側にデータがあるので、「レッスンの日は」という分析は別途できます。

## §3 お知らせ画面の 9/10 ── 維持します

### 3.1 私の最初の判断が、そのまま当てはまります

```
9月10日までに 再同意画面＋撤回ボタンが揃う → まとめて1回
9月10日に揃わない → ★その日に、通知だけ先に出す
```

★いま、揃わない見込みです。**だから、分けます。**
　「同じ人を2回止めない」と申し上げましたが、
　**あれは9/10に間に合う前提でした。間に合わないので、前提が外れます。**

### 3.2 優先順位

```
★1  撤回ボタンを作る            9/10まで。★最優先
　2  同意画面にポリシー/規約のリンクを足す   今すぐ。小さい作業
　3  お知らせ画面を出す          9/10
　4  再同意                      ★B-3/B-4 ができてから（第2便）
```

★**1が最優先である理由**

```
「いつでも撤回できます」と書いて、撤回できない状態が続いています
　　★これは、日数が延びるほど重くなります
　　★そして、B-3/B-4 に一切依存しません。いま作れます
```

### 3.3 通知の文面から、1つ外してください

```
（外す）「ポリシーと利用規約を直しました」
（残す）「同意の書き方に不備がありました。近いうちに、
　　　　　もう一度ご同意をお願いすることになります」
```

★**再同意の実施は、B-3/B-4 のあとで構いません。**
　通知は「これから起きること」を伝えるもので、
　**その場で同意を取り直す必要はありません。**

## §4 B-3/B-4 の段取り

### 4.1 いちばん大事な判断 ── 弁護士確認を待たない

```
★B-3/B-4 は、弁護士確認前の版で公開してよいです
```

★理由

```
いま公開されている /legal は、★そもそも弁護士確認前の下書きです
　　→ より良いものに差し替えるのを、弁護士待ちで止める理由がありません
　　→ ★いまより悪くなることは、ありません
```

★弁護士確認は、**有料化の前まで**で構いません。
　（そのときは、医師法の線引きも一緒に見てもらってください）

★これで、**クリティカルパスから外れます。**

### 4.2 詰まりは1つだけです

```
★/legal/terms の「表示される本文」が、まだ届いていません
```

★これが無いと B-4 が書けません。**コードではなく、レンダリング後の文字です。**
　すでに公開されている以上、そこに書いてあることは**公開中の約束**です。
　知らずに書き直すと、**約束を減らしてしまいます。**

★Code に、ブラウザで /legal/terms を開いて、本文を書き写させてください。
　（前便の規則どおり、ファイルに書いてパスを渡す形で）

### 4.3 段取り

```
坂本さん   B-3 の★空欄4つを埋める
　　　　　 　① 事業者の氏名の表記（「坂本 響」か「Woolsong（坂本 響）」か）
　　　　　 　② 住所を掲示するか、求めに応じて回答する形にするか
　　　　　 　③ お問い合わせ先のメールアドレス
　　　　　 　④ ★未成年の扱い（案1：年齢を聞く／案2：15歳未満は使えない）
```

★④は、教室プランを売る前に決めれば足ります。**急ぎません。**
