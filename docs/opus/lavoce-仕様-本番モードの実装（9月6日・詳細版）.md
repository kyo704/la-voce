## §1 events テーブル

### スキーマ

```sql
create table events (
  id            uuid primary key default gen_random_uuid(),
  user_id       uuid not null references auth.users(id) on delete cascade,

  -- ★逆算はこの2つだけで成立します
  event_date    date        not null,          -- ローカル日付（§1.3）
  kind          text        not null,          -- §1.1

  label         text,                          -- ★任意。アプリは読まない。表示だけ
  load_coef     numeric(3,2),                  -- 負荷。null なら kind の既定値
  recovery_coef numeric(3,2),                  -- 回復への影響（travel 用）
  org_event_id  uuid,                          -- 教室の予定から取り込んだ場合の元
  created_at    timestamptz not null default now(),
  updated_at    timestamptz not null default now()
);

create index events_user_date on events (user_id, event_date);
create index events_user_kind_date on events (user_id, kind, event_date);
```

### §1.1 kind の値と既定の係数

| kind | 表示名 | load_coef | recovery_coef | 備考 |
|---|---|---:|---:|---|
| `honban` | 本番 | 1.60 | 1.00 | ★逆算の基準になるのはこれだけ |
| `rehearsal` | リハーサル | 1.30 | 1.00 | |
| `lesson_take` | レッスン（受ける） | 1.20 | 1.00 | |
| `lesson_give` | レッスン（教える） | 1.35 | 1.00 | 教えるほうが話す時間が長い |
| `recording` | 録音・収録 | 1.40 | 1.00 | やり直しで回数が積み上がる |
| `audition` | オーディション | 1.50 | 1.00 | |
| `travel` | 移動 | 0.00 | **0.75** | ★声は使わないが回復を削る |
| `rest` | 休養 | 0.00 | 1.10 | |

```
★係数の数値は、運営者が変えられるようにしておいてください（設定に持つ）。
　私（Opus）は歌っていないので、形だけ用意しています。
```

### §1.2 label（任意）

```
・最大 40文字
・★アプリは読みません。一覧とホームに、そのまま出すだけ
・空でも全機能が動くこと
・例：「ミラノ・椿姫」「NHK 収録」「発表会」
```

**「自由記述欄を作らない」という決まりには触れません。**
アプリが読んで返すものではないからです（裁定-日記と自由記述のちがい）。

### §1.3 ★日付の扱い（イタリア移住があるので重要）

```
event_date は ★date 型。時刻を持たない
「今日」の判定は ★端末のローカル日付（Intl.DateTimeFormat().resolvedOptions().timeZone）
サーバの UTC 日付で判定しない
```

```ts
const today = new Date().toLocaleDateString('sv-SE')   // 'YYYY-MM-DD' ローカル
const dn = Math.round((Date.parse(eventDate) - Date.parse(today)) / 86400000)
// dn > 0 … 本番まで dn 日   dn === 0 … 当日   dn < 0 … 過ぎた
```

★**日本からイタリアへ移動すると、時差で「今日」が変わります。**
UTC で判定すると、本番の当日に「あと1日」と出ます。必ずローカルで。

### §1.4 持たないもの

```
✕ 会場名　✕ 曲目　✕ 共演者　✕ ギャラ　✕ 時刻
```

公表前の情報であることがあるので、持たないほうがこちらの責任も軽くなります。


### 保存

```sql
create table event_results (
  id          uuid primary key default gen_random_uuid(),
  user_id     uuid not null references auth.users(id) on delete cascade,
  event_id    uuid not null references events(id) on delete cascade,
  result      text not null check (result in ('out','partial','not_out')),
  answered_at timestamptz not null default now(),
  unique (event_id)
);
```

| 選択肢 | 保存する値 |
|---|---|
| 出た | `out` |
| 途中まで | `partial` |
| 出なかった | `not_out` |

```
★1つの本番に1件だけ（unique）。押し直しは上書き
★この表は ★要配慮個人情報になりません
　　（病名でも受診結果でもなく、本人の主観の3択です）
```

## §8 「前も、こうでした」の作り方（有料の中核）

### 出す条件

```
・有料プランに入っている
・D-7 〜 D-1 のあいだ
・過去に event_results が ★1件以上ある
```

### 何を出すか

```sql
-- 過去の本番のうち、同じ D-n の日に「のどの違和感」があったもの
select e.event_date, r.result
from events e
join event_results r on r.event_id = e.id
where e.user_id = $1 and e.kind = 'honban'
  and e.event_date < current_date
order by e.event_date desc
limit 5;
```

### 文言（3つの形）

**A. 同じ症状があったとき**
```
　前回、本番の前日にのどの違和感がありました（4月8日）。
　当日は「出た」でした。
```

**B. 同じことが複数回あったとき**
```
　同じことが 3回 ありました。3回とも「出た」でした。
```

**C. まだ材料が足りないとき（★これが最初は多い）**
```
　本番の記録が、まだ 1回 ぶんです。
　もう1回たまると、前の本番とくらべられます。
```

```
★Cを「制限」に見せないこと。「まだ」とだけ書く
★予測しない。「たぶん出ます」と書かない。★過去の事実だけ
★結果が「出なかった」でも、そのまま出す。隠さない
```

## §11 端の場合（★実装で必ず出ます）

```
□ 本番日を過ぎた　　　　　→ 帯は次の本番へ。無ければ未登録表示
□ 本番日を編集した　　　　→ 区間の判定は毎回計算する（保存しない）
□ 本番日を削除した　　　　→ event_results も一緒に消える（on delete cascade）
□ 同じ日に本番が2件　　　　→ 帯は1件だけ。一問は ★2件それぞれに聞く
□ 本番が今日から3日後　　　→ いきなり「抜く」区間から始まる。それでよい
□ 時差で日付が変わった　　→ ★必ずローカル日付で再計算（§1.3）
□ 過去4週のデータが無い　　→ ①を出さない（「―」も出さず、行ごと消す）
□ 体験中に本番日を変えた　→ ★体験期間は動かさない（一度決めたら固定）
□ オフラインで答えた　　　→ ローカルに積んで、つながったときに送る
```

## §12 これができたら「使ったことがある」状態です

```
□ 本番日を1件登録できる
□ ホームに「あと n 日」が出る
□ D-1 に「明日だね」が出る
□ D-0 に「いってらっしゃい」が出る
□ ★D+1 に一問が出て、答えが保存される
□ 2回目の本番の D-1 に「前も、こうでした」が出る　←　ここまで来たら完成
```

**最後の1つは、本番を2回こなさないと確かめられません。**
テストでは、event_date を過去にした本番と event_results を手で入れて確かめてください。
