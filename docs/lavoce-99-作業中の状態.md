## 5.11 ★Day 4（メモ欄）は、移行が要らないかもしれません — 要判断

文書の中で、2つの節が違うことを言っています。

  §4  「廃止しません。役割を変えます」
      「★既存のメモは1件も消さないでください。
        入力欄の見出しと説明文を変えるだけです」
  §7  interface SelfExplanation { userId; articleId; text; updatedAt }
      「★既存のメモをここへ移行する。消さない」

★いまの article_notes は、SelfExplanation の項目をすべて含んでいます。
  user_id / article_id / body / created_at ＋ kind / anchor_text /
  shared_with_teacher / deleted_at

つまり kind に 'self_explanation' を入れれば、新しい表を作らずに §7 の
形を満たせます。表を増やして中身を移すと、移し損ねる危険と、
書き出し・削除の対象を足し忘れる危険が生まれます。どちらも
このセッションで実際に踏んだ形です。

**私の考え**: 新しい表を作らず、article_notes の kind を使う。
§4 の「見出しと説明文を変えるだけ」とも一致し、移行そのものが不要になります。
§7 の意図（自己説明を別物として扱う）も、kind で満たせます。

★ただしこれは仕様の読み替えなので、坂本さんの判断が要ります。

# 2026-09-01｜手で作った表に、RLS のポリシーが足りていなかった

## 何が起きたか

削除試験のために先生役のアカウントで招待コードを発行しようとしたところ、
**403 / 42501** で止まりました。原因は2つ重なっていました。

```
① organizations に INSERT のポリシーが★1つも無かった
     SELECT のポリシーだけがありました。
     RLS が有効な表に INSERT ポリシーが無いと、service_role 以外からの
     INSERT は★すべて拒否されます。
```

```
organizations_select_own_created    自分が作った教室は読める（RETURNING のため）
memberships_insert_bootstrap_owner  自分を／owner として／自分が作った教室に／
                                    まだ誰も居ないときだけ
```

```sql
select c.relname as "テーブル"
  from pg_class c
  join pg_namespace n on n.oid = c.relnamespace
 where n.nspname = 'public' and c.relkind = 'r' and c.relrowsecurity
   and not exists (
     select 1 from pg_policies p
      where p.schemaname = 'public' and p.tablename = c.relname
        and p.cmd in ('INSERT', 'ALL')
   )
 order by 1;
```
