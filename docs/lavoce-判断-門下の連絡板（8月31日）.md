# Opus の判断 ── 門下ごとの連絡板（予定表の中に置く）

作成 2026年8月31日 ／ 坂本さんの提案に対する回答

---

## 0. 坂本さんの提案（原文）

> 大学の教室機能に門下ごとのグループ？
> 予定表にはその門下に関係のある人たちだけが見れる掲示板を設置。
> 誰でも自由に書けるが、基本的には門下全体に関わる
> 教室の緊急連絡のみの使用

**結論から書きます。作ります。**
**ただし、既存の恒久禁止と正面からぶつかるので、
なぜ今回だけ通るのかを、理由の側から書き直します。**

**名前は「掲示板」にしません。「門下の連絡板」とします（理由は §7）。**

## 1. ★まず、何とぶつかっているか

```
lavoce-教師間コミュニケーション仕様.md §3-1
　生徒を1人でも入れられるようにした瞬間に、
　これは「大人と未成年が自由記述でやり取りする場」になります。
　★「成人の生徒なら入れたい」という提案も断ってください。

lavoce-レッスン連絡パッチ.md §4-1
　自由記述欄を、絶対に作らない
　生徒との自由記述のやり取りは、作らない。★恒久的に
```

**今回の提案は、この2つに真正面からぶつかります。**
「学生が自由に書ける場を作る」というのは、まさに止めてきたものです。

**だから、例外として通すことはしません。**
**禁止していた理由の側を見て、その理由が今回も当てはまるかを確かめます。**

---

## 2. 禁止の理由は3つあった。そのうち何が残るか

**§3-1 で止めた理由を分解すると、こうなります。**

```
理由①  未成年が含まれる
理由②  1対1である
理由③  非公開である（第三者の目がない）
```

**この3つが揃うと、閉じた場でのやり取りになります。**
だから止めていました。**今回、3つとも当てはまりません。**

```
理由①  未成年     → 案D（8月30日）で、未成年フラグの口座は
                     先生に紐づけられない。門下に入れない。★自動的に外れる
理由②  1対1       → 連絡板は一対多。門下の全員が同じものを読む
理由③  非公開     → 先生と門下の全員が読む。★書いた瞬間に、20人が見ている
```

**★理由③が、いちばん強い抑止です。**
1対1の非公開の場で起きることは、公開の場では起きません。
**「見られている」という設計そのものが、安全装置になっています。**

### ★ただし、この判断には条件がついています

```
連絡板が許されるのは、①②③の3つが同時に成り立っているときだけです。

・未成年が門下に入れるようになったら → 連絡板を作り直すか、止める
・1対1のやり取りを足したくなったら   → ★足さない。そこが境界です
・「一部の人にだけ見える投稿」を足したくなったら → ★足さない。同上
```

**つまり、連絡板を作るということは、案D（未成年は先生に紐づけない）を
恒久的な決まりにする理由が、もう一つ増えるということです。**

## 3. データの形 ── 「門下」という新しい入れ物を作らない

**★新しいテーブルを作らないでください。**

```
門下 ＝ ある先生に、いま紐づいている学生の集合
     ＝ Assignment（teacherId, studentId, endedAt）で、すでに表現できている
```

```
連絡板が見える人
　その先生
　その先生の Assignment で endedAt が null の学生
　その org の owner / admin

連絡板が見えない人
　同じ大学の、別の門下の学生
　担当を外れた先生
　担当が終わった学生
```

**★担当を外れたら、その時点から過去の投稿も含めて見えなくなります。**
教師間コミュニケーション仕様 §4-1 の `Assignment.endedAt` と同じ扱いです。
「担当だった期間の分は読める」を作らないこと。

### 門下代表

**新しい role を作らないでください。** `Assignment` に真偽値を1つ足すだけです。

```
Assignment.isRepresentative  先生が指定する。1門下に1〜2名
```

## 4. ★いちばん大きな危険 ── 体調が、ここから漏れる

**これは坂本さんの提案には書かれていませんが、いちばん重要です。**

**この製品の約束は「記録は先生に見られない」です。**
連絡板は、その約束と同じアプリの中に、新しく開く窓です。

```
学生が書く
　「今日は喉の調子が悪いので、レッスン休みます」

このとき何が起きたか
　誰も約束を破っていません。学生が自分で書きました。
　しかし、体調のことが、先生と門下の20人に伝わりました。
　そして次の学生は「休むときは理由を書くものだ」と学びます。
```

**★「記録は見られない」が、静かに嘘になります。**
機能としてではなく、習慣として。

### 対処（3つとも実装してください）

```
① 投稿欄の下に、常に1行を出す
　　★「ここに書いたことは、門下の全員と先生が読みます。
　　　体調のことは、書かなくて構いません。」

② 欠席の連絡を、連絡板に書かせない
　　連絡板に「休みます」の導線を作らない。
　　既存の定型連絡（レッスン連絡パッチ §3）へ出す。
　　★定型連絡は、先生1人にしか届きません。門下の20人には届きません。

③ ★投稿の中身を、サーバーが検査しない
　　「体調の語を検出して警告する」を作らないでください。
　　それは、サーバーが全員の投稿を読むということです。害のほうが大きい。
```

**①の一行が、実際の守りです。** 安く、正直で、これ以上のものはありません。

## 5. 「誰でも自由に書ける」と「緊急連絡のみ」は、放っておくと両立しない

**坂本さんは両方を書いています。** どちらも本心だと思います。
**しかし、ソフトウェアは「緊急のことだけ書け」を強制できません。**

```
起きること
　最初の2週間  教室変更の連絡だけが載る。うまくいく
　1か月後      「今日の合わせ、ありがとうございました」が載る
　3か月後      緊急連絡が、雑談に埋もれる
　半年後       誰も見なくなる。緊急連絡は結局LINEで回る
```

**投稿数を制限しても解決しません。**（雑談を止めると、連絡板が固くなって、誰も書かなくなります）

### ★解き方 ── 制限ではなく、通知の非対称で解く

```
投稿できる人   門下の全員（学生も先生も。★提案どおり、自由に書けます）

「重要」を付けられる人   ★先生と、門下代表だけ

通知が鳴る投稿   ★「重要」が付いた投稿だけ
その他の投稿     静かに載る。連絡板のバッジに数が増えるだけ
```

**これで両方が成り立ちます。**

```
誰でも自由に書ける      → 満たされる
緊急連絡が埋もれない    → 「重要」だけが鳴るので、埋もれない
雑談が悪者にならない    → 鳴らないだけで、書いてよい
```

**★「重要」が付いた投稿は、連絡板の最上部に、既読になるまで留まります。**
既読になったら、通常の並びに戻ります。

## 6. 添付を作らない ── 理由は容量ではありません

**★画像もファイルも、v1では添付できないようにしてください。**

```
教師間コミュニケーション仕様 §3-2 と、まったく同じ理由です。

　学生が、自分の分析画面のスクリーンショットを貼れてしまう
　　→ 「私の今週のグラフです。見てください」
　　→ ★門下の20人が、その学生の体の状態を見る
　　→ 次の週、貼らない学生が「隠している」ことになる
```

**§4の危険が、画像の形で戻ってきます。**
**文字だけにしてください。** 教室の変更を伝えるのに、画像は要りません。

## 7. 名前 ── 「掲示板」にしない

```
掲示板    何を書いてもいい場所。書き込みが目的
連絡板    伝えることがある人が使う場所。伝わることが目的
```

**画面に出す言葉は「連絡」です。**

```
見出し      門下の連絡
投稿ボタン  連絡する
placeholder 門下のみんなに伝えること（教室の変更、時間の変更、持ち物など）
```

**★placeholder が、いちばん強く用途を決めます。**
ここに「教室の変更」と書いておけば、最初の1件がその形になります。
**最初の3件が、その場の性格を決めます。**

---

## 8. 置き場所 ── 予定表の中。独立したタブにしない

**★坂本さんの「予定表には…掲示板を設置」は、そのまま正しいです。**

```
教師間コミュニケーション仕様 §2
　汎用のチャットとしては、LINE にも Slack にも勝てません。
　勝てるのは、文脈が入っていることだけです。
```

**門下は、すでに LINE グループを持っています。移りません。**
**移る理由は一つだけです ── 予定表の隣にあること。**

```
LINE     「今日301から205に変わりました」
          → 今日のレッスンが何時だったかは、各自の記憶の中

Woolsong 同じ連絡が、その日の予定の真下にある
          → 予定を見にきた人が、必ず目にする
```

**だから、下タブに「連絡」を足さないでください。**
**予定表の画面の中に置いてください。** 独立させた瞬間に、LINEと同じ土俵になり、負けます。

---

## 9. 消えること ── 90日で自動的に消す

**★投稿は90日で自動的に消えます。最初からそう書いておいてください。**

```
理由①  緊急連絡は、3か月後には価値がありません
理由②  ★残さないことが、この製品の一貫した立場です
        （教室運営の範囲とカレンダー書き出し §3-1
         「Woolsong は、他人の予定を1件も保存しません」の精神）
理由③  坂本さんが1人で、イタリアから運用します。
        残るものが少ないほど、対応することが少なくて済みます
```

**画面に「90日で消えます」と書いてください。**
消えることを隠すと、消えたときに問題になります。書いておけば、機能になります。

## 10. 消す・報せる（作ってください）

```
自分の投稿を消す          誰でも。いつでも
門下の投稿を消す          ★先生と門下代表。理由の入力は求めない
報せる（通報）            誰でも。宛先は org の admin と坂本さん
                          ★1件でも来たら、その投稿は自動で隠す。判断はあとで
```

**★「1件で自動的に隠す」は、乱用されるように見えますが、そのままにしてください。**
門下は20人程度の、顔を知っている集団です。乱用は起きにくく、
**起きたときに坂本さんがイタリアから対応できることのほうが、はるかに重要です。**

**利用規約に、連絡板についての条項を1つ足してください。**
「投稿の責任は投稿者にある」「規約に反する投稿は削除する」の2点で足ります。

## 11. 時期 ── 大学導入を待つ必要はありません

**★これは大学固有の機能ではありません。**

```
門下 ＝ 先生1人と、その学生たち
      → 街の音楽教室でも、まったく同じ形です
```

```
lavoce-作業指示-音楽大学への導入と教材化.md
　★着手禁止。最初の1校が決まってから
```

**この禁止が掛かるのは「大学の時間割データの取り込み」の側です**
（lavoce-判断-大学のレッスン日程と外部連携.md）。
**連絡板は、そこに依存していません。**

```
実装できる時期
　教室プランの本体（複数教師・複数生徒・希望申告）が動いたあと
　★大学の1校目を待たない
```

### ★売るときに効くこと（覚えておいてください）

**大学に売るとき、痛んでいるのは門下代表（学生）で、払うのは大学です。**
**この2人が違うことが、大学導入のいちばんの難所でした。**

**連絡板は、門下代表の手間を直接減らす、数少ない機能です。**
学生が「これが欲しい」と言える機能が、いくつあるか ──
**それが、大学の中で話を運んでくれる人がいるかどうかを決めます。**
連絡板は、その一つです。
