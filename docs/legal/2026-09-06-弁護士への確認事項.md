# ④ 既往症の選択肢を持ち続けることの是非

## 伺いたいこと

既往症の選択肢を**あらかじめ用意しておくこと自体**に、
個人情報保護法上のリスクはないか。

## いまの選択肢（9つ）

```
逆流性食道炎 ／ 咽喉頭酸逆流 ／ アレルギー性鼻炎・花粉症 ／ 喘息 ／
副鼻腔炎 ／ 甲状腺疾患 ／ 貧血 ／ 睡眠時無呼吸症候群 ／
声帯結節・ポリープの既往
```

## 論点

- これらは**要配慮個人情報**（病歴）に該当すると理解しています。
- **選択肢として提示すること**自体が、取得の勧誘にあたらないか。
- 声を使う職業では、**逆流性食道炎などは声の不調と直接関係する**ため、
  記録する意味が実際にあります。医学的な必要性はある、と考えています。
- ただし、**選択肢を出せば「入れてよいもの」と受け取られる**面があります。

## いま行っている手当て

```
・要配慮個人情報の同意を、★別途取得（consent_health_data_at）
・同意の撤回ができる（consent_health_data_withdrawn_at）
・★同意を取り直した（2026年9月）
・★入力は任意。空のままでも、すべての機能が使える
・★先生（指導者）には共有されない項目がある（11列を明示的に除外）
```

# ⑤ 復旧コード・メールアドレス変更の設計

## 伺いたいこと

以下の設計に、個人情報保護法上の問題はないか。

## 復旧コードの設計

```
・12文字（Crockford Base32。★I / L / O / U を含まない）＝ 60ビット
・★平文では保存しません。scrypt でハッシュ化して保存
　　　N=2^15, r=8, p=1, 鍵長32バイト, maxmem=64MB
　　　★利用者ごとに異なるソルト
・照合は timingSafeEqual（★処理時間から情報が漏れないように）
・★ログに出しません（console 出力なし）
・5回まちがえると、15分ロック。★以降は倍々（上限24時間）
・保存先：recovery_codes 表（code_hash, code_salt）
```

**画面の文言**：「人に見せないでください。このコードだけで、記録を見られます。」

## メールアドレス変更の設計

```
・変更時、★新旧の両方のアドレスに通知します
・email_change_log 表に、old_email / new_email / 日時を記録
・★IPアドレスは保存しません
・重要な操作（書き出し・削除・メール変更・復旧コード再発行）の前に、
　パスワードで再確認。★確認から5分間だけ有効
・★確認した事実は、サーバ側にのみ保存（reauth_at 列）
```

## とくに伺いたい点

1. **復旧コードだけで記録全体にアクセスできる**設計は、
   本人確認の手段として適切か。（★問い合わせ窓口を作らない方針のため、
   これが唯一の復旧手段です）
2. `email_change_log` に**旧アドレスを保存し続けること**は、
   保存期間の観点から問題ないか。**いつまで持ってよいか。**
3. 新旧両方への通知は、**旧アドレスの持ち主が第三者になっている場合**
   （例：会社のアドレスを退職後に他人が使用）に問題を生じないか。

# ⑥ 保護者のメール確認の、法的な実効性

## 伺いたいこと

**メールへの確認リンクのクリックだけで、民法上の法定代理人の同意として
認められるか。**

## ★★前提の訂正（②と同じ）

**この機能は、まだ存在しません。**
コードを検索しましたが、保護者のメールアドレスを扱う処理は
一切ありません。

**現状は、本人が押すチェックボックスのみです。**
「保護者の同意を得た」と本人が申告するだけで、
**当方はその真偽を確認していません。**

★このため本項は、「いまの設計の評価」ではなく、
**「これから作るとして、意味があるか」というご相談**になります。

## 懸念していること

1. メールアドレスの入力者は**本人**です。
   本人が自分の別アドレスを入力すれば、通過してしまいます。
2. リンクをクリックした人物が**保護者本人である保証がありません。**
3. それでも「**確認した**」という記録が残ることで、
   **かえって「確認済み」と誤認される**リスクがあるのではないか。

★当方の設計方針は「**確かめられないことを、表示しない**」です。
　実効性のない確認手続きを入れることが、この方針に反しないか、
　法的にプラスなのかマイナスなのか、ご意見をいただきたいところです。

