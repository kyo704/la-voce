## 2. ★なぜ、これが問題か

アカウントを消された方には、30日の猶予のあとに本当に消えます（`lib/accountDeletion.js`）。
ところが**控えは、消した瞬間の前に取られたものが残ります**。
その控えから戻すと、★**消したはずの方が、何ごともなかったように戻ってきます。**

戻ってきたことに、誰も気づけません。本人にも通知は行きません。
「消してください」と言われたのに残っている、といういちばん重い状態が、
★事故ではなく**手順どおりに**起きます。

## 3. 提案：消した方の名簿を、控えの外に置く

### 3-1 かたち

`public.deletion_tombstones` — 列は3つだけです。

| 列 | 中身 |
|---|---|
| `user_id` | 消した方の id（uuid） |
| `purged_at` | 本当に消した日時 |
| `reason` | `'self'`（本人の申し出）／`'admin'` |

★**名前もメールも記録も入れません。** 「この id は消しました」という事実だけです。
消した方の情報を残すための表ではありません。**戻ってこないようにするための表**です。

### 3-2 ★控えの中に入れないこと

`lib/backupTables.js` の一覧に**入れません**。同じダンプに入れてしまうと、
古い控えを戻したときに**名簿ごと古くなり**、意味がなくなります。

置き場所の案（どちらかを選んでいただきます）:

- **案A**: 別のプロジェクト／別のデータベースに置く。いちばん確実です。
- **案B**: `backups/tombstones.csv` として、ダンプとは**別のファイル**で持ち出す。
  仕組みは軽いですが、★このファイルを取り忘れると効きません。

★私の推しは**案A**です。取り忘れが起きない形だからです。

### 3-3 使い方（★復元したあとに、必ず走らせる）

復元は年に何度もありません。だから**自動では動かしません**。
`docs/backup-restore.md` の手順の**最後の一段**として足します。

```sql
-- ★復元のあと、必ず走らせてください。
--   控えの中に、消したはずの方が戻ってきていないかを見ます。
select t.user_id, t.purged_at
  from deletion_tombstones t
 where exists (select 1 from auth.users u where u.id = t.user_id);
```

★ここに1行でも出たら、**その方は戻ってきています**。
出た id について、`lib/accountDeletion.js` の消し込みをもう一度走らせます。

★0行であることを確かめるまで、**復元は終わっていません**。

## 5. 合わせて：お知らせの宛先は、決めた時点で名簿に固める

いまの `lib/noticeAudience.js` は、`cohort` を**その場で読んで**宛先を決めます。
これは配信の直前までは正しいのですが、★**送ったあとに `cohort` が変わると、
「誰に送ったか」が後から変わってしまいます。**

- 先行公開が終わって `tester` → `general` に移した
- あとから `is_internal` を立てた

どちらも、あとで「送った人の一覧」を出し直すと**答えが変わります**。
★届かなかった方を探すときに、その人が一覧から消えていたら、永久に見つかりません。

**提案**: 宛先を決めた時点で、id の一覧を**そのまま保存**します。
以後の「送った／再送した／返事がない」は、★**その固めた一覧に対して**数えます。
`cohort` は二度と読み直しません。
