## 0. 実装者への前提共有

### このアプリは何か

声のプロフェッショナル（声楽家・ミュージカル俳優・声優・アナウンサー・ボイストレーナー）向けの、
**「歌が上手くなる」ではなく「声を壊さない」** ことに振った縦断的コンディション記録アプリ。

現在のタブ構成:

| タブ | 内容 |
|---|---|
| ホーム | 挨拶、今日のスコア、連続記録、次のアンロック進捗 |
| 今日の記録 | 声の記録（音名・響きスコア・CPPS測定）＋ 一日の記録（睡眠・食事・体重・環境・症状・メンタル） |
| 分析 | 声の調子スコア、偏差値、声の予報、音域到達マップ、ウォームアップ効率、症状カレンダー、栄養、ACWR ほか |
| レッスン | 指導者向け。生徒のレッスンカレンダーと生徒一覧 |
| おうち | ポイントで部屋・庭・服を買うゲーミフィケーション |
| ノート | 稽古ノート（カレンダー／メモ）、目標設定 |
| もっと | 学ぶ / 健康情報 / 質問票 / 受診用サマリー / レッスンモード / AIアドバイス / 各種設定 / LINE連携 |

### 絶対に壊してはいけない既存の設計（ガードレール）

以下は **維持すること**。このアプリの中核的価値であり、リファクタや簡潔化の名目で削らない。

1. **医学的断定を避ける免責文言** — 「医学的診断ではない」「自分自身の推移で見る参考値」という一貫したトーン
2. **音名表記のルール説明** — 国際式（ミドルC = C4）とヤマハ式のズレ。※常時表示はやめるが、内容は残す（4章参照）
3. **裏声ではなく地声で記録する指示** — ドメイン知識に基づく設計判断
4. **絶対湿度での環境快適帯** — 相対湿度ではなく絶対湿度で見る判断。意図的なもの
5. **ポイントは「記録を続けたか」だけで貯まる** — 体調の良し悪しで報酬が変わらない設計
6. **標準化質問票（RSI / VFI / SVHI-10 / EASE）** — 最大の差別化要素
7. **CPPSの録音データを保存せず即時破棄する処理** — プライバシー設計の中核
8. **段階的アンロック** — 継続動機の設計。※配置は変えるが仕組みは維持（4章参照）
9. **エネルギー可用性の「体重や体型ではなく」という立場** — 摂食障害リスクの高い職種への配慮

## 2. P0: 最優先（信頼を直接損なっている / 公開段階で必須）

### P0-1. 少数データでの断定的な文言を抑制する

**現状の出力例（分析タブ「複数の条件を組み合わせて見えてきたこと」）:**

> 食事では、喉の調子が良かった日（3日）に「白米（ご飯）」を食べていることが多いです（9日）。
> 反対に、喉の調子が悪かった日（1日）には「白米（ご飯）」を食べていることが多いです（3日）。

**問題:** 良い日にも悪い日にも同じ食品が挙がり情報量がゼロ。誤った因果を刷り込むリスク。
免責文を足しても解決しない。**出力しないのが正解**。

**対応:**

- 相関・傾向を文章で語るすべての箇所に、共通の最小件数ゲートを実装する
- 推奨閾値: 各群 n >= 10、かつ両群が揃っていること
- 満たさない場合は文章を生成せず、「あと◯件の記録で、食事と声の傾向の分析が始まります」に置き換える
- 閾値は定数として1箇所に集約する（例: `MIN_N_FOR_NARRATIVE = 10`）
- 対象箇所（網羅すること）:
  - 「複数の条件を組み合わせて見えてきたこと」の全文
  - 「休養方法ごとの声・メンタルの傾向」
  - 「滞在地ごとの声・メンタルの傾向」
  - 「よく一緒に出る症状」
  - 「気持ちタグの傾向」
  - 「時間帯別の声の傾向」の「調子が良い傾向」バッジ

**受け入れ条件:** 記録8日程度のアカウントで、断定的な相関文が1つも表示されない。代わりに進捗表示が出る。

### P0-2. 発声負荷（ACWR）の警告を、データが揃うまで出さない

**現状:** 分析タブ最上部に「⚠️ 今日の一言 / 今日の発声負荷比は2.2。喉を痛めやすい急増な状態です」
と警告が出る一方、「発声負荷バランス（ACWR）」パネル自体は「あと20日で解放されます（8/28日）」とロック中。

**問題:**

- ACWRは急性7日 / 慢性28日のローリング平均比が前提。慢性側が8日では数学的に信用できない
- ロックされているはずの指標が、警告としてだけ先に露出している
- 不安を煽る側の表示が、最も精度の低いタイミングで出ている

**対応:**

- 慢性側28日分が揃うまで、発声負荷比の警告を出さない
- 代わりに中立な文言を出す。例:「発声負荷バランスの計算には、あと20日分の記録が必要です。」
- ACWRパネルのロック状態とトップ警告の表示条件を **同一のフラグで制御** する
- 「今日の一言」の他の警告文も、根拠指標がロック中でないか確認する

**受け入れ条件:** ACWRパネルがロック中のとき、トップに発声負荷比の警告が出ない。28日揃った時点で両方が同時に有効化される。

### P0-3. データ書き出しとアカウント削除

**現状:** 「もっと」→ アカウント に「データの書き出し・アカウント削除機能は準備中です。」とだけ表示。

**対応（データ書き出し）:**

- 全記録をJSONまたはCSVでダウンロードできるようにする
- 最低限、日々の記録・質問票の回答履歴・目標／ノートを含める
- 声の記録と一日の記録は日付をキーに結合した形が望ましい

**対応（アカウント削除・多段フロー）:**

開発者方針により、ワンタップで消えない多段フローとする。以下の順で別ページに遷移させる。

1. 「もっと」→ アカウント → **アカウントの削除について**（別ページ）
   - 削除すると何が失われるか（記録日数、質問票の履歴、指導者との共有関係）を実データで表示
   - 「先にデータを書き出す」ボタンを目立たせる
2. → **削除の影響を確認**（別ページ）
   - 指導者アカウントの場合、生徒との共有がどうなるかを明示
   - 生徒アカウントの場合、指導者側の表示から消えることを明示
3. → **最終確認**（別ページ）
   - 登録メールアドレス、または「削除します」の文字列をテキスト入力させる
   - ここで初めて削除ボタンが有効化される

> **実装上の注意:** 多段にすること自体は問題ないが、各ステップが「情報提示」として意味を持つ形にすること。
> 無意味なページを挟むだけの引き止めは、GDPR上「削除権の行使を不当に妨げる」と見なされうる。
> 上記の3ステップは、いずれも「知らせる」「取り返しをつける」ための実質を持たせてある。

**受け入れ条件:** 設定から書き出しと削除の両方が実行できる。削除後、同一メールで再登録しても旧データが復活しない。

## 3. 新規機能

### 3-1. 発声量（vocal dose）の記録 ★最優先

**背景:** 受診用サマリーに「1日あたりの平均発声時間：約0時間」「声の使用量（週あたり）0h」と出ており、
この項目は事実上機能していない。発声時間を取る入力手段がないため。

音声医学で声の障害を最も予測するのは「どれだけ声を使ったか」であり、ここが空欄なのは構造的な欠落。
また現在のACWRは「休養／自主練習／レッスン／リハーサル／本番」という主観的カテゴリを数値化した代用品で
回っている。実測の発声量が入ることで、ACWRを含む複数の分析が同時に強くなる。

**軽量版（基本機能・全ユーザー）**

- 「今日の記録」に発声セッションの **開始 / 終了ボタン** を置く
- 1日に複数セッションを記録できる（朝の練習、レッスン、本番、など）
- セッションごとに種別（自主練習 / レッスン / リハーサル / 本番 / 発話業務）を持つ
- 押し忘れに備え、**後から手入力で時間を追加・修正できる**こと（ここは必須。押し忘れは必ず起きる）
- 集計値: 1日の総発声時間、種別ごとの内訳、週あたりの合計
- ACWRの入力を、カテゴリ由来の推定値から **実測発声時間** に切り替える
  （実測がない日はカテゴリ由来の推定値にフォールバックし、その旨をグラフ上で区別表示する）

**中量版（オプション・明示的なオプトイン）**

- バックグラウンドで一定間隔の **音圧レベルのみ** をサンプリングし、発声時間率を推定する
- **音声内容は一切保存しない。** CPPS測定と同じく、その場で数値化して破棄する
- 設定画面で明示的にオンにするまで動作しない。デフォルトはオフ
- オンにする画面で、何を取得し何を取得しないかを平易に説明する
- バッテリー消費の目安も表示する
- オフのままでも軽量版だけで全機能が使えること。中量版は精度の上乗せであって、前提にしない

**受け入れ条件:**

- 受診用サマリーの「1日あたりの平均発声時間」「声の使用量（週あたり）」に実データが入る
- 中量版がオフのユーザーでも、発声時間の記録と表示が成立する

### 3-2. ヘルスケアアプリ連携

**背景:** 現在、睡眠時間・体重をすべて手入力させている。記録負荷が重い最大の原因。
項目を削らずに負荷だけを消す解法。

**対応:**

- 連携先: Apple Health（HealthKit）、Google Fit / Health Connect を優先。Fitbit・Oura は後続
- 取得項目: 睡眠時間、睡眠の質（取得できる場合）、体重、心拍変動（HRV）、安静時心拍
- 取得した値は「自動取得」であることをUI上で区別表示する（手入力と混ぜない）
- 自動取得された値も **手動で上書きできる** こと
- 連携は任意。未連携でも従来どおり手入力で動く
- HRVは新規項目になるため、分析側の扱いは慎重に。当面は推移の表示のみとし、
  声との相関を語る文章は P0-1 の件数ゲートに従わせる

**受け入れ条件:** 連携をオンにした翌日、睡眠時間と体重が手入力なしで記録に入る。

### 3-3. カレンダー連携

**背景:** 本番・リハ・レッスンの予定は既にユーザーのカレンダーにある。取り込めば「活動内容」の入力自体が不要になる。

**対応:**

- 連携先: Google カレンダー、iCloud カレンダー（CalDAV）
- 読み取り専用。La Voce からカレンダーに書き込まない
- 特定のカレンダー（例:「仕事」）だけを選んで連携できるようにする
- 予定のタイトルからキーワードで種別を推定（本番／公演／ゲネ／リハ／レッスン／稽古 など）。
  推定結果はユーザーが修正できること
- 取り込んだ予定は 3-1 の発声セッションの候補として提示する
  （「今日18:00からリハーサルの予定があります。発声セッションとして記録しますか？」）
- 未来の予定は 3-4 の逆算プランニングの入力になる

**プライバシー上の注意:** カレンダーには声と無関係の私的な予定が含まれる。
取り込む対象カレンダーを絞れること、予定タイトルをサーバに保存しない（またはユーザーが選べる）ことを検討する。

---

### 3-4. 本番日から逆算するプランニング ★

**背景:** 現在の分析はすべて過去形で「こうだった」しか言わない。
声のプロが本当に必要としているのは「3週間後に本番、今どう配分するか」。
「本番ピーキング曲線」という分析は既にあるのに、それを未来に向けて使う導線がない。

**対応:**

- 本番日を登録すると（手動 or カレンダー連携から自動）、そこまでのカウントダウンと配分の目安を表示する
- 表示すべき内容:
  - 本番までの日数
  - 推奨する発声負荷の配分（3-1の実測発声時間ベース。ピーク・テーパリング・当日）
  - 前日の過ごし方の目安（就寝時刻、夕食から就寝までの時間 ※既に記録項目として存在する）
  - 当日のウォームアップ開始時刻の目安（既存の「ウォームアップ効率」の個人平常値から算出）
- 記録が蓄積したら、既存の「本番ピーキング曲線」から得た **その人固有の型** を反映する
  - 蓄積前は一般的な目安であることを明示する（P0-1・P0-2と同じ方針）
- 本番後は EASE（歌いやすさ評価）の記録を促す。ピーキング曲線の精度に直結する
- 配置: 本番が近い期間はホーム（または分析タブ最上部）に常時表示。本番がない期間は非表示

**受け入れ条件:** 本番日を登録すると、その日までの日数と配分の目安が表示される。記録が少ない段階では一般的な目安である旨が明示される。

### 3-5. 対処法ライブラリ

**背景:** 分析は充実しているが出口がない。「悪い」と分かった人が次に何をすればいいかが書かれていない。

**設計方針（開発者指示）: 見やすく、邪魔にならないこと。**
常時表示のコンテンツを増やすのではなく、**必要になった瞬間にだけ出る**形にする。

**対応:**

- 症状・状況をキーにした対処カードのライブラリを持つ
  - 例: 乾燥 / 嗄れ / 痛み / 違和感 / 喉の張り感 / 裏返り / 声の疲労 / 本番前 / 本番後 / 睡眠不足
- 内容の例: 声の休息（vocal rest）の取り方、SOVTE（ストロー発声）などの回復エクササイズ、
  加湿の実務、就寝前の食事タイミング（既存の健康情報の内容と接続）
- **出し方（ここが要件の中心）:**
  - 分析タブや症状カレンダーで該当の症状が検出されたときにだけ、そのカードへの小さなリンクを1行出す
  - 記録画面では出さない（記録のテンポを乱さないこと）
  - ライブラリ全体の一覧は「学ぶ／健康情報」から入れるようにし、トップ階層には置かない
  - モーダルではなくボトムシート等、閉じるのが容易な形式にする
- 1カードは短くする。長文は「学ぶ」の記事へリンクで逃がす
- 医学的助言にならないよう、既存の免責トーンを踏襲する

**受け入れ条件:** 症状が記録されていない日には、対処法への導線がどこにも表示されない。
症状が記録された日にだけ、該当する対処カードへの導線が1行出る。

### 3-6. オフライン記録

**背景:** PWA化済みだが、楽屋・ホール・ツアー先・移動中は電波が悪い。
記録が最も必要な本番期に、記録できない可能性がある。

**対応:**

- Service Worker でアプリシェルをキャッシュし、オフラインで起動できるようにする
- 記録の入力・保存をローカル（IndexedDB）で受け付け、オンライン復帰時に同期する
- 同期待ちの件数をUIに表示する（「未同期 2件」）
- 同期の競合（別端末で同じ日を編集）が起きた場合の解決方針を決めておく。
  推奨: 最終更新時刻が新しい方を採用し、上書きした旨をユーザーに通知する
- CPPS測定はオフラインでも動作すること（端末内計算のため可能なはず）

**受け入れ条件:** 機内モードでアプリを起動し、記録を保存し、オンライン復帰後にサーバへ反映される。

### 3-7. レッスン記録の共有（指導者 → 生徒の一方向）

**背景と設計意図（開発者判断）:**

生徒 → 指導者の方向でレッスン記録を共有する設計は採らない。理由は、
**生徒がレッスン内容を100%正確に理解しているとは限らず、誤解を含んだ記録を指導者が読むと関係性に問題が生じやすい**ため。
そのため共有は指導者 → 生徒の一方向とし、指導者の職務としての側面を強める。

**対応:**

- 指導者が、レッスン後に生徒向けのレッスン記録を書いて共有できる
- 生徒側は閲覧のみ。生徒はこの記録に対して編集・返信をしない
- 内容の想定: 今日扱ったこと、次回までの課題、注意点、声の状態についての指導者の所見
- 生徒の「ノート」タブから閲覧できるようにする（生徒自身の稽古ノートとは別枠で、出所が分かる形にする）
- 生徒側の既存の記録（声の記録・分析）は、これまでどおり生徒が公開範囲を制御する。
  ここは既存の「※生徒が公開範囲を変更・解除すると、この画面の表示もすぐに切り替わります」を維持
- 通知: 新しいレッスン記録が届いたら生徒に通知（LINE連携済みならLINE）

### 4-0. 横断する3原則

改修の判断基準として、以下を全ページに適用する。

1. **「まだ使えないもの」を上に置かない。**
   現在、分析タブにロックカードが5枚連続で上位に並び、学ぶタブに空の章が5つ並んでいる。

2. **設定・説明を、閲覧や入力の流れに割り込ませない。**
   音名ルールの長文、レッスンタブの「表示名」設定、おうちの説明文が該当。
   すべて「？」アイコンの中か、ページ末尾へ。
3. **同じ概念を1箇所に集める。**
   現在4つの概念が分散している:
   発声負荷（分析の最上部と最下部）／ レッスン機能（レッスンタブと「もっと」）／
   メモ（ノートタブと今日の記録の声のメモ）／ 健康記事（学ぶと健康情報）

### 4-1. 分析タブ ★最も問題が大きい

**現在の順序:**

```
1.  ⚠️ 今日の一言（警告）
2.  声の調子スコア（直近2週間・期間固定）
3.  コンディション偏差値（直近8日・期間固定）
4.  回復曲線（叫び・悲鳴）        [ロック]
5.  叫びテイク数の閾値            [ロック]
6.  パッサッジョの安定度          [ロック]
7.  話声位の日内変動              [ロック]
8.  ツアー耐久曲線                [ロック]
9.  分析する期間セレクタ
10. 【声】声の状態の予測 / 声の予報 / 時間帯別 / 声のメモ振り返り / 睡眠時間と質 /
         響きスコア / 声の高さの推移 / ウォームアップ効率 / 音域到達マップ / 症状カレンダー
11. 【身体】体重の推移 / エネルギー可用性 / タンパク質 / 栄養摂取と体重の変化
12. 【メンタル】落ち着き度 / 気持ちタグ
13. 【全体を関連づけた分析】休養方法 / 滞在地 / 発声負荷ACWR[ロック] / 環境の快適帯 /
         本番ピーキング曲線[ロック] / 複数条件の組み合わせ
14. この分析を強くする（声の時差マップ [ロック]）
```

**問題（重い順）:**

**(a) ロックカード5枚が3〜8番目に固まっている**
初めてスクロールした人が最初に出会うのが「まだ使えないもの」5連続。最下部に既に
「この分析を強くする」という置き場所があるので、そこへ全部集約する。

**(b) 期間セレクタが9番目にある**
上の1〜8はセレクタの影響を受けない（声の調子スコアは「直近2週間」固定、偏差値は「直近8日」固定）。
同じ画面に期間の効くカードと効かないカードが混在し、その境界がセレクタの位置という状態。
「期間を1年にしたのに数字が変わらない」という混乱を生む。
→ セレクタを最上部に固定し、期間固定のカードにはその旨をラベル表示する。

**(c) 「睡眠時間と質」が【声】セクションの中にある**
ジャンルが飛んでいる典型。睡眠は【身体】。
しかも【声】内で「声のメモ振り返り」と「響きスコアの推移」の間に挟まっており、
**声の測定値グループ（響き / 声の高さ / ウォームアップ効率 / 音域到達マップ）を分断している。**

**(d) 発声負荷が画面の両端に分かれている**
ACWRパネルは最下部の【全体を関連づけた分析】にあるのに、その結論だけが最上部の「今日の一言」に出ている。
→ 発声負荷は【声】セクションへ移す（声の使用量なので身体でも全体でもない）。

**(e) 【全体を関連づけた分析】が雑多**
「関連づけ」という名前で括られているが、実際は行き場のないものの寄せ集めになっている。
- 環境の快適帯・滞在地 → 【環境】として独立
- ACWR → 【声】へ
- 本番ピーキング曲線 → 【本番】セクションを新設（本番系がロックカードと最下部に散っている）
- 残るのが「複数条件の組み合わせ」だけになり、それこそが本来の「全体を関連づけた分析」

**(f) 「声の状態の予測」と「声の予報」が連続して2つある**
- 前者「前日の夜の過ごし方から、理論的な根拠にもとづいて今日の声の状態を読み解きます」
- 後者「前夜の行動から、今日の喉の状態（1〜5）を数値で予報します」
ユーザーから見て違いが分からない。文章版と数値版なら **1枚のカードに統合**する。

**(g) 【身体】内で体重が2回出る**
体重の推移 → エネルギー可用性 → タンパク質 → 栄養摂取と体重の変化（また体重）。
→ 自然な流れは **摂取（カロリー・タンパク質）→ 結果（体重）→ 統合評価（エネルギー可用性）**。

**推奨する順序:**

```
1.  期間セレクタ（最上部・固定）
2.  今日の一言（データが揃っている警告のみ / P0-2）
3.  サマリー: 声の調子スコア → コンディション偏差値
4.  【声】予測（統合1枚）→ 時間帯別 → 響きスコア → 声の高さの推移 →
        ウォームアップ効率 → 音域到達マップ → 発声負荷ACWR → 症状カレンダー → 声のメモ振り返り
5.  【本番】ピーキング曲線 → ツアー耐久曲線 → 回復曲線（叫び）→ 叫びテイク閾値
6.  【身体】睡眠時間と質 → 摂取（カロリー・タンパク質）→ 体重 → エネルギー可用性
7.  【メンタル】落ち着き度 → 気持ちタグ
8.  【環境】環境の快適帯 → 滞在地
9.  【組み合わせ】複数条件の組み合わせ → 休養方法
10. これから開く分析（ロックカードを全部ここに集約）
```

## 5. 推奨する実装順序

1. **P0-1**（少数データの文言抑制） — 影響範囲が限定的で、信頼への効果が最も大きい
2. **P0-2**（ACWR警告の抑制） — 小さな修正。P0-1と同じ方針
3. **4-1 / 4-2**（分析タブと今日の記録タブの並べ替え） — 表示順の変更が中心でロジックに触れない
4. **3-1 軽量版**（発声セッションの開始/終了ボタン） — 他の分析の土台
5. **P0-3**（書き出し・削除フロー） — バックエンド作業。並行可
6. **3-2 / 3-3**（ヘルスケア連携・カレンダー連携） — 記録負荷の根本解決
7. **3-4**（本番から逆算するプランニング） — 3-1と3-3が入ってから
8. **4-3 / 4-4**（学ぶ・健康情報の整理と統合検討）
9. **3-5**（対処法ライブラリ） — 4-4の統合後の構造に乗せる

## 6. 実装時の注意

- P0-1 と P0-2 は、いずれも **「データが足りないときに何も言わない」** という共通方針の実装。
  指標ごとに「この指標が意味を持つ最小件数」を宣言的に持つ共通レイヤーを作り、表示側がそれを参照する形にすると、
  今後の指標追加時にも同じ問題が再発しない。
- 文言を消すだけにせず、必ず **「あと◯件／◯日で何が見えるか」** に置き換えること。
  既存の段階的アンロックのトーンと揃い、離脱ではなく継続の動機になる。
- 第4章の並べ替えは、多くがコンポーネントの表示順の変更で済む。ロジックに触れる前にここを片付けると、
  以降の機能追加でどこに何を置くかの判断がしやすくなる。
- 新機能（第3章）を追加する際は、第4章で定めたセクション構造のどこに入るかを先に決めること。
  行き場のないものを「全体を関連づけた分析」に足していった結果が、現在の(e)の状態になっている。
