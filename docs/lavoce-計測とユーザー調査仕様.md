## 1. 原則

### 1.1 「行動ログ」と「健康データ」はまったく別物

| | 内容 | 法的な重さ |
|---|---|---|
| **行動ログ** | どの画面を開いたか、記録を完了したか、どこで離脱したか、**どの項目を入れたか** | **軽い。** 健康の値そのものを記録しなければ、要配慮個人情報にあたらない |
| **健康データの集計** | 症状の出現率、スコアの分布、職業別のベンチマーク | **重い。** 統計利用への明示的な同意（`statsUse`）が必要 |

**いま欲しいのは前者です。**
「この機能は使われているか」「どこで諦めるか」を知るのに、健康の値は要りません。

### 1.2 第三者の分析ツールを使わない

健康アプリのイベントを Google Analytics のような外部サービスへ送るのは避けてください。

- GDPR やワシントン州法まわりで面倒が増える
- ユーザーが「健康アプリなのに外部に送っている」と気づいたときの心証が悪い

**自前の `events` テーブルで十分です。** ユーザーが100人を超えるまで、これ以上は要りません。

### 1.3 n が小さいうちは、平均を見ない

ユーザーが5〜20人のとき、**「完了率68%」のような数字はノイズ**です。
1人の行動で10ポイント動きます。

代わりに**個別の軌跡を1人ずつ読む**（管理画面仕様 §3.5）。
**n=20 の平均は無意味ですが、n=20 の個別の物語は金脈です。**

## 2. 今日できること（イベント不要・既存テーブルのみ）

**`events` テーブルを作る前に、いま出せる数字があります。**

### 2.1 項目ごとの入力率 ← 最優先

**このセッションの「項目を減らす」判断は、すべて推測です。**
入力率を出せば、意見が観測に変わります。

仕様は管理画面仕様 §3.3 を参照。**まずこれだけ出してください。**

### 2.2 離脱までの日数

```sql
-- 疑似SQL。実スキーマに合わせて調整
SELECT
  user_id,
  MIN(local_date) AS first_record,
  MAX(local_date) AS last_record,
  COUNT(*)        AS record_days,
  MAX(local_date) - MIN(local_date) + 1 AS span_days
FROM day_records
GROUP BY user_id
ORDER BY last_record ASC;   -- 離脱した人が上に来る
```

`span_days` の分布を見ると、**何日目に落ちるか**が分かります。
3日目に集中しているのか、7日目なのか、14日目なのかで、打ち手が変わります。

### 2.3 記録率の分布

```sql
record_rate = record_days::float / span_days
```

- 記録率が高いまま止まった人 → **飽きたのではなく、理由がある**（引っ越し、本番期間、不調）
- 記録率がじわじわ下がって止まった人 → **入力コストが原因**の可能性が高い

**この2つは対策が正反対です。** 分けて数えてください。

### 2.4 初回記録までの時間

登録から最初の記録までの経過時間。**24時間を超えた人は戻ってこない**傾向が強いので、
オンボーディングの評価指標になります。

## 3. events テーブル

管理画面仕様 §7「第2版」と同一のものです。ここでは定義を詳しく書きます。

### 3.1 テーブル

```ts
interface AppEvent {
  id: string
  userId: string
  name: string                      // §3.2 の15種類のみ
  props: Record<string, unknown>    // ★健康の値を入れない
  at: string                        // UTC
  tz?: string                       // ユーザーのタイムゾーン
  sessionId?: string
  platform?: 'web' | 'pwa'
}
```

インデックス：`(userId, at)` と `(name, at)`。

### 3.2 記録するイベント（15種類まで）

**多く取ると、どれも見なくなります。増やす前にこの表を更新してください。**

```
signup_completed
record_opened          { date, isToday }
record_saved           { fieldsFilled: string[], durationMs, mode, template }
record_abandoned       { lastSection }
voice_entry_added
analysis_opened
analysis_card_viewed   { metricId }
analysis_card_expanded { metricId }
unlock_reached         { level }
notification_clicked   { channel }
install_prompt_shown
install_prompt_accepted
checkout_started
checkout_completed
support_form_submitted
```

### 3.3 鉄則：props に健康の値を入れない

```
✓ record_saved { fieldsFilled: ['bodyFeel','sleep','hydration'], durationMs: 47000, mode: 'quick' }
✗ record_saved { bodyFeel: 2, symptoms: ['乾燥'] }
```

**`fieldsFilled` は項目名の配列であって、値ではありません。**
この線を守れば、行動ログは要配慮個人情報になりません。

**実装時のレビュー観点にしてください。**「便利だから」と値を入れたくなります。

### 3.4 `record_abandoned` の取り方

離脱の把握はこのイベントが要です。

- 記録画面を開いたまま**保存せずに離れた**とき（`visibilitychange` / `beforeunload`）
- `lastSection` は、**最後にフォーカスまたはスクロールで到達したセクション名**
- 送信は `navigator.sendBeacon` で（離脱時に確実に飛ばすため）

### 3.5 保持期間

行動ログは**13か月で削除**してください。それ以上持つ理由がありません。
削除ジョブを最初から入れておくこと。

## 4. アプリ内マイクロ調査

**会えない相手から「なぜ」を聞く、最も効率のよい手段です。**
面談の約束より回答率が桁違いに高い。

### 4.1 設計の鉄則

1. **1問だけ。** 2問目を足した瞬間に回答率が落ちます
2. **スキップを同じ大きさで置く**
3. **一度出したら、二度と出さない**
4. **記録の保存が完了した直後に出す**（記録の途中に割り込まない）
5. **解約を止めるために使わない**（§4.4）

### 4.2 データ

```ts
interface SurveyResponse {
  id: string
  userId: string
  surveyKey: string       // 'day7_want' | 'churn_reason'
  choice?: string         // 選択肢のキー
  freeText?: string       // 自由記述（任意）
  at: string
}

interface SurveyShown {
  userId: string
  surveyKey: string
  shownAt: string
  answered: boolean       // スキップの把握に使う
}
```

**`SurveyShown` を必ず持ってください。** 「出したが答えなかった」を数えないと、
回答の偏りが分かりません。

### 4.3 調査1：7日目の1問

**トリガー**：通算の記録日数が7日に達した日の、記録保存の直後。

```
┌───────────────────────────────┐
│ 7日間の記録、ありがとうございます │
│                               │
│ いま、いちばん知りたいことは？   │
│                               │
│ ┌───────────────────────────┐ │
│ │ 喉が不調になる原因          │ │
│ ├───────────────────────────┤ │
│ │ 本番に合わせる方法          │ │
│ ├───────────────────────────┤ │
│ │ 長期的な変化                │ │
│ ├───────────────────────────┤ │
│ │ その他                     │ │
│ └───────────────────────────┘ │
│                               │
│ ［ あとで ］                   │
└───────────────────────────────┘
```

「その他」を選んだときだけ、自由記述欄を出す。

**この1問で、指標設計の3層（朝30秒／週次の発見／本番）のうち
どれに需要があるかが分かります。** 実装の優先順位が変わる可能性があります。

### 4.4 調査2：解約時の1問

**引き止め画面にしないこと。** 解約を**確定させた後**に出します。

```
┌───────────────────────────────┐
│ 解約が完了しました              │
│ 8月31日までご利用いただけます    │
│                               │
│ 差し支えなければ、理由を         │
│ 教えていただけますか            │
│                               │
│ ・使う時間がなかった            │
│ ・入力が大変だった              │
│ ・欲しい情報が得られなかった      │
│ ・料金が見合わなかった          │
│ ・一時的に休むだけ              │
│ ・その他                       │
│                               │
│ ［ 回答せずに閉じる ］          │
└───────────────────────────────┘
```

**「一時的に休むだけ」を必ず選択肢に入れてください。**
声のプロは繁忙期と閑散期の差が大きく、これが相当な割合を占めるはずです。
これを「解約＝失敗」と数えると、判断を誤ります。

### 4.5 自由記述の扱い（注意）

**自由記述には健康情報が書かれることがあります**（「喉を痛めて休業したので」など）。

- `statsUse` の同意対象とは**別管理**にする
- **統計タブに出さない。公開・共有もしない**
- 管理画面では本文を読んでよい（運営者のみ）が、**エクスポート機能を作らない**
- プライバシーポリシーの利用目的に「お問い合わせ・アンケートへの対応」を含める

## 6. Instagram での調査（レーンB・坂本さん）

**心理的ハードルが最も低い調査手段です。** しかも「いま、育てています」の投稿を
したばかりなので、文脈が噛み合っています。

**ストーリーズのアンケート機能（2択）**

> 声の調子が悪くて、仕事に影響が出たことはありますか？　［ある／ない］

**ストーリーズの質問スタンプ（自由記述）**

> そのとき、原因は何だったと思いますか？

> 声のことで、いま一番知りたいことは何ですか？

**匿名で答えられるので、面と向かっては言いにくいことが出てきます。**
「本番で声が出なくて代役を立てた」のような話は、対面では聞けません。

週に1問、続けてください。回答は**そのまま書き写して保存**すること
（要約すると、言葉のニュアンスが失われます）。

## 7. ヒアリングの進め方（レーンB・坂本さん）

**オンライン通話30分で十分です。** 会う必要はありません。

### 7.1 やってはいけないこと

- ❌ **機能を説明して「便利そうですか」と聞く** → 全員「便利そう」と答えます
- ❌ **「〜だったら使いますか」** → 未来の行動の予測は、ほぼ当たりません
- ❌ **自分の仮説を先に言う** → 相手が合わせてくれてしまいます

**製品を見せるのは、最後の5分だけ。** それも「感想」ではなく
**「どこで手が止まったか」「何を質問したか」**を記録します。

### 7.2 質問スクリプト（30分）

**導入（2分）**

> 今日は製品の説明ではなく、お仕事の話を聞かせてください。
> 正解はないので、思ったままで大丈夫です。録音してもよろしいですか。

**過去の出来事（12分）← ここが本体**

> 直近で、喉や声の調子が原因で仕事に影響が出たのは、いつごろですか。

> そのとき、具体的に何が起きましたか。
> （何日前から兆候があったか／どんな症状か／どう対処したか）

> 原因は何だったと思いますか。

> あとから振り返って「あのとき、こうしていれば」と思うことはありますか。

**現在の行動（8分）**

> いま、体調について何か記録していますか。
> — している場合：何を、どこに、どのくらい続いていますか
> — していない場合：過去に試したことはありますか。なぜ続かなかったと思いますか

> 本番前の1週間、いつもと変えている習慣はありますか。

**指導者にだけ（5分）**

> レッスンの冒頭で、生徒の状態をどうやって把握していますか。

> 生徒が自分からは言わないけれど、知りたいことはありますか。

> もし生徒の記録を見られるとしたら、何を見たいですか。

**閉じ（3分）**

> 最後に、声のことでいま一番困っていることは何ですか。

### 7.3 記録の仕方

- **印象ではなく、発言をそのまま書き留める**
- 3人終わったら、**共通して出てきた言葉を数える**
  （「乾燥」「寝不足」「前日の飲み会」など。頻度がそのまま優先順位になります）
- **仮説が外れた箇所を、明示的に記録する。** それが一番価値のある情報です

### 7.4 何人聞けばよいか

**3〜4人で十分**です。同じ話が2回出てきたら、それは傾向です。
5人目以降は新しい情報がほとんど出なくなります。

## 9. Sonnet 5 への依頼のコツ

- **§3.3 の鉄則を、レビュー観点として毎回渡す。**
  `props` に健康の値を入れさせない
- **イベントを15種類から増やさせない。** 増やす提案が来たら、
  代わりに何を削るかを一緒に出させること
- **マイクロ調査を2問にさせない。** 1問だけ、スキップは同じ大きさ
- **解約アンケートを引き止め画面にさせない。** 解約確定後に出す
- `SurveyShown`（出したが答えなかった記録）を省略させない（§4.2）
- **レーンB（§6 §7）には手を出さない。** Instagram の投稿文案や
  ヒアリングの代行を提案しないこと
