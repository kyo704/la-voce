# La Voce ／ 教室運営の範囲・カレンダー書き出し・振替

**Claude Sonnet 5 へ。この文書は2つのことを決めます。**

```
① La Voce が「作るもの」と「作らないもの」の境界（§1〜§2、§7）
② レッスン予定を、ユーザーの本命カレンダーに自動で流す仕組み（§3）
```

読む順番：**統合実行ルート v4** → 本書 → カレンダー連携パッチ → 教室プラン仕様。

**§7 の「作らないもの一覧」は、実装中に何度も読み返してください。**
そこに並んでいるものは、どれも「あったほうが親切に見える」機能です。
だからこそ、理由と一緒に書いてあります。

---

## 0. 結論

```
① La Voce の柱は2本。
   ・声で仕事や勉強をする個人が、声を記録し・理解し・守ること
   ・教室が、レッスンという事業を回すこと
   この2つのどちらにも当てはまらない機能は、作らない。

② 汎用カレンダーにはならない。
   ★ユーザーの予定を「読み込む」のではなく、
     La Voce のレッスンを「書き出す」。方向が逆。

③ 教室運営の本丸は振替レッスン。教師間チャットより先に効く。

④ 月謝は「記録」する。「決済」はしない。
```

---

## 1. 二本柱と判断基準

機能を足すかどうか迷ったら、この2つで判定してください。

```
① その人が、声を記録し・理解し・守ることを助けるか
② 教室が、レッスンという事業を回すことを助けるか
```

**どちらかに当てはまれば検討してよい。両方外れたら作らない。**

そして、当てはまっていても**次の2つに引っかかるものは作りません。**

```
✗ 個人の私生活に踏み込むもの
✗ 既存の道具に勝てないもの（汎用カレンダー、汎用チャット、汎用メモ）
```

2つ目は既に一度使っている基準です。
教師間コミュニケーション仕様で「すべてのスレッドは何かに紐づく」と決めたのは、
**紐づかない雑談チャットでは LINE と Slack に勝てない**からでした。

---

## 2. 予定の3分類

```
○ 教室という事業の予定
    発表会、教室の休講日、試験、年間スケジュール、講師会議
    → ★La Voce が持つ。これは教室運営そのもの

○ 声に関わる個人の予定
    レッスン、本番、オーディション、録音、リハーサル
    → ★La Voce が持つ。負荷モデルの入力でもある

✗ 個人の私生活の予定
    歯医者、会議、旅行、飲み会、家族の用事
    → ★La Voce は持たない。1件も保存しない
```

**3つ目を持たないための道具が、既に設計済みの freeBusy です。**
予定の中身は読まず、空いているかどうかだけを見る。
**権限で隠すのではなく、取得しないことで守る。**

「昨日お酒を飲んだ」は**記録**として持ちます。**予定**としては持ちません。

## 3. ★レッスン予定を本命カレンダーへ書き出す

### 3-1｜方向を間違えないこと

```
✗ ユーザーのカレンダーを La Voce に取り込む
○ La Voce のレッスンを、ユーザーのカレンダーに送り込む
```

**ユーザーのカレンダーは、これまでどおり1つのままです。**
そこにレッスンが並ぶだけで、二重入力の面倒は消えます。
そして La Voce は、他人の予定を1件も保存しません。

### 3-2｜3つの方式。既定はB

**A｜単発の .ics ダウンロード（「カレンダーに追加」ボタン）**

```
・追加の権限が一切不要。どのカレンダーアプリでも動く
・実装が最も小さい
・★変更が伝わらない（追加した時点のコピーになる）
→ Bが使えない環境のための保険として、必ず用意すること
```

**B｜ICS購読フィード（webcal:// / https:// の購読URL）★これを既定にする**

```
・一度登録すれば、以後は自動で追随する
・追加の権限が不要。Google 認証も不要
・実装は「ICSを吐くエンドポイント」1つ
```

**★ただし更新間隔に重大な制限があります。**

```
Google カレンダーの購読フィード更新間隔：8〜24時間。★ユーザーは変更できない
Apple カレンダー：ユーザーが設定可能（最短5分）
```

**つまり Google では、当日の変更が届きません。**
この制限は回避できないので、**設計で受け止めます。**

```
★カレンダーは「予定の器」であって、「連絡手段」ではない。

  ・休講、時間変更、遅刻、教室変更 → ★レッスン連絡パッチの定型連絡で送る
  ・カレンダーは、確定した予定が最終的に載る場所

  この分担を、UI の文言でもユーザーに伝えること。
  「カレンダーへの反映には最大24時間かかることがあります」と購読画面に明記する。
```

**C｜Google Calendar API で直接書き込む（将来）**

```
・即座に反映される。理想的
・★専用スコープと Google の審査（verification）が必要
・★スコープ要件は変わるので、着手前に必ず最新の公式ドキュメントを確認すること
  （私の知識で断定しないこと）
・審査が通るまで公開できなくなるリスクがあるため、G4 では着手しない
```

**実装順は B → A →（必要なら）C です。**

### 3-3｜★フィードURLの安全性

購読URLは**認証なしでアクセスされます。**カレンダーアプリはログインできません。
つまり**URLを知っている人は誰でも中身を見られます。**

```
・URLに、推測不可能な長いトークンを含める（128bit以上の乱数）
・トークンはユーザーごと・役割ごとに発行する
・★「URLを再発行する」ボタンを必ず用意する（漏れたときの唯一の対処）
・退会・卒業・担当解除で、トークンを即座に無効化する
   → 共有解除の即時反映（統合実行ルート §3 ガードレール）と同じ扱い
・アクセスログを取る（いつ・どのUAが取得したか）。IPは保存しない
```

### 3-4｜★フィードに何を書くか

**ここが最も慎重を要する部分です。URLが漏れた場合に何が漏れるかを決めています。**

```
入れる
  ・日時（開始・終了）
  ・タイトル
  ・場所（教室名まで）

★入れない
  ・健康に関するデータを1文字も入れない（声の調子、周期、体調、questionnaire）
  ・レッスンの内容・メモ・振り返り（レッスンモードの解体.md §5）
  ・欠席理由
  ・生徒や講師の連絡先
  ・振替の交渉状況
  ・URLトークン以外のID
```

**タイトルの既定**

```
生徒側のフィード   「レッスン（田中先生）」
講師側のフィード   「レッスン（山田さん）」
```

**★教室の設定で、氏名を出さない形にも切り替えられること。**

```
「レッスン」のみ    ← 氏名を一切出さない
```

講師が家族とカレンダーを共有している場合があります。
**生徒の氏名が家族に見えるのは、避けられるようにしてください。**

### 3-5｜ICS の技術的な注意

```
・UID はレッスンごとに安定させる（再生成のたびに変えない）
・変更時は SEQUENCE をインクリメントする
・★キャンセルは VEVENT を消すのではなく、
  STATUS:CANCELLED にして30日間残す
  → 消すだけだと、一部のクライアントで古い予定が残り続ける
・DTSTART / DTEND は TZID 付き。★UTC固定にしない
・ユーザーのタイムゾーン設定に従う（Asia/Tokyo を決め打ちしない）
・X-WR-CALNAME に「La Voce レッスン」を入れる
・キャッシュヘッダは短めに（Cache-Control: max-age=300）
```

### 3-6｜画面

```
設定 › カレンダー
├─ レッスンをカレンダーに表示する
│   [ 購読URLをコピー ]  [ 手順を見る ]
│   ※ Google カレンダーでは反映に最大24時間かかることがあります
│   ※ 休講・時間変更のお知らせは、アプリの連絡で届きます
├─ 予定の書き方
│   ○ レッスン（山田さん）   ● レッスン
└─ [ URLを再発行する ]
    ※ これまでのURLは使えなくなります
```

**手順は、Google / Apple / Outlook の3つ分を用意してください。**
購読の登録方法はアプリごとに全く違い、ここで確実に脱落します。

## 4. ★振替レッスン（教室運営の本丸）

### 4-1｜なぜこれが最優先か

音楽教室・声楽教室の運営で、いちばん時間を食っているのが振替です。

```
生徒が休む → 別の日に振り替える → 先生の空きを探す
→ 他の生徒とぶつかる → 月謝の消化回数が合わなくなる
```

ほとんどの教室が、これを LINE と紙とエクセルでやっています。

**そして La Voce には、必要な部品がもう揃っています。**

```
担当関係（Assignment）      … 教室プラン仕様
レッスン日程と重なりの検出   … 教室プラン仕様
freeBusy による空き判定      … カレンダー連携パッチ
定型連絡（休みます／変更）   … レッスン連絡パッチ
```

**新しく作るのは、この上に乗る流れだけです。**

**教室プラン ¥12,800 の価格を正当化するのは、たぶん振替です。**
教師間チャットより先に効きます。

### 4-2｜流れ

```
① 生徒が「休みます」を送る（定型連絡。★理由は聞かない）
② 振替の対象かどうかを、教室のルールで自動判定
③ 対象なら、担当教師の空きから候補日を3件出す
   ・教師の既存レッスンと重ならない
   ・教師の freeBusy で空いている
   ・生徒の freeBusy で空いている（連携している場合のみ）
④ 生徒が1つ選ぶ
⑤ 教師が承認 → 確定 → レッスンが作られ、消化回数が更新される
⑥ カレンダーのフィードに反映（§3-2 の遅延に注意）
```

**★②〜③を自動化することが価値の中心です。**
候補日を人間が探すのをやめさせるのが目的で、
「振替の記録を残す」ことが目的ではありません。

### 4-3｜★欠席理由を聞かない

レッスン連絡パッチ §4-2 と同じです。

```
「体調不良のため」を選ばせると、健康情報を教師に渡すことになります。
★理由の選択肢を作らないでください。「休みます」だけで足ります。
```

教室のルール上、当日欠席と事前連絡を区別する必要はありますが、
それは**理由ではなく、連絡した時刻**で判定できます。

### 4-4｜教室ごとのルール

```
interface MakeupPolicy {
  orgId: string
  enabled: boolean
  deadlineHours: number      // 何時間前までの連絡なら振替可（例: 24）
  validWithinDays: number    // 振替の有効期限（例: 60日 / 当月内なら31）
  maxPerTerm: number         // 期間内の振替回数の上限
  carryOver: boolean         // 未消化を翌月に繰り越すか
}
```

**既定値は控えめに。**教室ごとに運用が全く違うので、
**La Voce が「正しい振替ルール」を決めないでください。**

### 4-5｜データモデル

```ts
interface MakeupRequest {
  id: string
  orgId: string
  enrollmentId: string
  originalLessonId: string
  requestedAt: string
  status: 'pending' | 'offered' | 'chosen' | 'confirmed' | 'expired' | 'declined'
  offeredSlots?: { startAt: string; endAt: string; teacherId: string }[]
  chosenSlot?: { startAt: string; endAt: string; teacherId: string }
  newLessonId?: string
  // ★理由のフィールドを作らない
}

interface LessonQuota {
  enrollmentId: string
  termStart: string
  termEnd: string
  plannedCount: number
  completedCount: number
  makeupUsed: number
  carriedOver: number
}
```

### 4-6｜通知

**レッスン連絡パッチの枠組みをそのまま使ってください。**
新しい通知の仕組みを作らないこと。

```
・22:00〜08:00 は送らない
・候補日の提示、確定の連絡は定型文
・★自由記述の交渉欄を作らない（生徒が関わるため）
   → 話し合いが必要なら、教師間スレッド（G5）か、教室の外でやること
```

## 5. 月謝は記録する。決済はしない

```
○ 作る    誰が・いつ・いくら払ったかの記録（台帳）
          未納の一覧、月ごとの集計、領収の記録

★作らない 決済の代行、クレジットカードの処理、口座振替、
          返金処理、La Voce を経由した送金
```

**この線を越えると、規制も責任もまったく別の世界になります。**
個人開発の範囲を大きく超え、公開そのものが遅れます。

**台帳だけでも、教室の事務は十分に楽になります。**
決済は、教室が既に使っている手段（銀行振込、現金、既存の決済サービス）のままで、
La Voce はその結果を記録するだけにしてください。

**★金額を扱う以上、監査ログ（A-5）の対象に含めること。**

## 6. 実装順（G4 に追加、14日）

```
Day 1-3    §3-2 B  ICS購読フィード（トークン・再発行・無効化を含む）
Day 4      §3-2 A  単発 .ics ダウンロード
Day 5      §3-6    設定画面と、Google / Apple / Outlook の手順
Day 6-10   §4      振替（ポリシー・候補日算出・承認・消化回数）
Day 11-12  §5      月謝の台帳
Day 13-14  テスト
```

**テストで必ず確認すること**

```
□ フィードURLに健康データ・メモ・欠席理由が1文字も含まれない
□ 「レッスン」のみ設定のとき、氏名がフィードに含まれない
□ URLを再発行すると、古いURLが 404 になる
□ 担当を解除した講師のフィードから、その生徒のレッスンが即座に消える
□ レッスンをキャンセルすると、STATUS:CANCELLED で残る（消えない）
□ タイムゾーンが Asia/Tokyo 以外のユーザーで、時刻がずれない
□ 当日欠席（deadlineHours 内）が振替対象にならない
□ 候補日に、教師の既存レッスンと重なる時間が出ない
□ ★MakeupRequest に理由を保存するフィールドが存在しない
□ 月謝の記録の変更が、監査ログに残る
```

## 7. ★作らないもの一覧（却下済み・理由つき）

**実装中に思いついても、作らないでください。**
どれも一度検討して、理由があって外したものです。

| 作らないもの | 理由 |
|---|---|
| **汎用カレンダー**（私生活の予定の登録） | 一人一つしか使われない領域。二番目に良いカレンダーは使われない。freeBusy で守った線を自分から越えることになる |
| **ユーザーのカレンダーの取り込み** | 予定の中身を DB に持つことになる。教室にはオーナーがいる |
| **1時間のレッスン録音** | 先生の声が入る／要配慮個人情報が確実に混入／保存が持たない／聴き返さない（レッスンモードの解体 §2） |
| **動画の姿勢・口の形の自動評価** | 科学的根拠が弱く、先生の指導と矛盾したときに生徒が壊れる（同 §4） |
| **レッスン中に生徒が操作する機能** | 手と意識が空いていない。先生の前でスマホを触らせると流通経路が壊れる（同 §1） |
| **基礎体温** | 妊活の道具として認識される。排卵日予測を必ず求められ、それは医療機器の線（周期記録 付録A-4） |
| **毎日の体調指数・アドバイス** | 3ゲートを構造的に通せない。白米の例と同じ（同 A-5） |
| **排卵日・妊娠しやすい日** | プログラム医療機器に該当し得る（同 §8） |
| **生徒 → 先生 の自由記述** | 未成年保護。定型連絡で足りる（レッスン連絡パッチ §4-1） |
| **教師どうしのDM** | 教室の外に出る話は教室の外で。記録が残らない場所を作らない（教師間コミュニケーション §3-4） |
| **スレッドへの画像添付（v1）** | 分析画面のスクショで、健康データの共有範囲が迂回される（同 §3-2） |
| **決済の代行** | 規制と責任が別世界。台帳で足りる（本書 §5） |
| **既読表示** | 生徒に「読んだのに返さない」という圧力を作る（レッスン連絡パッチ §5-3） |
| **欠席理由の選択** | 要配慮個人情報。連絡時刻で運用は回る（本書 §4-3） |
| **記録の催促** | 続かない人ほど催促で離れる（レッスンモードの解体 §11-13） |

**新しく「作らない」と決まったものは、この表に追記してください。**
**表が増えることは、設計が進んでいることです。**

## 8. Sonnet への依頼のコツ

**この文書で最も間違えやすいのは、§3 の方向です。**

「カレンダー連携」と書いてあると、
**ユーザーのカレンダーを読み込む実装を書き始めてしまいます。**

```
★読むのは freeBusy だけ。予定の中身は取得しない。
★書き出しは一方向。La Voce → ユーザーのカレンダー。
```

**迷ったときの基準は3つです。**

```
① それは、声か、教室の事業か、どちらかを助けますか？
   → どちらでもないなら、作らない。

② その情報は、URLが1つ漏れただけで人に見られてよいものですか？
   → いいえ なら、フィードに入れない。

③ 既存の道具（Googleカレンダー、LINE、銀行）に勝てますか？
   → いいえ なら、勝とうとせず、つなぐ。
```
