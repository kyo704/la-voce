### 3. 更新の側を直す（4表・1本の移行で）

下書き：`supabase/migration_fix_link_update_columns.sql`

★**各表の「アプリが `update` で送る列」は、コードで確定済みです。**

| 表 | 送る列 | 守る列 |
|---|---|---|
| `teacher_student_links` | `status` / `revoked_at` / `revoked_by` | `teacher_id` / `student_id` |
| `assignments` | `ended_at` | `org_id` / `teacher_id` / `student_id` |
| `org_events` | `event_date` / `previous_date` / `withdrawn_at` / `updated_at` | `org_id` |
| `lessons` | `held` | `link_id` / `org_id` / `teacher_id` / `student_id` |

**層1（権限）** ★これは `WITH CHECK` の全文を知らなくても書けます。
```sql
revoke update on public.<表> from authenticated, anon;
grant update (<上の「送る列」>) on public.<表> to authenticated;
```

**層2（`WITH CHECK`）** ★いまの全文が要ります。要約から書き起こさないこと。
```sql
and <守る列> = coalesce(
      (select t.<守る列> from public.<表> t where t.id = <表>.id),
      <守る列>)
```
★**`coalesce` を忘れないこと。** `ALL` のポリシーは `INSERT` にも効きます。
`insert` のとき副問い合わせは `null` を返すので、★**`coalesce` が無いと `insert` が全部止まります。**
★`for update` だけのポリシー（`teacher_student_links`）には要りません。

**層3（値の制約）** ★`teacher_student_links` は**すでに入っています**
（`status` は3値、`revoked_by` は2値の `CHECK`）。ほかの表は未確認。

★**時間が足りなければ、層1だけを4表に当ててください。**
★それだけで、身元の書き換えは止まります。層2は2枚目の板です。
