## 1. なぜ今これを書くのか

EU の医療機器規則（MDR）では、**医療目的を持つソフトウェアは医療機器**になります。
そして規則11によって、その多くがクラスIIa以上に分類され、
**認証機関（notified body）の審査**が必要になります。

**1人の開発者には不可能です。費用も期間も桁が違います。**

つまり **EU 展開が成立する道は1つしかありません。**

```
★医療目的を持たない製品として入る。
```

そして La Voce は、すでにそう作られています。

```
・診断しない
・リスクを表示しない
・文献の閾値を判定に使わない
・3ゲートを通らなければ文章を出さない
・排卵日を予測しない
・「逆流性食道炎の疑い」と書かない
```

**「判定しない」という設計思想が、そのまま EU への入場条件です。**

**この一貫性が1か所でも破れると、EU の扉が閉じます。**
そして破れるのはたいてい、**善意で追加された1行の文言**です。

## 2. ★文言（いちばん重要）

### 2-1｜監査の対象は、アプリの中だけではない

MDR は、製造者が表明した**意図された目的（intended purpose）**で判断します。
そこには**広告や説明文も含まれます。**

**★次を全部、監査の対象にしてください。**

```
□ アプリ内のすべての文言（全言語）
□ 学ぶ記事の見出しと本文
□ ★アプリストアの説明文・スクリーンショットの文字
□ ★ランディングページ（la-voce の公開ページ）
□ ★利用規約とプライバシーポリシー
□ 通知の本文
□ 共有カードに焼き込まれる文字
□ メールの文面
```

**アプリの中だけ綺麗にしても、ストアの説明文に「声の不調を早期発見」と
書いてあれば、それが意図された目的になります。**

### 2-2｜言ってはいけない表現

**機能や製品の説明として、次の意味を持つ表現を使わないでください。**

```
✗ 診断する／判定する／見つける／発見する
✗ 治す／改善する／予防する／防ぐ
✗ 病気・疾患・症状を「検出する」
✗ スクリーニング
✗ 医師の代わりに／受診の必要性を判断する
✗ 「異常」「正常」「基準値」「正常範囲」
✗ リスクが高い／低い
```

**言ってよい表現**

```
○ 記録する／残す／並べる／振り返る
○ あなたの記録から見えた傾向
○ 参考のための指標
○ 医学的な判断ではありません
```

**★病名そのものは、学ぶ記事の中で「説明」として書くのは構いません。**
禁止されるのは、**機能が病気を見つける／管理すると言うこと**です。

```
○ 学ぶ記事「声がかれる原因のひとつ ― 胃からの逆流」（説明）
✗ 機能名「逆流性食道炎チェック」（検出を示唆）
```

### 2-3｜言語ごとに用意する

**日本語の禁止語リストを機械翻訳しないでください。**
言語ごとに、その言語の医療表現で作ります。

```
英語   diagnose / detect / screen / treat / prevent / disorder / abnormal / normal range
ドイツ語 Diagnose / erkennen / Behandlung / vorbeugen / Krankheit / normal / Normbereich
イタリア語 diagnosi / rilevare / trattamento / prevenire / malattia / normale / valori normali
```

**「作業指示-多言語対応の完成.md」§7 の
「言語ごとの禁止語の CI テスト」を、そのまま EU 用に拡張してください。**
あれは日本の在住外国人のための機能でしたが、**EU の防御そのものです。**

### 2-4｜いま G3-18 でやること

```
□ 禁止語の CI テストを作る（★まず日本語と英語）
□ ★対象にアプリ内の文言だけでなく、ランディングページと
  ストア説明文のテキストファイルも含める
□ 新しい文言を足したときに、CI が落ちる状態にする
□ ドイツ語・イタリア語のリストは、EU 着手時に追加する（今は枠だけ）
```

## 3. ★同意（G3-15 で作り込む）

### 3-1｜「得た」だけでは足りない

GDPR は、**同意を得たことを証明できる**ことを求めます（第7条1項）。
「同意画面を出した」では不十分で、**誰が・いつ・何に・どの文言で**が要ります。

### 3-2｜記録する内容

```ts
interface ConsentRecord {
  id: string
  userId: string
  purposeKey: string      // 'health.record' | 'health.cycle' | 'health.reflux' など
  policyVersion: string   // 'ja-2026-08' のような版
  textHash: string        // ★そのとき表示した文言のハッシュ
  locale: string          // 表示した言語
  method: 'checkbox' | 'button'
  grantedAt: string
  withdrawnAt?: string    // ★撤回も記録する。行を消さない
  ip?: never              // ★IPは保存しない
}
```

**★`textHash` を省略しないでください。**
文言を改訂したあと「あの人は何に同意したのか」を答えられなくなります。

**★撤回した行を削除しないでください。**
「撤回した」という事実の記録が要ります。

### 3-3｜同意の取り方

```
・★目的ごとに分ける（記録全体・周期・食事と就寝を、別々に）
・★まとめて1つのチェックにしない
・★既定でオンにしない
・撤回が、同意と同じ手軽さでできること（第7条3項）
・撤回しても、それまでの記録は消えない（消すのは削除機能の役目）
```

### 3-4｜いま G3-15 でやること

```
□ 上の ConsentRecord をそのまま作る（EU 用に作り直さなくて済む）
□ 目的ごとに分けた同意にする
□ 撤回の導線を設定に置く
□ 文言の版とハッシュを保存する
```

**日本の要配慮個人情報の同意も、この形で足ります。**
**★EU 用に別の仕組みを作らないでください。1つで両方を満たします。**

## 4. ★データの置き場所

### 4-1｜いまは日本1つでよい

EU 展開時には、**EU 域内にデータを置ける形**が要ります。
ただし今から2つ運用する必要はありません。

**必要なのは「あとで分けられること」だけです。**

### 4-2｜そのために、作ってはいけないもの

```
✗ 全ユーザー横断のランキング・順位表
✗ 全ユーザーの統計を1つのテーブルに集約する仕組み
✗ 「みんなの平均」を出す機能
✗ 地域をまたぐ結合を前提にした集計
```

**★これらを作ると、データベースを分けた瞬間に壊れます。**

そして幸いなことに、**これらは既に別の理由で禁止されています。**
管理画面の k匿名化（n<5 を出さない）と、
「羊は記録した行為に反応し、記録の中身には反応しない」という規則です。

**同じ規則が、EU 展開の前提条件にもなっています。**

### 4-3｜持っておく列

```ts
interface UserRegion {
  userId: string
  dataRegion: 'jp' | 'us' | 'eu'   // ★今は全員 'jp'
}
```

**今すぐ使わなくても、列だけ作っておいてください。**
あとから全ユーザーに付与するより、最初からあるほうが安全です。

## 5. 自動的な決定をしない（第22条）

GDPR 第22条は、**個人に重大な影響を与える自動的な判定**を制限します。

**La Voce は、すでにこれを避けています。**

```
・3ゲートを通らなければ文章を出さない
・「あなたは◯◯の疑いがあります」を出さない
・スコアに合否や判定を付けない
・受診を勧めない
```

**★この設計を、EU のためにも維持してください。**
特に、将来「AIが助言する」機能を思いついたときに、この条文を思い出すこと。

## 6. 書き出しと削除（第20条・第17条）

**G3-16・G3-17 で作るものが、そのまま EU の要件を満たします。**

```
書き出し（第20条 データポータビリティ）
  □ 機械可読な形式（JSON か CSV）
  □ ★構造化されていること（画面の見た目ではなく、データとして）
  □ ★支払いの有無にかかわらず無料
  □ 同意の記録も含める

削除（第17条 消去権）
  □ 本人の操作で完結する
  □ ★削除の完了を確認できる
  □ バックアップからの消去方針を書いておく
  □ 法令上残す必要がある記録（監査ログ）は、その旨を明示する
```

**★書き出しをプレミアム機能にしないこと。** 法定の権利です。
（作業指示-課金の器と無料枠.md §3 と同じ規則）

## 8. 3年後の入り方（参考・実装しない）

### 8-1｜国

```
イタリア・ドイツ・オーストリアの3か国から。
理由：職業歌手の密度が最も高く、音名の対応（H/B と Do-Si）が済んでいて、
　　　3言語で足りる。24言語は要らない。
```

### 8-2｜経路

```
★個人からではなく、機関から。
  歌劇場の合唱団   1団体に40〜80人の職業歌手
  音楽大学の声楽科 1校に数十〜百数十人
```

**教室プランがそのまま当てはまります。**
そして**データ主体が数十万人ではなく数百人**なので、
消費者向けに広く展開するより、法的な負担がはるかに軽くなります。

### 8-3｜文化的な注意

**声楽の伝統がある国ほど、教師の権威が強い**です。
「アプリが先生の指導に口出しする構造を作らない」という規則
（レッスンモードの解体.md §4-2）は、**EU ではさらに強く効きます。**

## 11. Sonnet への依頼のコツ

**この文書は「EU の作業をしてください」という文書ではありません。**
**「いまの作業を、あとで壊れない形でやってください」という文書です。**

実装中に、次を思いつくはずです。

```
・「あなたの声は同年代の平均より…」（全ユーザー統計）
・「声の不調を早期に見つけましょう」（ストアの説明文）
・「AIがあなたに合った練習を提案します」（自動的な助言）
・同意を1つのチェックにまとめて、登録を短くする
```

**4つとも、EU の扉を閉じます。**
どれも「親切」と「使いやすさ」から出てきます。

**迷ったときの基準は1つです。**

```
★その表現は、この製品に「医療の目的」があると読めますか？
　→ 読めるなら、書かない。
```
