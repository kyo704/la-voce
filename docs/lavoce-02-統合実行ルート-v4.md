## 2. ★ 評価が決まるのは4つの瞬間です

**「10/10」は、機能の数では作れません。** 次の4つの瞬間のどれかで落ちると、
他が満点でも評価は上がりません。**逆に、この4つを通せば10/10になります。**

### 瞬間①｜開いてから60秒（「わかってる人が作った」と伝わるか）

**声のプロは、最初の1分で見抜きます。**

```
✅ 「地声で記録してください（裏声ではなく）」
✅ 「国際式・ヤマハ式のズレ」の注意書き
✅ 絶対湿度で環境を見ている
✅ パッサッジョ・テッシトゥーラという語を、説明なしで使っている
```

**これは既にあります。守ってください（§3）。**
**足りないのは、それを最初の60秒で見せることです。**
オンボーディングの最初の画面に、「なぜ地声なのか」を1行入れてください。

### 瞬間②｜初めて保存した直後（何か返ってくるか）

**いまは、保存しても何も起きません。ここが最大の取りこぼしです。**

分析の本領（発見カード）は14日ぶんのデータを要します。
**つまり新規ユーザーは、入れても何も返ってこない2週間を通過します。**

**その2週間を支えるのは、分析ではありません。**

```
睡眠を入れる    → 「14日平均より +0.3時間」
活動を入れる    → 「今週の発声負荷 1.12（ちょうどいい）」
保存を押す      → 「＋3pt ・ 6日つづいています ・ 今日わかったこと」
```

**入れた瞬間に返ってくること。** これが「使い続けられるアプリ」と「3日でやめるアプリ」を分けます。

### 瞬間③｜初めての「発見」（嘘をついていないか）

**ここが、改善タスク指示書 P0-1 が指摘した場所です。**

> 良い日（3日）に白米。悪い日（1日）にも白米。

**これは情報量ゼロであるだけでなく、信頼を一度で失います。**
声のプロは、根拠のない断定にきわめて敏感です。**一度「適当なことを言うアプリ」と判断されたら戻りません。**

**発見は、少なく、遅く、正しく出してください。**
1つの正しい発見は、10の当たり障りのない文章より価値があります。

### 瞬間④｜調子が悪い日（それでも開いたか）

**このアプリの成否を決める数字は、これ1つです。**

調子の良い日に記録が続くのは当たり前です。
**悪い日のデータこそ、このアプリが最も必要としているもの**であり、
**悪い日に開いてもらえるかどうかが、成立するかどうかそのもの**です。

```
❌ 「未入力 4項目」「完了度 55%」  → 悪い日に開かなくなります
❌ 連続記録が途切れて羊がしおれる  → 同上
✅ 「今日の記録 ●●●○○ 5項目」    → 増える表現だけを使う
✅ 30秒で終わる道が常にある
```

**この4つが、本書のすべての作業の判断基準です。**
Sonnet が何かを提案してきたら、**「4つの瞬間のどれを良くするか」**で判断してください。
どれも良くしないなら、いまはやらなくていいものです。

### 4-1｜コア項目から音名を外す理由

**改善タスクは「起き抜けの音名」をコアに入れていますが、外します。**

音名ピッカーは、コアの4項目の中で**唯一10秒以上かかる操作**です。
「30秒で終わる」を名乗る以上、ここに置けません。

```
コア（30秒）    喉のコンディション ／ 声の出来 ／ 活動 ／ 睡眠時間
推奨            ★起き抜けの音名 ／ 症状の有無 ／ 心の余裕 ／ 水分
詳細（任意）    食事・栄養・体重・環境・響きスコア・CPPS
```

**ただし、改善タスクの指摘は正しい**——音名がないと音域到達マップとウォームアップ効率が動きません。
**なので推奨層の先頭に置き、分析側から名指しで要求してください**（記録と分析の順番設計 §5.3）。

> 「音域到達マップは、起き抜けの音名をあと5日記録すると開きます」　[ 今日の分を入れる → ]

**「必須にする」ではなく「欲しがる」形にします。** これが本書 §2 の④を守る唯一の方法です。

### 4-2｜指導者機能を「隠す」が「捨てる」ではない理由

改善タスク P2-2 は正しい。**指導者は最大の増幅装置です。**

**ただし、いま権限の層が壊れています**（500・401、権限テスト未実施）。
**壊れた権限の上で増幅すると、事故も増幅されます。**

```
G1  権限を直す（500 を消す・テスト16件）
G2  10人に配る    ← 指導者機能はオフ
G3  法令要件を満たす
G3の直後  ★指導者機能を最優先で戻す（招待の正式化・途切れ通知）
G4  教室プラン（複数の先生 × 複数の生徒）
```

**順番の問題であって、優先度の問題ではありません。**

### 4-3｜5つ目の職業を凍結する理由

**教師・コールセンター等は、市場としては大きい。** ただし、

```
演者（声楽・アナ・声優・ポップス）  … 声が商品。壊れると仕事が止まる
職業的音声使用者（教師・接客）      … 声は道具。壊れても仕事は続く
```

**動機の強さがまったく違います。** そして UI の語彙も、分析の中身も、価格の感覚も別物です。
**4職種の深さが足りていない段階で5つ目を足すと、全部が浅くなります。**

**改善タスク自身が「優先度は低い」と書いています。その判断に従います。**

### 6-1｜件数だけでは足りません

白米の例は、件数の問題ではありません。**効果量がゼロなのに文章を出したこと**が問題です。
**n が100あっても、「良い日にも悪い日にも白米」は出してはいけません。**

**文章で語るものは、次の3つを全部通ったときだけ出してください。**

```
① 件数    各群 n ≥ 10、かつ両群が揃っている
② 効果量  |Hedges' g| ≥ 0.4（または |ρ| ≥ 0.3）
③ 多重比較 BH-FDR で q < 0.10 を通っている
```

**どれか1つでも欠けたら、文章を生成しないこと。**

### 6-2｜宣言的に持つ

```ts
interface DisplayGate {
  key: string                    // 'diet.narrative' | 'acwr' | 'forecast.hitRate' | ...
  minDays?: number               // 例: acwr = 28
  minNPerGroup?: number          // 例: 10
  minEffectSize?: number         // 例: 0.4
  requiresFdrPass?: boolean
  unlockMessage: (remaining: number) => string
}

const GATES: DisplayGate[] = [ ... ]   // ★1ファイルに集約する
```

**表示側は、必ずこのレイヤーを参照してください。**
**画面ごとに条件を書かないこと。** そこが今回の不整合の原因です。

### 6-3｜消すのではなく、置き換える

**文章を消しただけにしないでください。必ず「あと◯で何が見えるか」に置き換えます。**

```
❌ （何も表示しない）
❌ 「データ不足」
✅ 「あと7件の記録で、食事と声の傾向の分析が始まります」
✅ 「発声負荷バランスの計算には、あと20日分の記録が必要です」
```

**既存の段階的アンロックと、同じトーンに揃えてください**（§3 の 8）。

### 6-4｜対象箇所（網羅すること）

```
・「複数の条件を組み合わせて見えてきたこと」の全文
・「休養方法ごとの声・メンタルの傾向」
・「滞在地ごとの声・メンタルの傾向」
・「よく一緒に出る症状」
・「気持ちタグの傾向」
・「時間帯別の声の傾向」の「調子が良い傾向」バッジ
・「今日の一言」のすべての警告文
・偏差値（件数30未満は順位のみ）
・声の予報の的中率（14件未満は非表示）
```

**「今日の一言」は、根拠となる指標がロック中でないかを、指標ごとに確認してください。**
ACWR で起きたことが、他の指標でも起きている可能性があります。

## 8. ★ 9言語対応と、提供地域について（坂本さんの判断が要ります）

**改善タスクが GDPR に触れています。これは重要な指摘です。**

**UI が9言語に対応していることは、EU 域内の利用者に向けて提供している証拠のひとつと
みなされる可能性があります。** そして扱っているのは**健康データ（GDPR の特別カテゴリ）**です。

**そうなると、書き出し・削除だけでは足りません。**
域外の管理者には、EU 域内の代理人を置く義務が生じうるなど、要件が一段重くなります。

**G3 までの現実的な対応**

```
① 利用規約に「本サービスは日本国内の利用者に向けて提供しています」と明記する
② 海外向けの宣伝・アプリストアの配信地域を、日本に限定する
③ 言語の選択肢は残してよい（在日外国人・日本在住の利用者のため）
④ EU展開は、G4 の後に別途設計する（国際展開仕様の Phase 0 は既に済んでいます）
```

**書き出しと削除（G3 の 16・17）は、日本国内向けでも必要です。**
**そちらは予定どおり実装してください。**

## 11. 禁止事項

- ❌ §7 の差し替え表を読まずに、古い文書を実装しない

- ❌ 表示条件を画面ごとに書かない（§6-2 のレイヤーを必ず経由する）
- ❌ 文章を消しただけにしない（§6-3）
- ❌ **ACWR の計算式を、EWMA からローリング平均に変えない**（§4 の 2）
- ❌ コア項目に音名を入れない（§4-1）
- ❌ かんたん記録のポイント・連続記録を減点しない
- ❌ 「未入力」「不足」「完了度◯%」をUIに出さない
- ❌ 羊のポイントを体調の良し悪しに連動させない
- ❌ RLS のポリシーの中で他テーブルを直接参照しない
- ❌ **RLS だけで守らない。**サーバー側の `canView()` と二重にする
- ❌ 管理者に、担当していない生徒の健康データを見せない
- ❌ **レッスンの連絡に、自由記述欄を作らない**（レッスン連絡パッチ §4-1）
- ❌ **欠席の理由を選ばせない**（同 §4-2。要配慮個人情報になります）
- ❌ 「疑い」「リスク」「早期発見」「予防」をアプリのどこにも出さない
- ❌ 文献の基準値と、ユーザーの数値を同じ画面に並べない
- ❌ データの書き出しを有料機能にしない
