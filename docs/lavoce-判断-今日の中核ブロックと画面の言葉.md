## 1. なぜブロックを作らないか

### 1-1｜利用者が入力するのは、3つだけです

**あなたの ③④ の指摘が、そのまま答えになっています。**

```
① 睡眠時間               ★入力する
② 本番外の発話時間       ★入力する（4択化済み）
③ 絶対湿度               自動取得。★入力欄は不要
④ 本番・レッスンの翌日か 活動の記録から導出。★利用者に聞かない
⑤ 起きたときのむくみ     ★入力する
```

**「5つのブロック」は成り立ちません。3つしかないからです。**

私は5項目を並べる前提で指示を書きました。**そのうち2つが入力項目ではないことに、
気づいていませんでした。**

### 1-2｜器は、すでにあります

**「かんたん（30秒）モード」がそれです。**

```
いま    のどの調子 ／ 声の出来 ／ 昨夜の睡眠

★あと  のどの調子 ／ 声の出来 ／ 睡眠 ／ むくみ ／ 本番外の発話時間
```

**これで中核5項目が全部揃います。**

```
前2つ    結果（y）
後3つ    原因（x）
絶対湿度  自動
本番翌日  導出
```

**新しいブロックは要りません。★かんたんモードの中身を、この5つにしてください。**

**そして「3つだけでいい」という説明は変えないでください。**
5つになっても「これだけでいい」です。**増えたことを強調しない。**

### 1-3｜★「中核」と名前を付けて囲ってはいけません

**囲った瞬間に、それ以外が「そうでないもの」になります。**

```
周期を記録している人にとって、周期は中核です
逆流に悩んでいる人にとって、食事と就寝が中核です
「ほかの仕事」で声を削っている人にとって、それが中核です
```

**「中核5項目」は、★分析の都合による分類です。利用者の生活の分類ではありません。**

**分析の都合で決めた序列を、画面に持ち込まないでください。**

## 2. あなたの懸念について

> 分散させる案Bだと、「これが中核5項目である」というまとまりの意識自体が失われ、
> §2④（項目ごとの記録率を測る）の土台としても扱いにくくなる懸念があります。

**§2④ は内部の集計なので、画面のまとまりとは無関係です。**

```
lib に CORE_FIELDS という定数を1つ置けば足ります。
★画面上のまとまりは、集計の前提になりません。
```

そして——

> 5つを目立たせて、埋まっていない項目に気づいてもらう

**この役割は、§2④ が果たします。**

「今日の1つ」の枠に、埋まっていない中核項目だけを**事実として**出す。

```
○ 「むくみは、まだ3日ぶんです」
✗ 「記録しましょう」「あと◯日です」
```

**画面で囲って目立たせる必要はありません。**
**そして、目立たせることは、催促の一歩手前です。**

## 3. ③④ の扱い

### 3-1｜絶対湿度 ── 入力欄を作らない

```
□ 1日の記録の「環境」セクションで、★自動取得のみ
□ ★手入力の逃げ道は必ず残す
     （海外公演・地下スタジオで API が当てにならないため。憲章 §4-2）
□ ★「今日の中核」のような入力ブロックに並べない
```

**参考：**現在の充足率は 55.6%（18日中10日）、うち**気温も湿度も両方欠けている日が 7日**
という報告がありました。**取得の経路そのものに問題がある可能性があります。**
**★これは別件として、配布前に一度調べてください。**補完はしません。取得を確実にする話です。

### 3-2｜「本番・レッスンの翌日か」── 利用者に聞かない

```
□ ★活動の記録から導出する
□ ★入力項目にしない
```

**同じことを2か所で聞くと、食い違ったときにどちらが正か分からなくなります。**
年齢の件（`profiles.age` と `is_under_18` を兼用しない）と、同じ理由です。
