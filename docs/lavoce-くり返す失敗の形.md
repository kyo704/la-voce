# くり返す失敗の形

★この文書は**足すだけ**です。直った項目も消しません。**同じ形が何度も出る**ことが、
いちばん大事な情報だからです。

★新しい形が出たら、いちばん下に足してください。回数も更新してください。

---

## ★★ いちばん先に読んでください ★★

### 本番で何かを試すとき

> ★**`begin;` 〜 `rollback;` は、守りとして数えません。**
> SQL エディタが文を1つずつ流していると、★**囲みは効きません。**
> 1文ごとに確定するので、途中でエラーになっても、★**それより前の文は残ります。**
>
> ★**2026-09-03 に、実際に残りました。** 自己昇格を試す照会で、
> 先頭の `insert` が本番に残りました（`id = 64a84bcd-…`）。
>
> **だから、こうします。**
> 1. ★**書き込まずに済む形を、先に考える**
> 2. ★どうしても書くなら、★**元に戻す文を、同じ出力の中に置く**
>    （「あとで消す」ではなく、**作る文と消す文を一緒に渡す**）
> 3. ★**エラーで止まったら、まず「何が残ったか」を確かめる。**
>    「エラーだから何も起きていない」とは考えない
> 4. ★**実在の方の行では試さない。** 壊れたときに戻せない相手がいます

詳しくは **7-4** を見てください。

★「書き写さないこと」とコメントするだけでは防げません。何度もそう書いてありました。

  別の関数（`canSeeStudentTeacherLink`）にあり、★**常に true** でした。

**「この列だけ見せる」**と読める。作った人は、そのつもりだった。
★**RLS は列を絞れません。** 行が読めれば、その行の**全部**が読めます。

**出た回数**：1回（`profiles`。★`allergies` / `regular_medications` /
`conditions`（既往症）/ `health_notes` / `is_under_18` / `line_user_id` が、

## 6-3. WITH CHECK の無い UPDATE ポリシー

> ★**WITH CHECK の無い UPDATE のポリシーは、欠陥です。例外はありません。**
> （2026-09-03・Opus の裁定）

**形**：`USING` だけ書いて、`WITH CHECK` を書かない。
★`USING` は**更新前の行**を見ます。★**更新後の行は、誰も見ていません。**
だから `USING` を通れば、★**どの列でも書き換えられます。**

**出た回数**：★**1日で2回**（2026-09-03）

| 表 | どうなったか |
|---|---|
| `memberships` | 9/2 に★**自己昇格が実際に起きた**。その後、手で `role_rank` の条件が足され、いまは塞がっている |
| `teacher_student_links` | ★**2026-09-03、実地で両方向とも書き換えに成功**（#006）。生徒が `teacher_id` を自分に、先生が `student_id` を第三者に |

★**2回出たものは、3回目があります。** 常設の照会を作りました：
`supabase/AUDIT_update_without_with_check.sql`

**★あわせて憶えること：列を絞れるのは GRANT です**

私は今日、「RLS は列を絞れません」と何度も書きました。★**それは正しい。**
★**ですが「では何なら絞れるのか」を、一度も書きませんでした。**

```sql
grant update (status, revoked_at, revoked_by) on public.teacher_student_links to authenticated;
```

★**列単位の権限は、PostgreSQL の標準の機能です。**
★「RLS では無理」で止めず、★**「何なら可能か」まで言います。**
止めたことで、私は関数で包む遠回りな案を推してしまいました。

**★2枚の板で塞ぐ**

> ★**ポリシーの不在は1枚の板。権限の剥奪と合わせて2枚にすること。**
> （2026-09-03・Opus）

- 1枚目：**権限**（`GRANT` / `REVOKE`）… そもそも書ける列を渡さない
- 2枚目：**ポリシー**（`WITH CHECK`）… 身元の列が変わっていないことを確かめる

★**どちらか片方が外れても、もう片方が残ります。**
★**「ポリシーが無いから安全」で止めません。** 権限も剥がします。

## 7-3. 出す順番の向きを、逆にする

**形**：「コードを先に、SQL を後に」を、**足すときにも当てはめてしまう**。

★**向きは、足すか消すかで逆になります。**

| | 何を先に | なぜ |
|---|---|---|
| **消すとき**（列・ポリシー） | ★**閉じる側を先に** | 読まれた行は戻せません。壊れた画面は数分で直せます |
| **足すとき**（関数・表） | ★**受け皿を先に** | 無ければ 404。コードが先に出ると、その間ずっと壊れます |

**出た回数**：1回（2026-09-03）
`profiles_connected_display_name` を落としたのは**正しい順**でした（先に閉じた）。
ですが `get_connected_names` は★**コードを先に出してしまい**、
関数が入るまで4か所が 404 になりました。

★`supabase/migration_lesson_held.sql` に、私は自分で
「★コードの側を先に直してください。順番を逆にすると insert が壊れます」
と書いています。★**あれは列を消す話です。** 足す話に当てはめたのが誤りでした。

**防ぎ方**：出す前に、★**「これは門を閉じる変更か、受け皿を作る変更か」**を一度言葉にする。
閉じるなら閉じる側が先、作るなら作る側が先。
★**どちらか片方しか起きないとき、無害なほうが起きる順**を選びます。

## 7-4. `begin` 〜 `rollback` が守ってくれると思いこむ

**形**：本番で試すとき、`begin;` … `rollback;` で囲めば何も残らない、と考える。
★**SQL エディタが文を1つずつ流していれば、囲みは効きません。**
1文ごとに自動で確定するので、途中でエラーになっても、★**それより前の文は残ります。**

**出た回数**：1回（2026-09-03）
自己昇格を試す照会で、先頭の `insert`（試験用の membership）が★**本番に残りました。**
`id = 64a84bcd-…` が、実在の行として作られました。
★エラーは、そのあとの `update` で起きています。★**囲みは働きませんでした。**

★**幸い、確かめたかったことは分かりました**（`update` が弾かれた＝守りは効いている）。
★**ですが、それは結果論です。** 逆の順で壊れていれば、消し方の分からない行が残りました。

**★これからの決めごと**

1. ★**本番で試すときは、`begin`/`rollback` を守りとして数えません。**
2. ★**書き込まずに済む形を、先に考えます。**
   - ポリシーの式だけを評価する（例：`select role_rank('owner') <= role_rank('teacher')`）
   - すでにある行を使い、★**同じ値へ更新する**（変化なし）と、
     ★**上の値へ更新する**（弾かれるはず）を比べる
3. ★**どうしても作るなら、作った id をすぐ返させ、消し方も一緒に書きます。**
   ★「あとで消す」ではなく、★**消す文を、作る文と同じ返信に置きます。**
4. ★**エラーで止まったら、まず「何が残ったか」を確かめます。**
   ★「エラーだから何も起きていない」とは考えません。

## 8. 取り返しのつかない操作の前に、確かめた数値が「戻ってきていない」

**形**：安全のための数え上げ（「中身のある行は0か」）を用意し、運営者が実行し、
**その数値が実装側まで返らないまま**、次の取り返しのつかない手順が承認される。
手順としては守られているのに、**確かめた事実を知らない者が居る**状態が残る。

**出た回数**：1回（`lessons.teacher_note` の DROP。★実際には①は0で、
順番も守られていました。返ってこなかったのは**数値そのもの**です）

★これは**コードの読み違いではなく、受け渡しの欠落**です。だから別の項目にしています。
コードを直しても、この形は防げません。

**防ぎ方**：取り返しのつかない手順（`drop column` / `delete` / 本番の設定変更）の前に、
★**その手前の確認の「実際の値」を、実装側まで一度返す。**
「進んでよい」だけでは足りません。★**何がいくつだったか**を返します。
返っていないうちは、実装側は「まだ確かめていない」として扱ってよい
（そう扱ったことで、この項目が見つかりました）。

★似た紛らわしさ：「列はもう無い（0）」と「落とす前の中身は0だった」は、**別の事実**です。
前者は後者を意味しません。

## 10. リポジトリが通っていることを、本番が動いていることと読む

★2026-09-03 の全面停止（インシデント #008）から。

★**当てられていない移行ファイルと、手で当てた別の形の関数が重なって、
本番が止まりました。★そのとき検査は120本あり、すべて通っていました。
★見つけたのは、実機で触った人です。**

    リポジトリに関数が書いてある   ← 検査はこれを見ます
    本番にその関数が当たっている   ← ★検査は1本も見ていません

★この2つは、別の事実です。片方から、もう片方は出てきません。

失敗の形は3つ重なりました。

1. ★**移行ファイルが当たっていなかった。**
   書いた人は、書いた時点で終わったつもりでいました。
2. ★**手で当てた関数の、引数の形が違っていた。**
   PostgREST は、引数が合わない関数を「無い」と同じに扱います。
   ★存在する、という照会では見つかりません。★形まで見ること。
3. ★**SQL を会話で渡していた。**
   8本のうち4本が届いていませんでした。★切れたことは、
   どちらの側からも見えませんでした。

やること。

- ★**「検査が全部通った」を、報告に書かないこと。**
  書くなら「リポジトリの検査が通った」と書きます。
  ★本番については、何も言っていません。
- ★関数を照会するときは、名前だけでなく
  `pg_get_function_identity_arguments` まで見ること。
- ★SQL はファイルで渡すこと（Desktop に置く）。会話に貼らないこと。
- ★本番に手で当てたら、その日のうちにリポジトリへ写すこと（7-2）。
  ★写さないと、リポジトリのほうが嘘になります。実際なりました
  （`migration_identity_columns_immutable.sql:57` の列は、本番と違っていました）。
