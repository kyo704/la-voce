## 1. 結論

```
① ★画面のどこかに、バージョンを表示する。ここが起点になります。
② 新しい版が出たら、★利用者が何もしなくても入れ替わる。
③ HTMLはキャッシュしない。静的ファイルは★中身が変わればURLも変わる形にする。
④ ★「キャッシュを消してください」と利用者に言わせない。それは敗北です。
⑤ 配布の前に、★実機2台で確認する。
```

## 2. バージョンの表示（★最初にこれ）

```
もっと（設定）の★いちばん下に、小さく表示する

　バージョン  2026.08.28-3
　最終更新    8月28日 14:32
```

```
・ビルド時のコミットハッシュか、日時から生成する

・利用者に説明は不要。★私たちが確認するために置きます
```

**これがあると、「古い画面を見ている」ことが1秒で分かります。**
**いまは、それを見分ける方法がありません。**

---

## 3. Service Worker の更新

### 3-1｜要件

```
□ 新しい Service Worker を検知したら、★待たせずに有効化する
     （skipWaiting）
□ 有効化したら、★すぐ全タブを制御下に置く
     （clients.claim）
□ アプリを開いたとき、および★バックグラウンドから復帰したときに
     registration.update() を呼ぶ
□ controllerchange を受けたら★1回だけ location.reload() する
     ★ループ防止のフラグを必ず置くこと
```

### 3-2｜キャッシュの方針

```
HTML（ページ本体）      ★キャッシュしない（network first）
JS / CSS               中身が変わればファイル名も変わる形（ハッシュ付き）
                       → ★長期キャッシュしてよい
画像・フォント          長期キャッシュしてよい
APIの応答               ★キャッシュしない
```

**Next.js の既定でほぼ満たされますが、
自前の Service Worker が上書きしていないかを確認してください。**

### 3-3｜古いキャッシュの掃除

```
□ activate で、★現行バージョン以外の caches を全部削除する
□ キャッシュ名にバージョンを含める（例 woolsong-v3）
```

```
□ GitHub連携が生きていることを、★毎回の作業の最後に確認する
□ デプロイの成否を通知で受け取る設定にする
□ ★「push したから反映されたはず」で終わらせない
```

**§2 のバージョン表示を見れば、反映されたかどうかが分かります。**

## 5. 受け入れ条件（★実機で）

**端末を2台使ってください。1台は、古い版を開いた状態のまま残しておくこと。**

```
□ 新しくデプロイしたあと、★古い版を開いていた端末で、
     アプリを閉じて開き直すと、30秒以内に新しい版になる
□ そのとき、もっとの★バージョン表示が変わっている
□ ホーム画面に追加した状態でも、同じことが起きる
□ 機内モードで開いても、アプリが起動する（オフラインで壊れない）
□ 機内モードを解除して開き直すと、新しい版になる
□ ★利用者に「キャッシュを消してください」と言う場面が、一度もない
```
