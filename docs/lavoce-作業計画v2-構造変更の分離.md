# La Voce ／ 作業計画の修正 — 声の構造変更を分離する

記録項目 v2 の実装順について、**「声の記録の構造変更（§3.1・§3.2）を今回は見送る」
という判断を承認**し、対象項目を修正するための指示書。

---

## 0. 結論

**判断は正しい。そのまま進めてください。** 修正は2点だけです。

| | 内容 |
|---|---|
| ✅ 承認 | 声の構造変更（記録項目v2 §3.1・§3.2）を今回は見送る |
| ✅ 承認 | 専用セッションで、他に何も並行させずに取り組む |
| 🔧 修正1 | **稽古ノート（§3.7）と カスタマイズ（§4）は「独立」ではないので、今回から外す** |
| 🔧 修正2 | **「弱声の最高音」だけは今回入れる。** 構造変更ではなく、nullable なカラム追加1本で済みます |

### 判断が正しい理由

曲目複数化という、比較にならないほど小さいスキーマ変更で保存周りが何往復も壊れました。
**これは推測ではなく観測です。** 手元で得られる最良のデータが警告を出している以上、
それに従うのが正しい。

なお、記録項目v2 が「§3.1 は破壊的変更なので最初に片付ける」と書いていたのは、
**テストがあって壊れたらすぐ気づける環境を前提にした原則**でした。
その前提が満たされていない現状では、順番より安全性が優先されます。
**この点で元の仕様書が誤っていました。**

### 稽古ノートを今回やらない理由

稽古ノートの価値の中心は、**「変わった気がしない」と書いた横に、
実は半音上がっているグラフが並ぶ**ことです（記録項目v2 §3.7）。
その自動添付がないと、単なるメモ帳になります。

**構造変更の直後にやると、いちばん効きます。**

### §4 を今回やらない理由

詳細度（`DetailConfig`）は `voice` グループも対象に含みます。
記録画面の表示・非表示の仕組みを作り直す変更なので、
声の欄の構造が確定してから着手するのが自然です。

## 3. 弱声の最高音（今回入れる／追加のみ）

### 3.1 なぜ今回入れるのか

記録項目v2 が §3.1・§3.2 と並べて書いたせいで一体の変更に見えていましたが、
**「弱声の最高音」と「時刻つきエントリへの再構築」は別々の変更**です。

弱声の最高音は、**いまの構造に nullable なカラムを1本足すだけ**で成立します。
既存データは `null`、既存の読み書きは一切変わりません。**移行が発生しません。**

これを入れると、**このアプリで最も費用対効果が高い指標**（別資料の A-1）と、
次回の稽古ノートの目玉が同時に解放されます。

### 3.2 データ

```
既存の声の記録に、次の1カラムを追加する

  pitchSoftMaxMidi : number | null     // MIDI番号で保持（国際展開仕様 §2.1）
```

**既存フィールドを一切変更しないこと。** マイグレーションはカラム追加のみ。

### 3.3 記録画面

既存の「起き抜けの音名」「ルーティン後の音名」と**同じ音名ピッカー**を、もう1つ置く。

```
起き抜けの地声の音名      [ A3 ▾ ]
ルーティン後の地声の音名   [ C4 ▾ ]
弱声の最高音              [ E5 ▾ ]   ← 追加
  ▸ これは何？
```

ヘルプ（「▸ これは何？」の中身）：

> ごく小さな音量で出せる、いちばん高い音です。
> 「ハッピーバースデー」の出だしを、ささやくような音量で歌ってみてください。
> 大きな声だと分かりにくいので、**できるだけ小さく**が大事です。

### 3.4 表示

**① 音域マップに3本目**

既存の音域マップ（鍵盤ビジュアル）に、弱声の最高音のマーカーを追加する。

**② 推移グラフ**

既存の「起き抜け・ルーティン後の音名の推移」に3本目の線として追加。

**③ 平常値との比較**

```
m   = 中央値(pitchSoftMaxMidi)          直近28日
MAD = 中央絶対偏差
z   = 0.6745 × (今日の値 − m) / MAD

z ≤ −1.5 が3日以上続いたら、おうちのカードで知らせる
```

**表示条件：記録3日以上。**

### 3.5 文言（重要）

国際展開仕様 §5.2 の規則に従います。**むくみ・診断語を使わないこと。**

> ✗ 「声帯のむくみが疑われます」「浮腫のサインです」
> ✓ 「弱声の最高音が、あなたの平常値より3半音低い日が4日続いています」

## 4. 次回セッションの前に：保存・読み込みのテスト

**構造変更に着手する前に、必ずこれを済ませてください。**

曲目複数化で何往復もしたのは、**壊れたことに気づく仕組みがなかったから**です。
次はもっと大きい変更なので、同じ状態で臨めば同じことが起きます。

### 4.1 最低限のテスト（6本）

```
1. 保存 → 読み出しで、すべてのフィールドの値が一致する
2. 任意フィールドが未入力（null / undefined）でも、保存と読み出しができる
3. 過去日を編集しても、他の日のデータが変わらない
4. 同じ日に2回保存しても、レコードが重複しない
5. オフラインで入力 → オンライン復帰で同期され、重複しない
6. 配列（活動・曲目）の並べ替えと削除の後も、order が連番で整合している
```

**6本で十分です。** これがあるだけで、次の移行の往復回数が桁で変わります。
E2E である必要はなく、保存・読み出しの関数に対する単体テストで構いません。

### 4.2 データのバックアップ

移行を流す前に、**全ユーザーのデータをエクスポートして保管**してください。
記録項目v2 §6.3 の書き出し機能がまだなら、**スクリプトで一括ダンプするだけでよい**。

## 5. 専用セッションの手順書（声の構造変更）

**一気にやらず、4段階に分けて、1PRずつ。**

### Step 1：読み取り互換レイヤー（PR-1）

新旧どちらの形でも読める関数を**1つだけ**作り、
**すべての読み出し箇所をこの関数経由にする。**

```ts
// 旧形式（総合 ＋ 朝昼晩の固定枠）でも
// 新形式（時刻つきエントリの配列）でも、常に VoiceEntry[] を返す
function readVoiceEntries(record: unknown): VoiceEntry[]
```

**この時点でアプリの挙動は一切変わりません。** ここが安全弁になります。

### Step 2：新構造の追加（PR-2）

新しいテーブル／フィールドを追加する。**旧構造はそのまま残す。**
書き込みはまだ旧のまま。

### Step 3：移行スクリプト（PR-3）

旧 → 新へデータを写す。**旧データは消さない。**

```
総合の「喉の状態」    → VoiceEntry.bodyFeel（context: 'other', at: '12:00'）
総合の「声の調子」    → VoiceEntry.quality（5段階 → 0–10 に線形変換）
「響きスコア」        → VoiceEntry.quality（★あればこちらを優先）
朝／昼／晩の3枠       → VoiceEntry 3件（at は 08:00 / 13:00 / 20:00 を既定）
起き抜けの音名        → VoiceEntry.pitchChest（context: 'wake'）
ルーティン後の音名    → VoiceEntry.pitchChest（context: 'after_routine'）
弱声の最高音          → VoiceEntry.pitchSoftMax（context: 'wake'）

移行したエントリには source: 'migrated' を立て、
時刻が推定であることを分析側で区別できるようにする（日内変動の分析から除外）
```

**Step 3 で止めても、アプリは動いたままです。** 問題が出たら旧構造のまま運用を続けられます。

### Step 4：書き込みの切り替え（PR-4）と、旧フィールドの削除（PR-5）

- PR-4：書き込みを新構造に切り替える。**旧フィールドはまだ残す**
- **数日運用して問題がないことを確認してから**、PR-5 で旧フィールドを削除する

### 5.1 ロールバックの手順

| 段階 | 戻し方 |
|---|---|
| Step 1〜3 | そのまま。挙動が変わっていないので、戻す必要がない |
| Step 4（PR-4後） | 書き込みを旧構造に戻す。旧フィールドが残っているので即座に戻せる |
| Step 5（PR-5後） | **戻せない。** だから数日空ける |

### 5.2 このセッションでやらないこと

- UI の見た目の改善
- 新しい分析指標の追加
- 他の項目の実装

**構造変更だけに集中してください。** 並行させると、
不具合の原因がどちらか分からなくなります。

## 7. Sonnet 5 への依頼のコツ

- **今回のセッションで §3.1・§3.2 に触れないこと。** カラム追加（§3）だけが例外です
- 弱声の最高音は「**既存フィールドを一切変更しない、追加のみのマイグレーション**」と
  明示して依頼する。ここで既存の音名フィールドを整理し始めると、本末転倒になります
- §2 の作業リストは**上から順に、1項目1PR**で。まとめてやらせない
- 次回の構造変更セッションでは、**§5 の Step 1 から順に、必ず1PRずつ**。
  「Step 1 と 2 を一緒に」は認めないこと
- §4 のテストは、構造変更の**前提条件**です。「あとで書く」を許さない
