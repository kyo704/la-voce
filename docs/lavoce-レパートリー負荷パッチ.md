# La Voce ／ レパートリー負荷 実装パッチ仕様

**前提：この機能はすでに実装済みです。** 本書はゼロからの仕様ではなく、
既存実装への**差分パッチ**として書いています。

## 0. 仕様の訂正（実装者は悪くありません）

職業別設計の資料に「曲目ごとの負荷は**新しい入力は不要**」と書きましたが、
**これは誤りでした。**

曲名から音域・テッシトゥーラを引ける実用的なデータベースは存在しません。
オペラのアリアですら断片的で、ミュージカル・ポップス・アニメ曲では皆無です。
**「1曲につき1回だけの軽い登録」を追加した現行の実装判断が正解です。**

以下のパッチは、その判断を前提に、精度と使い勝手を上げるためのものです。

**パッチの優先順位**

1. **§2 曲目名の正規化とサジェスト** ← これを入れないと機能が静かに壊れます。最優先
2. §1 負荷計算式の修正
3. §4 ランキングカードの並べ替えと件数門番
4. §3 登録UIの軽量化
5. §5 スキーマの一般化（他職業への展開と、将来の集合知）

## 1. 負荷計算式の修正

### 1.1 現行の式と、2つの問題

```
役の負荷 = 演奏時間(分) × |テッシトゥーラ − 快適音域の中心| / 快適音域の幅
```

**問題1：中心で歌うと負荷がゼロになる。**
快適音域のど真ん中の曲を3時間歌っても `|0| = 0`。
実際には「歌うこと自体のコスト」があります。ベースを 1.0 にして、逸脱をその上に乗せます。

**問題2：上下を同じ重みで扱っている。**
快適音域の中心より**上**を歌うのは、同じ半音数だけ**下**を歌うよりずっと重い。
絶対値では高い役と低い役が同じ負荷になります。

### 1.2 修正後の式

```
■ 入力
  tess   : テッシトゥーラ（MIDI番号）
  low    : プロフィールの音域（最低音、MIDI）
  high   : プロフィールの音域（最高音、MIDI）
  minutes: 演奏時間（分）
  actW   : 活動係数（休養0 / 自主練1.0 / レッスン1.2 / リハ1.3 / 本番1.6）

■ 計算
  center = (low + high) / 2
  half   = (high - low) / 2

  d = (tess - center) / half            // -1 〜 +1 に正規化

  strain_raw = (|d| / 0.85) ^ GAMMA     // GAMMA = 1.7（初期値）
  strain     = d >= 0 ? strain_raw
                      : strain_raw * KAPPA    // KAPPA = 0.6（初期値、下方向の重み）
  strain     = clamp(strain, 0, 1.5)

  songFactor = 1.0 + 1.5 * strain       // 1.00 〜 3.25

  L_song = minutes * actW * songFactor
```

**`L_song` は既存の発声負荷 ACWR にそのまま加算できます**（単位が「分 × 係数」で揃うため）。
これが最大の利点です。曲目ごとの負荷を、独立した数字ではなく
**ACWR の一部として扱ってください。**

### 1.3 検証済みの挙動（テノール C3–C5、center = C4）

**この表をそのままユニットテストにしてください。**

| テッシトゥーラ | d | songFactor |
|---|---|---|
| C3（最低音） | −1.00 | 2.19 |
| E3 | −0.67 | 1.60 |
| G3 | −0.42 | 1.27 |
| A♯3 | −0.17 | 1.06 |
| **C4（中心）** | **0.00** | **1.00** |
| D4 | +0.17 | 1.09 |
| F4 | +0.42 | 1.45 |
| G4 | +0.58 | 1.79 |
| A4 | +0.75 | 2.21 |
| B4 | +0.92 | 2.71 |
| C5（最高音） | +1.00 | 2.98 |

ソプラノ（A3–C6、center = A♯4）でも確認済み：
C4 → 1.77 ／ F4 → 1.26 ／ A♯4 → 1.00 ／ D5 → 1.20 ／ G5 → 1.90 ／ A5 → 2.29。

**本番120分・活動係数1.6 のときの `L_song`**（テノール）

| 役の性質 | テッシトゥーラ | L_song |
|---|---|---|
| 中心 | C4 | 192 |
| やや高い | F4 | 278 |
| 高い役 | A4 | 425 |
| 低い役 | E3 | 306 |

**きつい役が快適な役の2倍強**になり、同じ距離なら上のほうが重い。
体感と一致するはずです。

### 1.4 「快適音域」について

現行実装は、プロフィールの**音域（最低音／最高音）を快適音域として使っています**。
これは厳密には**全音域**であり、快適に出せる範囲より広いはずです。

修正案：**プロフィールに「無理なく出せる音域」（任意）を2フィールド足し、
入力があればそちらを優先する。** 未入力なら現行どおり全音域を使う。

```ts
interface Profile {
  rangeLowMidi?: number       // 既存：出せる最低音
  rangeHighMidi?: number      // 既存：出せる最高音
  comfortLowMidi?: number     // 追加（任意）：無理なく出せる最低音
  comfortHighMidi?: number    // 追加（任意）：無理なく出せる最高音
}

// 計算に使う値
const low  = profile.comfortLowMidi  ?? profile.rangeLowMidi
const high = profile.comfortHighMidi ?? profile.rangeHighMidi
```

推定で埋めない（全音域から15%削る、などのヒューリスティックは入れない）。
**入力がなければ全音域を使い、その旨をツールチップで示す**のが誠実です。

## 2. 曲目名の正規化とサジェスト（最優先）

### 2.1 なぜ最優先か

**「蝶々夫人」「蝶々夫人（ある晴れた日に）」「Butterfly」が別の曲として登録されると、
この機能は静かに壊れます。** エラーも出ず、ただランキングが断片化して意味を失う。

休養方法の「その他」自由記述で、すでに同じ失敗が起きています
（「東京へ行く（鈍行）。帰りは特急」が休養方法として1件計上されている）。

### 2.2 正規化

保存時に `titleRaw`（入力そのまま）と `titleNormalized`（照合用）の両方を持つ。

```ts
function normalizeTitle(raw: string): string {
  return raw
    .normalize('NFKC')            // 全角英数・半角カナを統一
    .toLowerCase()                // ラテン文字の大小を統一
    .replace(/[\s　]+/g, ' ') // 連続空白を1つに（全角空白含む）
    .replace(/[・･]/g, '')        // 中黒を除去
    .replace(/[「」『』"'"']/g, '') // 引用符・かぎ括弧を除去
    .replace(/[（(][^）)]*[）)]/g, '') // 括弧内の補足を除去
    .trim()
}
```

**`titleNormalized` は照合にだけ使い、表示は必ず `titleRaw`。**
ユーザーが書いた形をそのまま見せます。

### 2.3 入力UI：新規入力より「選択」を優先させる

```
┌───────────────────────────────┐
│ 曲目・演目                     │
│ ┌───────────────────────────┐ │
│ │ 蝶々│                     │ │  ← 入力中
│ └───────────────────────────┘ │
│ ┌───────────────────────────┐ │
│ │ 蝶々夫人          F4 ・ 8回│ │  ← 過去の登録からサジェスト
│ │ 蝶々夫人（第2幕）  G4 ・ 2回│ │     登録済みテッシトゥーラと回数
│ ├───────────────────────────┤ │
│ │ ＋「蝶々」を新しく登録      │ │  ← 新規は最後
│ └───────────────────────────┘ │
└───────────────────────────────┘
```

- **前方一致＋部分一致**で、`titleNormalized` に対して検索
- 使用回数の多い順に並べる
- 新規作成の選択肢は**リストの最後**に置く（先頭にあると押されてしまう）

### 2.4 近い名前の警告

新規登録しようとしたとき、`titleNormalized` の**レーベンシュタイン距離が2以下**、
または一方が他方を含む既存曲があれば確認する。

```
┌───────────────────────────────┐
│ 似た曲目が登録されています      │
│                               │
│ 蝶々夫人（F4・8回）            │
│                               │
│ ┌─────────────┬─────────────┐ │
│ │ 同じ曲です   │ 別の曲です   │ │
│ └─────────────┴─────────────┘ │
└───────────────────────────────┘
```

### 2.5 あとから統合できるようにする

表記ゆれは必ず発生します。**設定に「レパートリーの整理」画面**を用意し、
2つの曲目を選んで**統合（マージ）**できるようにしてください。
統合すると、過去の記録の `repertoireId` が付け替わります。

## 3. 登録UIの軽量化

### 3.1 「テッシトゥーラ」を主質問にしない

**多くの歌手は、曲のテッシトゥーラを一音に特定できません。**
音楽用語として知ってはいても、「この曲は F4」と即答できる人は少数です。

**主質問を「最高音」に変える。** 答えやすさが段違いで、しかも歌手にとっての負荷は
上の音が支配的なので、予測力はむしろ高い可能性があります。

```
┌───────────────────────────────┐
│ 「蝶々夫人」を登録              │
│ （1回だけ。あとから変えられます）│
│                               │
│ この曲の最高音は？              │
│  ┃█┃█┃ ┃█┃█┃█┃ ┃█┃█┃ ┃█┃█┃█┃│  ← 既存の音名ピッカー
│  ┗━┻━┻━┻━┻━┻━┻━┻━┻━┻━┻━┻━┛│
│              B♭4               │
│                               │
│ ▸ テッシトゥーラも入力する（任意）│  ← アコーディオン、既定は閉じる
│                               │
│ ┌─────────────┬─────────────┐ │
│ │  登録する    │  あとで      │ │  ← 「あとで」を同じ大きさで
│ └─────────────┴─────────────┘ │
└───────────────────────────────┘
```

### 3.2 テッシトゥーラの推定

最高音しか入力がない場合は推定する。**推定値であることを画面に明示すること。**

```
tess ≈ topNote − 5   （半音）
```

声楽の一般的なアリアで、テッシトゥーラは最高音のおおむね完全4度〜5度下に来ます。
**この −5 は仮置きです。** 両方入力された曲が5件貯まったら、
その人の実測平均に置き換えてください。

```ts
// 両方入力済みの曲が5件以上あれば、個人の平均差を使う
const offset = bothEntered.length >= 5
  ? median(bothEntered.map(r => r.topNoteMidi - r.tessituraMidi))
  : 5
```

### 3.3 最後の手段：3択

音名で答えられない人向けに、フォールバックを置く。

```
自分の音域の中で、この曲はどのあたり？
┌──────┬────────┬──────┐
│ 低め  │ 真ん中  │ 高め  │
└──────┴────────┴──────┘
```

```
低め   → d = −0.5
真ん中 → d =  0.0
高め   → d = +0.5
```

`d` を直接与える形にすれば、テッシトゥーラを持たなくても `songFactor` が出せます。
**推定の粗さを `confidence` として保存し、分析側で件数の重みに使ってください。**

### 3.4 登録の3原則

1. **スキップしても記録は保存される**（登録は記録の前提条件ではない）
2. **あとから登録したら、過去の記録に遡って適用される**
3. **一度スキップした曲に、繰り返し登録を促さない**（3回目の使用時にもう一度だけ）

## 4. ランキングカードの修正

### 4.1 並べ替えの軸を変える

現行は**計算した負荷の順**に並べています。それはモデルの出力であって、観測ではありません。

**「実際に翌日が落ちた順」に並べ、計算負荷は横に添える。**
そうすると、この2つがズレた役が浮かび上がります。

### 4.2 修正後のカード

```
┌───────────────────────────────┐
│ あなたにとって重い役             │
│ 翌日の落ち込みが大きい順          │  12px muted
│                               │
│ ① 蝶々夫人                     │
│    翌日 −1.8  ▓▓▓▓▓▓▓░░       │
│    計算上の負荷 2.21 ・ 5回     │  12px muted
│                               │
│ ② トスカ                       │
│    翌日 −1.2  ▓▓▓▓▓░░░░       │
│    計算上の負荷 1.45 ・ 4回     │
│    ⚠ 計算より重い              │  ← ズレの指摘
│                               │
│ ③ 椿姫                         │
│    翌日 −0.4  ▓▓░░░░░░░       │
│    計算上の負荷 1.79 ・ 3回     │
│                               │
│ ─────────────────────────     │
│ カルメン（2回）                 │  ← 件数不足はグレー表示
│ あと1回でランキングに入ります    │
└───────────────────────────────┘
```

### 4.3 件数の門番

- **n ≥ 3** で本表示。それ未満は「あと◯回でわかります」
- 翌日の落ち込みは `翌日の喉コンディション − その人の平常値` で出す
  （生の平均ではなく、偏差で見る）
- **必ず件数を併記する**

### 4.4 ズレの検出＝いちばん面白い発見

```
乖離 = (実測の落ち込みの順位) − (計算負荷の順位)
```

乖離が大きい役に「⚠ 計算より重い」を出す。これは
**音域以外の要因が効いているサイン**です。

- 演技の消耗、感情の負荷
- 立ち位置・移動量・衣装（コルセットは呼吸を制限します）
- 共演者・指揮者・会場
- 本番の緊張度

**本人にしかわからない発見**なので、そのまま提示して解釈は委ねてください。

> 「トスカは計算上そこまで重くない役ですが、翌日の落ち込みは1番目に大きいです。
> 音域以外の要因があるかもしれません。」

### 4.5 「軽いのに落ちない役」も出す

逆向きも価値があります。

> 「蝶々夫人は計算上いちばん重い役ですが、翌日の落ち込みは平均的です。
> この役はあなたに合っているのかもしれません。」

## 5. スキーマの一般化

### 5.1 曲目専用にしない

**同じ仕組みが4職種すべてで必要です。** 曲目専用のコードにせず、
**汎用の「レパートリー」エンティティ**にしてください。

| 職業 | レパートリーの実体 | 主な属性 |
|---|---|---|
| 声楽家・ミュージカル | 曲目・役 | テッシトゥーラ、最高音、演奏時間 |
| 声優 | 役・作品 | 声の高さ帯、叫びの多さ |
| ポップス/ロック | 曲 | 最高音、ベルト/シャウトの有無、キー |
| アナウンサー | 番組・案件 | 発話時間、生放送か |

### 5.2 データモデル

```ts
type RepertoireKind = 'piece' | 'role' | 'song' | 'program'

interface Repertoire {
  id: string
  userId: string
  kind: RepertoireKind

  titleRaw: string          // 表示用。ユーザーが書いたまま
  titleNormalized: string   // 照合用（§2.2）

  // 声楽・ミュージカル・ポップス
  topNoteMidi?: number      // 最高音（主質問）
  tessituraMidi?: number    // テッシトゥーラ（任意）
  dOverride?: number        // 3択フォールバックの値（-0.5 / 0 / +0.5）

  // ポップス/ロック
  hasBelt?: boolean
  hasShout?: boolean
  keyOffset?: number        // 原曲からの移調（半音）

  // 声優
  screamHeavy?: boolean

  /** 入力の確からしさ。分析側の重みに使う */
  confidence: 'entered' | 'estimated' | 'coarse'

  usageCount: number        // サジェストの並び順に使う
  createdAt: string
  updatedAt: string
}
```

`Activity` 側から参照する：

```ts
interface Activity {
  // ...
  repertoireIds: string[]   // 1日に複数曲
  minutesPerItem?: number[] // 曲ごとの時間（未入力なら等分）
}
```

### 5.3 将来の集合知（設計だけ先に入れておく）

**この機能は、使われるほど価値が上がる資産になります。**

ユーザーが登録を重ねるほど、その人のレパートリー・マスタが育ちます。
そして統計利用の同意（記録項目v2 §6.2 の `statsUse`）を得たうえで集約すると、
**「Nessun dorma のテッシトゥーラは F4 前後」という全ユーザーの集合知**が貯まります。

すると新規ユーザーが曲名を打った瞬間に、こう出せる。

> 「他の方の登録では **F4** です。これを使いますか？」

**登録の手間が、使われるほど消えていく。**
そして「世界中の声のプロが登録したレパートリー負荷データベース」は、
どこにも存在しません。国際展開における最大の参入障壁になり得ます。

**いま必要なのは実装ではなく、スキーマの準備だけです。**

- `titleNormalized` を持つ（§2.2）— 集約のキーになる
- `confidence` を持つ — 集約時に `entered` だけを採用できる
- `userId` でスコープする — いまはユーザー単位、将来は横断集計

**注意**：集約して他ユーザーに提示するのは、
**`statsUse` の同意を得たデータのみ**。要配慮個人情報のオプトアウト第三者提供は
認められていません。曲目名そのものは健康情報ではありませんが、
「誰がどの役で喉を痛めたか」は結びつくと健康情報になります。
**集約は曲目とテッシトゥーラのみとし、コンディションの実測値は混ぜないこと。**

## 6. 係数の較正（データが貯まったら）

`GAMMA = 1.7` と `KAPPA = 0.6` は仮置きです。
**8件以上のレパートリーに「翌日の喉コンディション」が揃ったら、
実データから推定し直してください。**

```
目的変数 y : 翌日の喉コンディションの偏差（その人の平常値との差）
説明変数   : L_song(GAMMA, KAPPA) を含む線形モデル

  y ≈ a + b · L_song(GAMMA, KAPPA) + c · 前日の睡眠時間

(GAMMA, KAPPA) をグリッド探索し、交差検証の二乗誤差が最小になる組を選ぶ

  GAMMA ∈ {1.0, 1.2, 1.4, 1.7, 2.0, 2.4}
  KAPPA ∈ {0.3, 0.45, 0.6, 0.8, 1.0}

件数が少ないので LOO（1件抜き）交差検証で十分。
n < 8 のときは探索せず、初期値のまま使う。
```

推定後は「あなたの声は、快適音域より**上**の負担が下の**1.9倍**効いています」と
提示できます。**係数そのものが発見になる**、珍しい種類の指標です。

| 8 | §6 係数の較正（n ≥ 8 で有効化） | 2日 |

**§5 の一般化は、声優・ポップスのテンプレートを作る前に済ませてください。**
あとからだと3回同じコードを書くことになります。

## 8. Sonnet 5 への依頼のコツ

- **§1.3 の表をそのままテストケースとして渡す。** 境界（d = ±1.00、d = 0）を必ず含める
- `normalizeTitle()` と `songFactor()` は**純関数として切り出し、単体でテスト**させる。
  コンポーネントの中に埋め込ませない
- `GAMMA` `KAPPA` `TESSITURA_OFFSET` は**定数ファイルに置き、あとで差し替えられる形**にする
  （§6 の較正で書き換えるため）
- §5 のマイグレーションは「読み取り互換 → 移行 → 書き込み切り替え → 旧フィールド削除」の
  4ステップに分け、1PRずつ
- ランキングカードの文言は、国際展開仕様 §5.2 の規則に従うこと
  （疾患名・「疑い」・文献閾値を出さない。この機能では該当しにくいが、
  「この役は喉を痛めます」のような断定は避け、「翌日の落ち込みが大きい」に留める）
