# La Voce ／ アプリ配布と課金 実装仕様

ウェブアプリを PWA として配布し、将来ネイティブアプリを出すまでの、
配布・課金・審査対応の仕様。実装は Claude Sonnet 5 を想定。

**この文書の優先順位**

1. **§1 販売チャネルの設計** ← ここを決めないと課金の実装が始められない
2. **§2 課金状態の一元管理** ← あとから直すと二重管理で破綻します。最重要
3. §3 PWA化とインストール導線 ← 今すぐやる
4. §4 ウェブ課金（Stripe）
5. §5 ネイティブアプリ ← **まだ着手しない**（§5.1 の判断基準を満たしてから）

---

## 0. 前提となる判断

**ネイティブアプリは、先に出しません。** 理由：

- 設計済みの機能はすべてブラウザで動く（録音は Web Audio、通知は LINE、
  オフラインは Service Worker、ホーム画面は PWA）
- App Store の検索は、このニッチでは機能しない
  （「声楽 体調管理」で検索する人はまだいない。実際の獲得経路は指導者の口コミ）
- 健康データを扱うアプリは審査で追加要求が来る
- 「ウェブアプリを包んだだけ」のラッパーは、最低限の機能要件で落ちうる

**まず PWA のインストール導線を作り、数字を見てから判断します**（§5.1）。

## 1. 販売チャネルの設計

### 1.1 プラン別の販売チャネル

| プラン | 価格 | ウェブ | アプリ内課金（将来） | 理由 |
|---|---|---|---|---|
| **個人プラン** | ¥580/月・¥5,800/年 | ✓ | ✓ **同額** | 価格を1つにする。手数料は獲得コストとして飲む |
| **指導者プラン** | ¥3,980〜9,800/月 | ✓ | **✗ 販売しない** | 金額が大きく、ストア経由の顧客ではない。法人契約・請求書払いも発生する |

### 1.2 価格差をつけない

アプリ内課金の価格をウェブより高くする案は**採用しません。**

- 日本のスマホ新法では、外部決済を提供する場合
  **アプリ内でウェブ価格を表示し、IAPと外部決済を並べて示すこと**が求められます。
  **価格差は全ユーザーに見えます**
- 声のプロは横のつながりが強く、「アプリから入ると損する」は必ず共有される
- 個人プラン月580円の15%は**月87円**。ストア経由でなければ獲得できなかった顧客に
  払う獲得コストとしては、広告やアフィリエイトより桁違いに安い

**収益の本命は指導者プラン（ウェブのみ）なので、手数料の痛みはほとんど残りません。**

### 1.3 アプリ内リンクによる外部決済は採用しない

日本では合法ですが、小規模事業者にとって経済的に意味がありません。

```
Apple 小規模事業者プログラム IAP      15%
Apple アウトリンク（小規模）          10% + Stripe 3.6% = 13.6%
──────────────────────────────────────────────
差                                    約 1.4 ポイント（月580円で 約8円）
```

その1.4ポイントのために、外部決済への離脱を丸ごと引き受けることになります。
**リンクを置くくらいなら IAP のほうがよい**、という結論です。

なお、アプリ内にリンクを置くと**帰属期間**が発生します
（Apple 7日 / Google 24時間以内の全購入が手数料の対象）。

## 2. 課金状態の一元管理（最重要）

**支払い経路が複数になっても、アプリが見る「権利」は1つにします。**
ここを分けると必ず破綻します。

### 2.1 Entitlement をサーバで持つ

```ts
type PlanKey = 'free' | 'personal' | 'teacher'
type BillingSource = 'stripe' | 'apple' | 'google' | 'manual'

interface Entitlement {
  userId: string
  plan: PlanKey
  status: 'active' | 'grace' | 'canceled' | 'expired'
  source: BillingSource        // どこで買ったか（表示と解約導線の出し分けに使う）
  currentPeriodEnd: string     // ISO
  cancelAtPeriodEnd: boolean
  updatedAt: string
}
```

### 2.2 実装の規則

- **クライアント（ウェブ／アプリ）は `GET /api/entitlement` の結果だけを見る。**
  Stripe のサブスク状態や StoreKit のレシートを、クライアントで直接判定させない
- **価格・プランの定義はサーバから配信する。** アプリのバイナリに埋め込まない
  （価格改定のたびに審査を通すことになります）
- 機能の出し分けは `plan` と `status` のみで行う。`source` は
  **解約導線の出し分けにだけ使う**（§5.6）
- Webhook（Stripe / App Store Server Notifications / Google RTDN）は
  **すべて `Entitlement` を更新する1つの関数に集約**する

```ts
// これ1本に集約する
async function applyBillingEvent(event: NormalizedBillingEvent): Promise<void>
```

## 3. PWA化とインストール導線

**アプリを出す前に、これを先にやります。** 実装1〜2日で「敷居」の実質がかなり埋まります。

### 3.1 PWA の要件

- `manifest.webmanifest`（name / short_name / icons 192・512・maskable / display: standalone /
  theme_color / background_color / start_url）
- Service Worker（オフラインで**記録画面が開き、入力が保存できる**こと）
- オフライン時は IndexedDB に退避し、復帰時に同期。**画面に「保存されています」と明示**
- iOS Safari の制約（ストレージの揮発、バックグラウンド制限）を前提に、
  **重要なデータは可能な限り早くサーバへ送る**

### 3.2 インストール導線

**iOS の「ホーム画面に追加」は共有ボタン経由で、日本のユーザーはほぼ知りません。**
図解つきの案内を出します。

```
表示条件（すべて満たしたときに1回だけ）
  ・記録が3日以上ある
  ・スタンドアロン起動ではない（display-mode: standalone が false）
  ・過去にこの案内を閉じてから14日以上経っている
  ・案内の表示回数が3回未満
```

```
┌───────────────────────────────┐
│ ホーム画面に追加すると          │
│ 1タップで開けます              │
│                               │
│ ① 下の [ 共有 ] をタップ       │  ← iOS：図で示す
│ ② 「ホーム画面に追加」を選ぶ    │
│                               │
│        [ わかった ]  [ あとで ] │
└───────────────────────────────┘
```

- **iOS と Android で手順を出し分ける**
  （Android は `beforeinstallprompt` を捕まえてワンタップ）
- 追加済みの検出：`window.matchMedia('(display-mode: standalone)').matches`、
  iOS は `navigator.standalone`
- **追加済みの人には二度と出さない**

### 3.3 計測（アプリを出す判断のために必要）

| 指標 | 用途 |
|---|---|
| 案内の表示数 / 「わかった」率 | 導線の質 |
| スタンドアロン起動の割合（DAU比） | 実際のインストール率 |
| スタンドアロン起動ユーザーの継続率 vs ブラウザ | 「常駐」の効果測定 |
| 「アプリはないのか」という問い合わせ件数 | 需要の実測 |

## 4. ウェブ課金（Stripe）

### 4.1 実装範囲

- Checkout Session（サブスク、月額・年額）
- Customer Portal（支払い方法の変更、解約）
- Webhook（`customer.subscription.*`, `invoice.*`）→ §2.2 の集約関数へ
- **Webhook は冪等に。** 同じイベントが2回届いても状態が壊れないこと
  （`event.id` を保存して重複を弾く）
- Stripe Tax を有効化（将来の海外課金のため。国際展開仕様 §7）

### 4.2 特定商取引法：最終確認画面の必須項目

**サブスクをウェブで売る場合、申込みの最終確認画面に以下を表示する義務があります**
（2022年6月施行の改正）。IAP が肩代わりしてくれていた部分です。

- 分量（サブスクリプションの内容と提供される機能）
- **販売価格（税込）**
- 支払いの時期と方法
- 提供時期（決済完了後ただちに、など）
- **申込みの撤回・解除に関する事項**
- 定期購入である旨と、**契約期間・更新のタイミング**
- **解約の方法と条件**（どこから、いつまでに、どうすれば解約できるか）

**「規約を読めばわかる」では要件を満たしません。最終確認画面そのものに書きます。**

### 4.3 解約導線

- 設定 → プラン から**3タップ以内**で解約できること
- 解約後も期間末までは使えることを明示
- **解約の引き止めは1画面まで。** ダークパターンにしない
- 解約完了をメールで通知

## 5. ネイティブアプリ（まだ着手しない）

### 5.1 出す判断の基準

**次のいずれかを満たしてから検討します。** 感覚で決めない。

- PWA のインストール導線を出した後も、**スタンドアロン起動が DAU の 15% を超えない**
  （＝導線では埋まらない）
- 「アプリはないのか」という問い合わせが**月10件以上**
- **指導者プランの商談で、アプリの有無が理由で断られた事例が3件以上**
- 月間アクティブが 1,000 を超えた

### 5.2 技術選択

**Capacitor でウェブをラップする。** React Native への書き直しはしません。

- 1つのコードベースを維持する
- Web 側の更新がそのままアプリに反映される構成にする
  （ただしストア審査を経ない大幅な機能変更は避ける）

### 5.3 審査：最低限の機能要件

**「ウェブサイトを包んだだけ」のアプリはリジェクトされます。**
ネイティブらしい価値を**最低1つ、できれば2つ**持たせること。設計済みの素材から選べます。

| 候補 | 実装 |
|---|---|
| オフラインでの記録 | すでに Service Worker で実装済み。ネイティブ側で強化 |
| 録音（CPPS） | ネイティブのマイク権限。バックグラウンド不要 |
| ウィジェット | 「今日の声」を1枚。iOS / Android |
| ローカル通知 | 記録リマインド（LINE と併用ではなく、LINE 未連携の人向け） |
| ショートカット | 長押しで「30秒で記録」に直行 |

**推奨はウィジェット＋ショートカット。** どちらも「毎朝ひらく」設計と噛み合います。

### 5.4 審査：健康アプリとしての要件

**ストアの説明文とスクリーンショットも審査対象です。**
国際展開仕様 §5.2 の文言規則を、ストア掲載物にも適用してください。

- ✗ 「声帯のむくみを検知」「不調の原因を診断」「逆流の可能性を判定」
- ✓ 「声と体調の記録を、自分の平常値と比べて見られます」

必須のもの：

- プライバシーポリシーの URL（審査で必須）
- **医学的な診断ではない旨の免責**（アプリ内とストア説明文の両方）
- App Privacy（データ収集の申告）を正確に。**健康データの収集を申告する**
- 健康データを広告目的に使わない（使っていない旨を申告できる状態にする）
- 審査メモに「自己申告の記録を統計処理して表示するツールであり、
  診断・治療を目的としない」ことを明記して提出する

### 5.5 IAP の実装

- 個人プランのみ。**指導者プランはアプリ内で販売しない**（§1.1）
- StoreKit 2 / Google Play Billing を直接使うか、RevenueCat のような
  抽象化レイヤーを使うか。**どちらでも可だが、最終的な権利判定はサーバの
  `Entitlement`（§2）に集約すること**
- **App Store Server Notifications / Google RTDN をサーバで受け、
  `applyBillingEvent()` に流す**
- レシート検証はサーバで行う。クライアントで判定しない

### 5.6 ウェブ契約者がアプリを使う場合

**これが最も事故りやすい部分です。**

- ウェブで契約した人がアプリでログインしたら、**そのまま有料機能が使える**こと
  （`Entitlement` を見るだけなので、正しく実装されていれば自動的にこうなります）
- **その人にアプリ内で課金を促してはいけません。** 二重課金の元です
- 解約導線を `source` で出し分ける

```
source === 'stripe' → アプリ内から解約画面（ウェブ）へ
source === 'apple'  → 「解約は iPhone の設定からお願いします」＋手順
source === 'google' → 「解約は Google Play からお願いします」＋手順
```

- 「購入の復元（Restore）」を実装する（Apple の要件）

### 5.7 スマホ新法：併記の義務

**アプリ内で外部決済を提供する場合**、日本では
**IAP と外部決済を並べて示し、ウェブ価格も表示する**ことが求められます。

ただし §1.3 のとおり**外部決済は採用しない**ため、この義務は発生しません。
**アプリ内にウェブ課金へのリンクを置かないこと**を、実装上の規則として守ってください
（置いた瞬間に帰属期間と手数料が発生します）。

ウェブ側で契約してほしい場合は、**アプリ外（メール、LINE、サイト）で案内**します。

## 6. 絶対にやってはいけないこと

- ❌ アプリ内に「ウェブのほうが安い」と書いてリンクを置く
  （§1.3。中途半端がいちばん損をします）
- ❌ IAP の導線を意図的に劣化させる（審査でリジェクトされます）
- ❌ クライアントで課金状態を判定する（§2.2）
- ❌ アプリのバイナリに価格を埋め込む（改定のたびに審査）
- ❌ ストア説明文に診断・検知を連想させる表現を使う（§5.4）
- ❌ 解約を難しくする（特商法 §4.2、および審査）
- ❌ 指導者プランを IAP で売る（§1.1）

## 8. Sonnet 5 への依頼のコツ

- **`Entitlement`（§2）を最初に作らせる。** 課金の実装より先です。
  ここが後回しになると、Stripe と IAP の状態が二箇所に分かれて必ず壊れます
- Webhook は**冪等性を明示的な要件として書く**。「同じイベントが2回届いても
  状態が壊れないこと」と、そのままの言葉で伝えてください
- **クライアントで課金状態を判定させない**ことを、レビュー観点として毎回渡す
- 特商法の最終確認画面（§4.2）は**項目をそのままチェックリストとして渡す**。
  ドラフトは書けますが、**最終的な内容の妥当性は人間が確認**してください
- ストア掲載物の文言は、国際展開仕様 §5.3 のチェックリストで監査させる
- Capacitor のラップは、**「ウェブを表示するだけ」で終わらせない**ことを
  要件に明記する（§5.3 の候補から2つ選んで指定する）
