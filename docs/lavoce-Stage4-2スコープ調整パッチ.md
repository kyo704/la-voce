# La Voce ／ Stage 4-2（カスタマイズ）スコープ調整パッチ

記録項目v2 §4「カスタマイズの設計」の実装範囲について、
**縮小する判断を承認**したうえで、4点を修正するための指示書。

---

## 0. 結論

**「既存ユーザーの表示を意図せず変えない」という原則は正しい。** そのまま維持してください。
毎日使う習慣アプリで、ユーザーが頼んでもいないのに欄が消えるのは、
機能追加ではなく破壊です。

**「畳んだら戻せない」欠陥を自分で見つけて直す判断も正しい**（§2）。

修正は4点、確認が1点です。

| | 内容 |
|---|---|
| ✅ 承認 | 既存ユーザーの表示を変えない |
| ✅ 承認 | プリセットは新規ユーザーのみ |
| ✅ 承認 | 「畳んだ項目を戻す」UI を追加する |
| ✅ 承認 | 日別テンプレート・職業別分岐は今回見送る |
| 🔧 修正1 | **実装順を入れ替える**（戻すUI → プリセット） |
| 🔧 修正2 | **プリセットの対象を、全新規ユーザーに広げる** |
| 🔧 修正3 | 既存ユーザー向けの答えを **§4.3 の提案が担当**すると明示する |
| 🔧 修正4 | 日別テンプレートの**見送り理由を依存関係として記録する** |
| ❓ 確認 | **`collapsed` と `DetailConfig` が二重管理になっていないか**（§6） |

## 1. 修正1 ｜ 実装順を入れ替える

**「戻すUI」を先に、プリセットを後に。**

「戻すUI」は追加項目ではなく、**プリセットを安全にする前提条件**です。
畳んだ状態で出荷して戻す手段がなければ、
体重を記録したい新規ユーザーが永久にたどり着けません。

```
1. 畳んだ項目を戻すUI          ← 先
2. 動作確認（§1.2）
3. 新規ユーザー向けプリセット   ← 後
```

### 1.1 「戻す」UI の要件

各セクションの末尾、または記録画面の最下部に、常設の入口を置きます。

```
┌───────────────────────────────┐
│  ＋ 記録する項目を増やす        │  ← 常に表示。畳んだ項目が0件でも出す
└───────────────────────────────┘
```

押すとシート／画面が開き、**畳まれている項目の一覧**が出ます。

```
┌───────────────────────────────┐
│ 記録する項目             ✕    │
│                               │
│ 表示中                        │
│  ✓ 声の記録                   │
│  ✓ 睡眠                       │
│  ✓ 活動                       │
│  ✓ 心の余裕                   │
│                               │
│ 畳んでいる                    │
│  ＋ 食事の詳細                 │
│  ＋ 運動の詳細                 │
│  ＋ 体重・身体データ            │
│  ＋ 服薬                      │
│  ＋ 気持ちタグ                 │
│                               │
└───────────────────────────────┘
```

**要件**

- 畳んだ項目が0件でも、この入口を消さない（存在を知らせるため）
- 表示中の項目も一覧に出し、**ここから畳めるようにする**（双方向）
- 変更は即座に記録画面へ反映する
- **「戻す」操作で、過去に入力した値が失われないこと**（畳む＝非表示であって、削除ではない）

### 1.2 動作確認

プリセットに進む前に、必ず確認してください。

```
1. 項目を畳む → 記録画面から消える
2. 「記録する項目を増やす」から戻す → 記録画面に再表示される
3. 戻した項目に、過去に入力した値が残っている
4. 別の端末でログインしても、畳み方が同じ（§6.2）
```

## 2. 修正2 ｜ プリセットの対象を、全新規ユーザーに広げる

### 2.1 なぜ広げてよいか

**「新規ユーザーのみ」という安全策は維持したまま、対象だけ広げます。**

- **新規ユーザーには、壊れる既存の状態が存在しません**
- 唯一のリスク（欲しい項目にたどり着けない）は、**§1 の戻すUI で解消済み**

つまり、対象を絞ることで**追加の安全は得られていません。**
絞ると効果だけが減ります。

### 2.2 いまの案では効果がほとんど出ません

「『記録だけしたい』を選んだ人の、服薬タグと気持ちタグ詳細だけを畳む」では、

- その選択肢を選ぶ新規ユーザーは少数
- 畳む対象が2つだけで、80項目のうち2つ

**プリセットの目的は「新規ユーザーの最初の画面が80項目にならないこと」**です。
そこに届いていません。

### 2.3 変更後の既定

**全新規ユーザーに適用**します。

| | 項目グループ |
|---|---|
| **開いておく** | 声の記録／睡眠／活動／心の余裕 |
| **畳んでおく** | 食事の詳細／運動の詳細／体重・身体データ／服薬／気持ちタグ／水分の内訳／環境（自動取得が動いていれば） |

初回の記録画面が**10項目前後**になります。**これが本来の効果です。**

### 2.4 オンボーディングの回答による差分

記録項目v2 §4.1 の2問（職業・目的）は、**この既定からの差分**として使います。
ゼロから組み立てない。

```
既定（§2.3）を土台に、回答に応じて開く項目を足す

  goalFocus === 'train'    → 体重・身体データ を開く
  goalFocus === 'peak'     → 環境 を開く
  goalFocus === 'log_only' → 既定のまま（何も足さない）
  profession に 'classical' → 活動の曲目欄を開く
```

**差分方式にすることで、プリセットが増えても既定が壊れません。**

## 3. 修正3 ｜ 既存ユーザーへの答えは §4.3 が担当する（明示する）

「既存ユーザーには一切影響なし」は正しい判断ですが、
**80項目問題が既存ユーザーには残ったまま**です。

これは放置ではなく、**別の仕組みが担当する**と整理してください。

| 対象 | 仕組み | 性質 |
|---|---|---|
| **新規ユーザー** | プリセット（§2） | こちらが決める。最初から少ない |
| **既存ユーザー** | **§4.3 の「畳みますか？」提案** | アプリから声をかけ、**本人が決める** |

§4.3 は実装済みとのことなので、**役割分担はすでに成立しています。**

**この整理を、コード内のコメントか `docs/` に明記してください。**
書いておかないと、後日「既存ユーザーにもプリセットを当てるべきでは」という
議論が再燃し、同じ危険を繰り返します。

## 4. 修正4 ｜ 日別テンプレートの見送り理由を、依存関係として記録する

見送りの判断は正しいですが、**理由の記述が不正確**です。

> ✗ 「職業別設計そのものに踏み込む規模のため」
> ✓ **「活動ブロックの複数化（実行順マスター Stage 5-2）に依存するため」**

曲目複数化パッチ §2.0.1 で、テンプレートは
**「1つ目の活動ブロックの種別を選ぶショートカット」に降格**しました。

つまり、**活動ブロックが複数化されていない状態でテンプレートを作ると、
Stage 5-2 のあとに作り直しになります。**

**記録**：`docs/` またはタスク管理に、次の形で残してください。

```
日別テンプレート（記録項目v2 §4.4）
  状態：保留
  理由：活動ブロックの複数化に依存（曲目複数化パッチ §2.0.1）
  再開：実行順マスター Stage 5-2 の完了後
```

「規模が大きいから」と書くと、**いつ戻ってくるかが分からなくなります。**

## 6. 確認事項 ｜ 状態が二重になっていないか

**技術的に、ここが一番の懸念です。**

記録項目v2 では **`DetailConfig`（`0` = 記録しない ／ `1` = 簡易 ／ `2` = 詳細）** を
定義しました。一方 §4.3 では「畳む」の仕組みを作っています。

### 6.1 まず確認すること

**`collapsed: boolean` と `detail: 0|1|2` が、別々の状態として存在していませんか。**

**並存している場合は、いまのうちに統合してください。**
小さいうちなら半日ですが、Stage 4-2 の残りをこの上に積むと、
**「畳んだのに詳細度は2のまま」のような矛盾**が出て、あとで解けなくなります。

統合は `detail` に寄せるのが自然です。

```ts
type Detail = 0 | 1 | 2   // 0 = 畳んだ状態（= 記録しない）と同義

// collapsed は廃止し、detail === 0 で表現する
const isCollapsed = (g: FieldGroup) => detailConfig[g] === 0
```

**判定は1箇所のフックに集約**してください（記録項目v2 §3.3 の要件）。

```ts
const { visible, level } = useFieldGroup('meal')
```

### 6.2 保存先の確認

**畳んだ状態は、サーバに保存されていますか。**

`localStorage` だと、機種変更や PC ↔ スマホの切り替えで畳み方が失われます。
**毎日使い、端末をまたぐアプリなので、サーバに持つべきです。**

`localStorage` になっている場合は、**プリセットを載せる前に移してください。**
プリセットを先に載せると、「新しい端末で開いたら項目が全部出ている」という
分かりにくい挙動になります。

- **§1（戻すUI）を先に、§2（プリセット）を後に。** 順序を入れ替えさせない
- **§1.2 の動作確認4項目を、実際に通してから**プリセットに進ませる
- **§6 の確認を先に済ませる。** 二重管理が見つかったら、
  プリセットより先に統合する
- プリセットは **§2.3 の既定を土台に、§2.4 の差分方式**で。
  オンボーディングの回答ごとにゼロから組ませない

- §4 の保留理由は「規模」ではなく「依存関係」として記録させる
