# La Voce ／ レッスンモードの解体と「レッスン前後」の設計

**Claude Sonnet 5 へ。この文書は「レッスンモード」という画面を廃止し、その中身をレッスンの前後の導線に置き換えるための仕様です。**

読む順番：**統合実行ルート v4** → 本書 → レッスン連絡パッチ → 教師間コミュニケーション仕様。

**本書は機能を追加する文書ではありません。減らす文書です。**
実装量は減りますが、消す判断のほうが難しいので、§1-3 の「まず報告する」から始めてください。

---

## 0. 結論

```
① レッスン「中」に生徒が操作する機能は、全部やめます。
② 1時間のレッスン録音は作りません。音声を保存する設計そのものを持ち込みません。
③ 動画の姿勢・口の形の自動評価は作りません。
④ 代わりに「レッスン直後の90秒」「次回レッスンの30分前」「レッスン翌日」の
   3つの瞬間に機能を置きます。
```

**「レッスンモード」という名前の画面は、実装から消してください。**

---

## 1. なぜ「レッスン中」の機能を作らないのか

### 1-1｜生徒の手と意識が空いていない

レッスン中、生徒は歌っているか、聴いているか、先生の顔を見ています。
**この状態でスマホを操作する機能は、どれだけ設計が良くても使われません。**

これは「使いやすくすれば解決する」種類の問題ではありません。
**物理的に手が塞がっている**ので、UI の改善では解決しません。

### 1-2｜★先生の前でスマホを触らせる設計は、流通経路を壊す

統合実行ルート v4 の **G3.5「指導者経由で広げる」**を思い出してください。
La Voce は先生から生徒へ広がる設計です。

**レッスン中に生徒がスマホを触るアプリは、先生に嫌われます。**
先生に嫌われたら、招待が止まります。招待が止まったら、G3.5 が機能しません。

**先生の側から見て「レッスンの邪魔をしないアプリ」であることが、成長の条件です。**

### 1-3｜★最初にやること：現状の棚卸し（実装の前）

**私（Sonnet）は、コードを消す前に、次を報告してください。**

```
□ 現在「レッスンモード」と呼ばれている画面／コンポーネントのファイルパス
□ その中にある機能を1行ずつ列挙
□ それぞれについて、DBに書き込みがあるか（あるなら既存データの件数）
□ それぞれについて、他の画面から参照されているか
```

**この一覧を坂本さんに見せて、承認を得てから削除してください。**
既存ユーザーのデータが入っている機能を黙って消さないこと。
消す場合も、**データは残したまま画面だけ外す**（`deletedAt` を立てる、など）。

## 2. ★1時間のレッスン録音を作らない、4つの理由

「レッスンを1時間録音して音声解析する」という案は、価値がないのではなく、
**4つの問題が同時に来ます。** どれか1つでも実装を止めるだけの重さがあります。

### 2-1｜保存が持たない

```
1時間の音声 = 圧縮しても 30〜60MB
週1回 × 52週 = 年間 1.5〜3GB / 人
```

無料枠では成立しません。有料でも、ストレージ費用が課金額を食います。

### 2-2｜★録音には必ず先生の声が入る（第三者の音声）

生徒が同意しても、**先生は同意していません。**
そして先生の指導内容は、**先生の営業資産**です。

「録音されている」と分かった時点で、指導の質を落とす先生が出ます。
これは 1-2 と同じで、流通経路を壊します。

### 2-3｜★要配慮個人情報が確実に混入する

レッスン中の会話には、次が普通に含まれます。

```
「今日は喉の調子が悪くて」
「先週、耳鼻科で声帯結節と言われました」
「生理前でいつも高音が出にくい」
```

**これらは要配慮個人情報です。** 音声として保存した時点で、
明示的な事前同意・第三者提供のオプトアウト不可・漏えい時の PPC 報告義務がかかります。

**いま CPPS を「録音して即座に破棄する」設計にしているのは、まさにこれを避けるためです。**
（統合実行ルート v4 §3 ガードレール「CPPS録音即時破棄」）

**1時間保存は、このガードレールを正面から破ります。**

### 2-4｜そして一番大きい理由：録っても聴き返さない

1時間の音声を後から聴き返す人は、ほとんどいません。
レッスン録音アプリが定着しない理由がこれです。

**録音は「安心して忘れるための行為」であって、「思い出すための行為」ではありません。**

## 3. ★音声から取りたい数字はある。ただし v1 では音声を使わない

### 3-1｜本当に欲しいのは2つだけ

```
① レッスン中に生徒が実際に声を出していた時間（分）
② その日出た最高音・最低音
```

**そして①②は、音声を1バイトも保存せずに取れます。**
端末の中で実時間処理して、数字だけ残す。音声はマイクから出た瞬間に捨てる。

**カレンダー連携（freeBusy）と同じ考え方です — 権限で隠すのではなく、取得しないことで守る。**

### 3-2｜★しかし技術的な壁がある：先生と生徒の声は分離できない

**正直に書きます。レッスン室で、先生のお手本と生徒の声を機械的に分離することはできません。**

- 先生が範唱すれば、それも「発声」としてカウントされます
- 声域が違えばある程度は分けられますが、**同性の師弟では不可能です**
- 話者分離（diarization）はブラウザ上では実用的な精度が出ません

**この壁を無視して実装すると、「レッスン中の発声時間 55分」のような明らかに間違った数字が出ます。**
そして負荷モデル（`songFactor`、EWMA ACWR）に直接効くので、**分析全体が壊れます。**

### 3-3｜★だから v1 では、音声を使いません

代わりに、**掛け算で推定します。**

```
レッスン発声時間（推定） = 実レッスン時間（分） × 自己申告の割合
```

自己申告は**一度だけ**、次の3択で聞きます。

```
レッスン中、自分が声を出しているのはどれくらいですか？
 ○ 3割くらい（先生の話を聞く時間が長い）
 ● 5割くらい                        ← 既定
 ○ 7割くらい（ほとんど歌っている）
```

60分 × 0.5 = **30分**。

**素朴な音声解析より精度が悪いということはありません。**
電池も食わず、マイク権限も要らず、privacy の問題もゼロです。

**音声解析は、これの精度を上げる「改良」であって、土台ではありません。**
v2 以降で、単独練習（先生がいない＝分離問題が無い）の場面から導入してください。

## 4. ★動画の自動評価を作らない、3つの理由

### 4-1｜科学的な根拠が弱い

姿勢や口の開き方と発声の質の関係は、**定量的な閾値が確立していません。**
「口を大きく開ける」が正しいかどうかは、発声法・流派・曲種で割れます。

統合実行ルート v4 §3 のガードレール「**文献閾値は学ぶ記事のみ**」に照らして、
**アプリが動画から「良い／悪い」を判定することはできません。**

### 4-2｜★先生の指導と矛盾したときに、生徒が壊れる

アプリが「口の開きが足りません」と出し、先生が「開けすぎ」と言ったとき、
生徒は必ず混乱します。そして多くの場合、**アプリを信じます**（数字が出ているから）。

**アプリが先生に口出しする構造を作らないでください。** これは 1-2 と同じ問題です。

### 4-3｜先生の肖像と指導方法が映る

2-2 と同じです。動画のほうが重い。

### 4-4｜「撮るだけ」なら意味はある。ただし v1 では作らない

生徒が自分のために動画を撮ること自体は有益です。ただし：

```
・端末の中だけに置く。サーバーにアップロードしない
・解析しない。表示するだけ
・そして正直に言えば、これは iPhone の標準カメラで足りている
```

**v1 では作りません。** 作るとしても v3 以降、明確な要望が出てからです。

## 5. 作るもの ①：★レッスン直後の90秒

**ここが本命です。**

### 5-1｜なぜこの瞬間なのか

```
・記憶が最も鮮明
・気分が高い（レッスンが終わった解放感）
・移動時間があり、手が空く
・そして翌日には8割忘れている
```

**生徒が本当に困っているのは、「レッスンで言われたことを翌日には忘れていること」です。**
レッスンモードの全部を、ここに集中させます。

これは「記録と分析の順番設計」§3.5 の**「保存した直後の報酬」**と同じ設計思想です。
統合実行ルート v4 §2 の「評価が決まる4つの瞬間」の②に接続します。

### 5-2｜置くのは3つだけ

```
┌─ 今日のレッスン ──────────────────────┐
│                                                │
│  言われたこと（3つまで）                       │
│  ┌──────────────────────────┐  │
│  │ 🎤 話して入力                        │  │
│  └──────────────────────────┘  │
│  ① _______________________________          │
│  ② _______________________________          │
│  ③ _______________________________          │
│                                                │
│  次までにやること（1つ）                       │
│  ___________________________________          │
│                                                │
│  声の感じ                                      │
│   ○──○──●──○──○                        │
│  重い          ふつう          軽い            │
│                                                │
│           [ 保存する ]                         │
└────────────────────────────────┘
```

**4つ目を足さないでください。** 増やすと書かれなくなります。

**入力仕様**

| 項目 | 型 | 上限 | 必須 |
|---|---|---|---|
| キーワード | string[] | 3件 × 各40字 | 任意 |
| 宿題 | string | 1件 120字 | 任意 |
| 声の体感 | 1〜5 | — | 任意 |

**全部任意です。** 1つも書かずに閉じても、レッスンの記録自体は残ります。

### 5-3｜★音声入力を既定にする

移動中に打つのは無理です。**Web Speech API を使い、マイクボタンを最初から見せてください。**

```
・認識結果はそのままテキスト欄に入る。編集できる
・音声そのものは保存しない（§2 と同じ原則）
・非対応ブラウザではボタンを出さない（キーボード入力のみ）
```

### 5-4｜★「学ぶ画面」のメモ機能を再利用する

**新しいメモ機能を作らないでください。**
「職業別項目の再設計と学ぶ画面.md」§7 で設計したメモ用コンポーネントを、そのまま使ってください。

保存先のテーブルは分けます（下の §9）が、**入力 UI は共通**にしてください。
2つ作ると、片方だけ改善されてズレていきます。

### 5-5｜★既定では先生に見せない

**これが一番重要な設計判断です。**

```
LessonReflection.sharedWithTeacher = false   ← 既定
```

**理由：先生に読まれると分かっている欄には、生徒は「先生が喜ぶこと」を書きます。**

「記録と分析の順番設計」で扱った、
**主観と客観を同じ流れに置くと、片方から片方を推測してしまう**問題と同じ構造です。
先生の目が入ると、振り返りは記録ではなく報告になり、データとして死にます。

**共有は、項目ごとに生徒が個別にオンにできる形にしてください。**
宿題だけ共有したい、というのは自然な要求です。キーワードと体感は既定で非共有のままにします。

### 5-6｜保存直後

羊が反応します（「羊のおうち仕様.md」のスタンプ演出を流用）。
**ポイントは記録に対してのみ付きます**（ガードレール「ポイントは記録のみ」）。
**書いた内容の中身では、絶対にポイントを変えないでください。**

### 5-7｜いつ出すか

```
① 先生が「レッスン終了」をタップした直後（G5-31 がある教室）
② カレンダーのレッスン終了時刻（連携がある場合）
③ 手動（レッスン画面の「振り返りを書く」ボタン）
```

**プッシュ通知は 22:00〜08:00 は送りません**（教師間コミュニケーション仕様 §6 と同じ規則）。
夜21:30 に終わるレッスンでは、**アプリを開いたときに画面上部に出す**方式にしてください。
通知が送れないことと、機能が使えないことは別です。

## 7. 作るもの ③：★レッスン翌日の声の調子

**これが La Voce にしか作れないデータです。**

```
「あなたはレッスンの翌日に調子が落ちるタイプです」
「あなたはレッスンの翌日のほうが調子が良いタイプです」
```

他のレッスン管理アプリも、他の音声アプリも、これは出せません。
**日々の声の記録とレッスン日程の両方を持っているのは La Voce だけだからです。**

### 7-1｜★表示ゲートを必ず通す

統合実行ルート v4 **§6 の3ゲート**を、例外なく適用してください。

```
① 件数    レッスン翌日 n ≥ 10、かつ非レッスン翌日 n ≥ 10
② 効果量  |Hedges' g| ≥ 0.4
③ 多重比較 BH-FDR で q < 0.10
```

**1つでも欠けたら、文章を出さないでください。** 数字も出さないでください。
「まだ判定できません（あと◯回）」とだけ表示します。

### 7-2｜負荷モデルへの接続

推定したレッスン発声時間は、**本番外の発話時間**に入ります。
そこから先の計算は既存のままです。

```
★ EWMA ACWR（λa = 2/8、λc = 2/29）は変更しないこと。
★ rolling 7/28 に書き換えないこと。
★ songFactor / strain / KAPPA = 0.6 も変更しないこと。
```

### 7-3｜二重計上を防ぐ

生徒が同じ日に発話時間を手入力した場合、**黙って足さないでください。**

```
┌────────────────────────────────┐
│ レッスン分（推定30分）が自動で入っています。   │
│ 手で入れた45分と、二重になっていませんか？     │
│   [ 合計75分にする ]  [ 手入力の45分だけにする ]│
└────────────────────────────────┘
```

自動で入った分は `source: 'auto'` として別行で保持し、**生徒が消せるようにしてください。**

### 7-4｜「推定」であることを画面に出す

```
レッスンでの発声：約30分（推定）
　60分 × 5割 で計算しています  [ 割合を変える ]
```

**「約」と「推定」を省略しないでください。**
そして**生徒が実測値で上書きできるようにしてください**（`overriddenMinutes`）。

## 8. 先生の範唱30秒（v2 以降）

生徒が本当に欲しがる音声は、**1時間のレッスンではなく、先生のお手本30秒**です。
短く、目的が明確で、何度も聴き返します。

ただし §2-2 の問題があるので、**先生側にスイッチを置きます。**

```
・先生の画面に「録音を許可」トグル（既定オフ）
・オンの間だけ、生徒の画面に録音ボタンが出る
・上限30秒。1レッスンあたり3本まで
・先生はいつでも削除できる（生徒の端末からも消える）
・教室プランの管理者は、教室単位で一括オフにできる
```

**v1 では作りません。** G5 が終わってから着手してください。

## 9. データモデル

```ts
interface LessonReflection {
  id: string
  lessonId: string            // 教室プラン仕様の Lesson
  studentUserId: string
  keywords: string[]          // 最大3、各40字
  homework?: string           // 120字
  feel?: 1 | 2 | 3 | 4 | 5    // 声の体感
  homeworkDone?: boolean      // §6 の「できた / まだ」
  sharedKeywords: boolean     // 既定 false
  sharedHomework: boolean     // 既定 false
  sharedFeel: boolean         // ★常に false。UI も出さない
  createdAt: string
  updatedAt?: string
  deletedAt?: string
}

interface LessonVoiceEstimate {
  lessonId: string
  studentUserId: string
  actualMinutes: number          // 開始終了 or カレンダー or 予定時間
  minutesSource: 'lessonRun' | 'calendar' | 'scheduled'
  ratio: 0.3 | 0.5 | 0.7         // 生徒の自己申告
  estimatedMinutes: number       // actualMinutes * ratio
  overriddenMinutes?: number     // 生徒が実測で上書きした場合
  writtenToVoiceLog: boolean
}
```

**`sharedFeel` は型の上では持ちますが、常に false で、UI を作らないでください。**
体感は主観データなので、先生に見せた瞬間に §5-5 の問題が起きます。
将来「共有したい」と言われたときに議論できるよう、列だけ残します。

**RLS**

```
LessonReflection の SELECT：
  ・本人（studentUserId = auth.uid()）は常に読める
  ・担当教師は、shared◯◯ が true の項目だけ読める
    → ★行ごとではなく「列ごと」の制御が必要。
      ビューを作って、shared が false の列は NULL を返すこと
  ・教室の管理者は読めない（健康の面。教室プラン仕様 §3 の分離に従う）
```

## 11. ★禁止事項

```
1.  レッスン中に生徒が操作することを前提にした機能を作らない
2.  レッスンの音声を保存しない（長さを問わず）
3.  レッスンの動画を保存・解析しない
4.  マイクから取った音声を、数値化した後もメモリに保持し続けない
5.  ★先生と生徒の声を分離できるかのような表示をしない
6.  推定値を「推定」と書かずに出さない
7.  ★体感（feel）を先生に見せる導線を作らない
8.  振り返りの中身でポイント・羊の反応を変えない（記録した事実だけで変える）
9.  ★3ゲートを通っていないレッスン関連の分析文を出さない
10. EWMA ACWR のλを変えない。rolling 7/28 にしない
11. 自動で入った発声時間を、手入力に黙って合算しない
12. 先生に「レッスン内容を入力させる」機能を作らない（先生の負担＝離脱）
13. 振り返りの未記入を、生徒への催促に使わない（3回連続で未記入なら出すのをやめる）
14. 既存のレッスンモードのデータを、坂本さんの承認なしに削除しない
```

**13 について：** 記録が続かない人ほど、催促で離れます。
