## 1. 「既定値の混入」とは、具体的に何か

### 原因（★もう直っています）

`newVoiceEntry()` が、新しい声の記録を作るときに
**`bodyFeel: 3` と `quality: 5` を最初から入れていました。**

スライダーに一度も触らずに保存すると、
`throat_condition = 3` と `resonance_score = 5` が
**「記録された値」としてデータベースに書かれていました。**

d420db4 のコミットメッセージより:

> throatCondition はこのアプリで最も多く読まれる項目（33か所）で、
> 静かに嘘のデータが広がる形になっていた。

d420db4 で、両方 `null` で始まるように直しました。
**★今日 08:15 以降に作られた記録は、きれいです。**

### 残っているもの（★これが⑤）

**08:15 より前に書かれた行には、その既定値がそのまま残っています。**
本人が答えた「3」と、触らずに入った「3」は、見分けがつきません。

`throat_condition` は約33か所から読まれます。偏差値、相関、
表示ゲートの n の数え上げ——いま全部が、この値を本物として
読んでいます。

### ★いちばん厄介な性質

**行ごとに「これは既定値だ」と証明できません。**

- `throat_condition = 3` かつ `resonance_score = 5` は**疑わしい**だけです。
  本当にそう答えた人がいてもおかしくありません。
- 目印の列がありません。
- `entries` に `updated_at` がありません。

使える手がかりは、**d420db4 の時刻（2026-08-28 08:15 JST）**だけです。
それ以前に作られた行は「混入しているかもしれない」、
それ以降は「混入し得ない」。それだけが確かです。

## 2. 先に数えてください（★決める前に）

職業のときの §6 と同じ順番です。数字が無いまま規則を決めません。

```sql
-- ============================================================
-- ⑤ 既定値混入の広がりを数える（★読み取りだけ。何も変えません）
--   基準の時刻: d420db4 = 2026-08-28 08:15:16 JST

-- ① 全体の内訳
select
  count(*)                                                as "記録の総数",
  count(*) filter (where created_at < '2026-08-28 08:15:16+09') as "基準より前",
  count(*) filter (where created_at >= '2026-08-28 08:15:16+09') as "基準より後（きれい）"
from public.entries;

-- ② 基準より前の行のうち、既定値そのものが入っているもの
--    ★「疑わしい」だけです。本当にそう答えた人も含まれます。
select
  count(*) as "基準より前の行",
  count(*) filter (where throat_condition = 3)                    as "喉が3",
  count(*) filter (where resonance_score = 5)                     as "響きが5",
  count(*) filter (where throat_condition = 3 and resonance_score = 5) as "両方（★これが本命）",
  -- ★2026-08-28 修正。前の版は、ここに voice_quality is null を入れていました。
  --   voice_quality は resonance_score から導出される列です
  --   （VocalTracker.jsx:1660 voiceQuality = intOrNull(quality10ToFiveScale(rep.quality))、
  --    quality10ToFiveScale(q) = 1 + (q/10)*4 なので、5 → 必ず 3）。
  --   つまり resonance_score = 5 のとき voice_quality は絶対に null になりません。
  --   条件が最初から成立せず、★必ず 0 が返ります。実際に0が出て、
  --   「4件とも本人が答えたものだ」と誤って読みかけました。
  --   導出された列を「触っていない証拠」に使わないこと。
  count(*) filter (where throat_condition = 3 and resonance_score = 5
                     and (sleep_hours is not null
                          or activity_type is not null
                          or meals is not null))
    as "両方＋声以外は記録している（＝スライダーだけ触っていない疑い）"
from public.entries
where created_at < '2026-08-28 08:15:16+09';

-- ③ 比較のため、基準より後で同じ値がどれくらい出るか
--    ★後の期間にも「3と5」が普通に出るなら、②の多くは本物です。
select
  count(*) as "基準より後の行",
  count(*) filter (where throat_condition = 3 and resonance_score = 5) as "両方"
from public.entries
where created_at >= '2026-08-28 08:15:16+09';

-- ④ 何人に関わるか
select count(distinct user_id) as "影響を受けうる人数"
from public.entries
where created_at < '2026-08-28 08:15:16+09'
  and throat_condition = 3 and resonance_score = 5;
```

★`entries` に `created_at` が無い場合は ① が失敗します。
　そのときは `date` 列で切ってください（精度は落ちます）。

## 4. ★どの案を採るにしても守ること

1. **保存された値を消さない・書き換えない。**
   除外するのは**分析の読み取り側だけ**です。
   本人の書き出しと削除には、これまでどおり全部含めます。
   d420db4 自身も `computeEntryPointsLegacy` を残しています
   （「変えると過去が書き換わる」ため）。同じ理由です。

2. **★除外は必ず `lib/displayGates.js` を通すこと。**
   行を落とすと、群ごとの n が変わります。ゲートは n ≥ 10 を
   要求しているので、ゲートの外で落とすと、
   画面に出す n と、その裏のデータが食い違います。
   このリポジトリが繰り返してきた壊れ方そのものです。

3. **除外したことを、利用者に見える形で言わない。**
   「あなたの記録の一部は使っていません」と出すと、
   何が悪かったのかを説明できません。内部の扱いに留めます。

# 実行の結果と、決めたこと（2026-08-28）

## 数えた結果

```
     喉が3                   8
     響きが5                 5

```

## ★「0」は証拠ではありませんでした

`voice_quality is null` を「ほかの項目を触っていない証拠」として
使っていましたが、この列は `resonance_score` から導出されます。
`resonance_score = 5` なら `voice_quality` は必ず 3 になり、
null にはなりません。**条件が成立しないので、必ず0が返ります。**

★この0を見て「4件とも本人の回答だ」と読みかけました。
　導出された列を、入力の有無の判定に使わないこと。

## 決めたこと: **C（いまは何もしない）**

理由は、混入が無いからではありません。**データが少なすぎて、
そもそも文章が1つも出ていないから**です。

- 記録は全部で **16行**（前15・後1）
- `lib/displayGates.js:22` が `NARRATIVE_MIN_N_PER_GROUP = 10`
- 群比較は**両群とも** n ≥ 10 が要る。16行では成立しません
- 分析は本人1人ぶん（N-of-1）なので、1人あたりはさらに少ない

**いま、この混入が影響している表示は1つもありません。**
ゲートが既に止めているものを守るために、本物の回答を巻き添えに
する仕組みを入れるのは、割に合いません。

★ただし 15件中4件（27%）は低くありません。
　人数が増えたときに効いてきます。「いまはやらない」であって
　「やらない」ではありません。

## いつ数え直すか

**15〜20人に配ったあと。** ③（基準より後）が1行では、
比べる相手がありません。配布後なら、基準より後のデータが
まとまって出るので、④の比較が初めて意味を持ちます。

★混入した期間は1日で、すでに閉じています。
