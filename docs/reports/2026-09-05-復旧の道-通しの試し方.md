## §0 ★先に、正直なこと

```
★私は、実機で試せません。★ブラウザも、データベースへの接続も持っていません。
★★だから、★「通りました」とは書けません。
　★下は、★コードを1行ずつ辿って、★そうなるはずだ、と言っているだけです。
```

★★そして、★1つだけ、★私が確かめられない分かれ道があります（§3）。
　★そこで止まる可能性が、いちばん高いです。★先に書いておきます。

## §1 試す手順

```
★別のアドレスを2つ、ご用意ください（★どちらも、いま受け取れるもの）。
　　A … 登録に使う
　　B … 付け替え先
```

```
① 新しく登録する
   /hajimeru →「はじめる」→ A で登録
   → 番号が A に届く → 入れる
   → ★★控えの番号が出ます。★書き写してください
   　　（★「書き写しました」を押すまで、進めません）

② いったん出る
   /shindan →「出て、もう一度確かめる」
   → ★「★入っていません」になること

③ 付け替える
   /login →「パスワードをお忘れの方は」
   → ★その下の「メールそのものが使えない方は、こちら」
   → /recovery
       いままでのアドレス          A
       控えの番号                  ①で書き写したもの
       これから使うアドレス        B
       もう一度、これから使うアドレス  B
   →「付け替える」

④ ★★ここが、いちばん見たいところです
   → ★「新しいアドレスに、番号を送りました。」の画面が出ること
   → ★★B に、番号が届くこと
   → ★番号を入れるまで、★中に入れないこと
   → 入れたら、/dashboard に入れること

⑤ お知らせが届くこと（§7）
   → ★A と B の両方に「メールアドレスが変わりました」
   → ★本文のアドレスが、伏せてあること（sa＊＊＊＊＊＊@…）
```

## §2 ★見ていただきたい「起きてはいけないこと」

```
✕ ④で、★番号を聞かれずに /dashboard に入ってしまう
　　→ ★★これが起きたら、★直っていません。すぐ教えてください

✕ ③で、2つのアドレスが違うのに「付け替える」が押せる
✕ 同じ控えの番号で、★2回目も通ってしまう
✕ 控えの番号を1文字変えたのに、★通ってしまう
✕ ★合っていないのに「登録されていません」と出る
　　→ ★誰が使っているかを、調べられてしまいます
```

## §3 ★分かれ道は、詰めました（★2026-09-05 夜・追記）

★はじめ、★ここで止まるかもしれない、と書きました。★詰めました。

```
（前）email_confirm: false
（いま）★email_confirm: true
```

★理由。★噛み合っていませんでした。

```
★false のとき、そのアドレスは「まだ確かめていない」状態です。
　★その状態で番号を頼むと、Supabase は
　★★「登録の確認」の側の番号を送ります。
　★こちらの画面は「ログインの番号」として受けています。
　★★番号が届いても、通らない形でした。

★true にすると、★「ログインの番号」が送られ、★受かります。
```

★★安全は、落ちません。

```
★この印が決めるのは「★どちらの番号を送るか」だけです。
★★入れるかどうかを決めるのは、★番号そのものです。
　★番号を入れるまで、★セッションは1つも作られません
　（この経路は、cookie を1行も触りません）。
★打ち間違いは、★画面で2回入れていただくことで止めています。
```

★★それでも、★私は動かして確かめていません。
　★④で番号が届かない、または★入れても通らないときは、
　★そのまま教えてください。★次の手を出します。

## §4 ★そのほか、いま分かっていること

```
□ 出る（signOut）は、正しく動いています ★2026-09-05 夜・実機で確認ずみ
□ redeem は、★セッションを作りません（cookie も token も1行も触っていません）
□ 打ち間違いは、★2回入れていただく形で止めています
□ 控えは1回きり。★使ったら、その場で閉じます
□ 付け替えに失敗したら、★控えを戻します（★使えない控えを残さない）
□ お知らせは、★新旧の両方へ。★送れなくても、付け替えは止めません
```
