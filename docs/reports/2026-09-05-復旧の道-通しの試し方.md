★私は、実機で試せません。★ブラウザも、データベースへの接続も持っていません。

## §1 試す手順

```
★別のアドレスを2つ、ご用意ください（★どちらも、いま受け取れるもの）。
　　A … 登録に使う
　　B … 付け替え先
```

```
① 新しく登録する
   /hajimeru →「はじめる」→ A で登録
   → 番号が A に届く → 入れる
   → ★★控えの番号が出ます。★書き写してください
   　　（★「書き写しました」を押すまで、進めません）

② いったん出る
   /shindan →「出て、もう一度確かめる」
   → ★「★入っていません」になること

③ 付け替える
   /login →「パスワードをお忘れの方は」
   → ★その下の「メールそのものが使えない方は、こちら」
   → /recovery
       いままでのアドレス          A
       控えの番号                  ①で書き写したもの
       これから使うアドレス        B
       もう一度、これから使うアドレス  B
   →「付け替える」

④ ★★ここが、いちばん見たいところです
   → ★「新しいアドレスに、番号を送りました。」の画面が出ること
   → ★★B に、番号が届くこと
   → ★番号を入れるまで、★中に入れないこと
   → 入れたら、/dashboard に入れること

⑤ お知らせが届くこと（§7）
   → ★A と B の両方に「メールアドレスが変わりました」
   → ★本文のアドレスが、伏せてあること（sa＊＊＊＊＊＊@…）
```

## §2 ★見ていただきたい「起きてはいけないこと」

```
✕ ④で、★番号を聞かれずに /dashboard に入ってしまう
　　→ ★★これが起きたら、★直っていません。すぐ教えてください

✕ ③で、2つのアドレスが違うのに「付け替える」が押せる
✕ 同じ控えの番号で、★2回目も通ってしまう
✕ 控えの番号を1文字変えたのに、★通ってしまう
✕ ★合っていないのに「登録されていません」と出る
　　→ ★誰が使っているかを、調べられてしまいます
```

## §3 ★★私が確かめられない、1つの分かれ道

★③で付け替えるとき、★アドレスを「まだ確かめていない」状態にしています。

```
admin.auth.admin.updateUserById(user.id, {
  email: newEmail,
  email_confirm: false      ← ★ここです
})
```

★★狙い ── ★確かめは、このあとの番号でします。
　★ここで「確かめ済み」にすると、★誰のものか分からないアドレスが確定します。

★★ですが、★Supabase が、
　★「まだ確かめていないアドレスには、番号を送らない」
　★という作りだった場合、★④で番号が届きません。

★私は、Supabase の中の作りを、★実際に動かして確かめていません。

### ★もし④で番号が届かなかったら

★★それは、★この分かれ道が原因です。★直し方は1行です。

```
email_confirm: false   →   email_confirm: true
```

★安全は落ちません。★★入るには、★どのみち番号が要るからです。
　★この印は「送ってよいか」を決めるだけで、★入れるかどうかは番号が決めます。

★★届かなかったら、★そう教えてください。★その場で変えます。
　★★推測で先に変えません。★どちらが正しいか、★見てから決めます。

## §4 ★そのほか、いま分かっていること

```
□ 出る（signOut）は、正しく動いています ★2026-09-05 夜・実機で確認ずみ
□ redeem は、★セッションを作りません（cookie も token も1行も触っていません）
□ 打ち間違いは、★2回入れていただく形で止めています
□ 控えは1回きり。★使ったら、その場で閉じます
□ 付け替えに失敗したら、★控えを戻します（★使えない控えを残さない）
□ お知らせは、★新旧の両方へ。★送れなくても、付け替えは止めません
```
