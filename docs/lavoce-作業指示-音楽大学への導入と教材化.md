# 作業指示｜音楽大学への導入と、「音楽家の商い」の教材化

**Claude Sonnet 5 へ。G4 で作るものの設計です。★いま着手しないでください。**

**最初の1校が具体的になってから着手します。** 先に作ると、使われない機能が増えます。
本書は「そのときに何を作るか」を決めておくためのものです。

読む順番：教室運営の範囲とカレンダー書き出し.md → 課金の器と無料枠.md → 本書。

## 0. 前提となる営業の形

```
音大は★複数の学科でできています。
全学に売ろうとすると、稟議が通りません。

有料の席   ★声を使う学科ぶんだけ
           （声楽科・ミュージカル科・音楽教育科・ポピュラー科）
無料で開放  ★それ以外の学科の学生も、記録と「学ぶ」は使える
           分析だけがプレミアム

大学は「全学生が使える」と言えて、費用は声を使う学科ぶんだけ。
```

**この形を成り立たせることが、本書の目的です。**

---

## 1. 結論

```
① 大学 → 学科 → 学生 の★3段の階層を作る。席の割当は学科単位。
② 席に★2種類を持たせる（有料席／無料枠）。同じ組織の中で混在する。
③ 招待コードを★学科ごとに発行する。名簿は受け取らない。
④ ★「声を使う仕事ではない」という状態を作る。記録画面を出さず、学ぶだけ開く。
⑤ 年度の入れ替え。★卒業してもアカウントとデータは本人に残る。
⑥ 大学に見せるのは★「使われているか」だけ。健康の中身は一つも出さない。
```

## 2. 学科の階層

```ts
interface Department {
  id: string
  orgId: string            // 大学
  name: string             // 「声楽科」
  seatType: 'paid' | 'free'
  seatLimit: number        // 有料席の上限。free のときは無制限
  active: boolean
}
```

```
・既存の Org（教室）を、そのまま大学として使う
・★Org の下に Department を1段足すだけ。3段目は作らない
・小さな教室は Department を1つだけ持つ（既定で「本科」）
   → ★既存の教室が壊れないこと
```

**RLS**

```
・学科の管理者は、★自分の学科の席の状況だけ見られる
・大学の管理者は、全学科の★席の状況だけ見られる
・★どちらも、個々の学生の記録には一切アクセスできない
```

## 3. 席の2種類

```ts
interface Seat {
  id: string
  departmentId: string
  type: 'paid' | 'free'
  assignedUserId?: string
  assignedAt?: string
  releasedAt?: string
}
```

```
paid  記録 ＋ 学ぶ ＋ ★分析
free  記録 ＋ 学ぶ　（★分析だけロック）
```

```
・★エンタイトルメントの判定を、席の type から引く
・個人契約（月600円）と、席による付与が★同時に存在し得る
   → 個人契約が優先。★二重に課金しない
・席を外しても、★本人のアカウントは残る（無料枠に落ちる）
```

**課金の器（G3.2）と同じ仕組みの上に載せてください。新しい判定を作らないこと。**

## 4. 学科ごとの招待コード

```
大学が申し込む
  → ★学科ごとに別のコードを発行する
  → 学科がコードを学生に配る
  → 学生が自分で登録し、そのコードを入れる
  → その学科の、その種別の席に入る
```

```ts
interface InviteCode {
  code: string
  departmentId: string
  seatType: 'paid' | 'free'
  maxUses?: number
  expiresAt?: string
}
```

```
・★大学から名簿を受け取らない（契約書 第4条5項）
・使用回数の上限を、席数と一致させる
・★誰がどのコードを使ったかは、学科管理者に見せない
   （見せると、誰が使っているかが分かってしまう）
```

**§6 の集計だけで足ります。**

## 5. ★「声を使う仕事ではない」状態

**器楽科・作曲科・音楽学の学生のための状態です。**

```
職業の選択肢に、1つ足す
　○「声を使う仕事ではない（記事だけ読む）」
```

```
・★記録画面を出さない
・★分析を出さない
・「学ぶ」だけが開く
・★あとから、声を使う側に切り替えられる
   （卒業して教員になった人が、そこで記録を始める）
```

**★「器楽科」という職業を作らないでください。**
管楽器は呼吸と口腔の負荷が近いのですが、**声帯を使いません。**
共通コアの「朝の声の調子」「むくみ」が意味を持たず、分析が空振りします。
（職業を声の型で切り直す.md §10-11 の禁止事項のまま）

**作るのは「職業」ではなく「状態」です。**

## 6. 大学に見せる画面（★ここがいちばん危ない）

### 6-1｜見せてよいもの

```
学科ごとの
  ・付与した席の数
  ・そのうち、登録が済んだ人数
  ・★直近30日に1回以上記録した人数
```

### 6-2｜★見せてはいけないもの

```
✗ 誰が使っているか（氏名・ID・一覧）
✗ 誰が使っていないか
✗ 学生別の記録・傾向・スコア・連続日数
✗ 「調子を崩している学生がいます」という通知
✗ 学科ごとの健康に関する集計（平均・分布・何であれ）
```

### 6-3｜k-匿名

```
・★対象が5人未満の集計は、数値を出さない（「—」と表示）
・学科をまたいだ絞り込みをさせない
・期間を細かく切らせない（★月単位まで）
```

**「使われているか」までが、大学の知る権利です。**
**学生が自分で気づくのが目的であって、大学が気づくのが目的ではありません。**

**★休学予防は、営業では話してよいが、機能にしてはいけません。**
大学に「この学生は危ない」を出した瞬間、学生は本当の数字を書かなくなり、
この製品は成り立たなくなります。

## 7. 年度の入れ替え

```
□ 席の一括返却と再割当（3月〜4月）
□ ★卒業した学生のアカウントとデータは、本人に残る
   → 無料枠に落ちる。データは1行も消さない
□ 「卒業予定」の印を付けて、まとめて処理できるようにする
□ 年間一括の請求に合わせた期間管理
```

**★「卒業したらデータが消える」と思われた瞬間、学生は本気で記録しません。**
登録のときと、卒業のときに、**残ることを明示してください。**

## 8. 教員が使う機能（★最小限に）

```
○ 教員が「学ぶ」の記事の★おすすめを並べられる
✗ ★誰が読んだかを教員に見せる
✗ 読了を課題として割り当てる
✗ 記録や読了を成績評定に用いる
```

**読んだかどうかが見えた瞬間、それは課題になります。**


## 付録｜門下によって、先生の関わり方がまったく違う（2026-09-01）

**坂本さんが実際に見てきたこと。**大学へ持ち込むときの前提になります。

```
門下によって、レッスンの日程を誰が決めているかが、まるで違います。

  片方の端  先生はほとんど関わらない（学生どうしで全部決める）
  もう片方  先生が自分で全部組む

★「どちらが普通か」という答えはありません。門下ごとに違います。
```

**なぜこれが重要か（判断-大学のレッスン日程と外部連携.md §7）**

Opus の §7 は「**痛みを感じている人と、お金を払う人が違う**」ことを
価値提案の弱点として挙げていました。この観察は、そこに直接効きます。

```
先生が全部組んでいる門下
  → 痛みを感じているのは★先生本人。話が早い

学生どうしで決めている門下
  → 先生は痛くない。学生が痛い。
    ★先生に「これが要る」と言ってもらいにくい
```

**★大学に対して、ひとつの売り文句は作れません。**
**門下がどちらの型かを見てから、話す内容を変えてください。**

学科単位・大学単位で一律に売り込む形にすると、
「うちはそれ、困っていません」と言う教員が必ず出ます。
★教員ごと・門下ごとに当たるほうが、結果的に早いはずです。

★これは実装の指示ではありません。大学への導入が実際に始まるときに読む記録です。
