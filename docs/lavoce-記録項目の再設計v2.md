# La Voce ／ 記録項目の再設計 v2 — 実装仕様

現行の記録画面（1日あたり約80項目）を、**入力コストを半分以下にしつつ、
分析価値を上げる**方向に作り替えるための仕様書。実装は Claude Sonnet 5 を想定。

**この文書の優先順位**

1. §3.1 記録エントリの構造変更 ← 破壊的変更。最初に片付ける
2. §4 カスタマイズの設計 ← ここを間違えると全画面をやり直すことになる
3. §3 のその他 ← 独立して進められる
4. §7 表現のルール ← コードではなく文言。全画面に適用

---

## 1. 設計原則

1. **分析に接続されていない項目は持たない。** 使うなら構造化する、使わないなら消す
2. **入力コストと分析価値が釣り合わない項目は、詳細度を下げる**（消すのではなく簡易化）
3. **自動で取れるものはユーザーに入力させない**
4. **専用アプリに勝てない領域（食事・運動）は深追いしない**。声に効く部分だけ残す
5. **重複は統一する**
6. **要配慮個人情報は、使う目的があるものだけ持つ。** 目的があるなら構造化して活かす
7. **カスタマイズは「設定でオンオフ」ではなく「プリセット＋その場で増やす」**

## 2. 変更サマリ

| 項目 | 現状 | 変更後 | 規模 |
|---|---|---|---|
| 声・喉の記録単位 | 総合1組 ＋ 朝昼晩の固定3枠 | **時刻つきエントリを何回でも追加**（総合欄は廃止） | 大 |
| 声の評価 | 喉の状態(pp–ff)／声の調子(pp–ff)／響きスコア(0–10) の3つ | **身体感覚(pp–ff)** と **声の出来(0–10)** の2つに整理 | 中 |

| 体重・BMI | 毎日入力、BMIと参考体重レンジ（上下両側）を表示 | **週1入力**。BMI/体重レンジ表示は廃止し、**エネルギー可用性（下側のみ）**に置換 | 中 |
| 身長・年齢・性別 | カロリー目標の推定にのみ使用 | **残す**。除脂肪体重の推定に使う | 小 |

| 水分 | 朝昼夕間食の4分割入力 | **カウンター1つ**（+200ml ボタン） | 小 |
| 運動 | 種目×分×強度の複数行が既定 | **詳細度3段階**。既定は3択 | 小 |
| 休養方法 | 選択肢＋自由記述の「その他」を集計対象に | **選択肢のみ集計**。自由記述はメモ扱い（集計対象外） | 小 |
| 弱声の最高音 | なし | **追加**（別資料 §A-1） | 小 |

## 3. 個別仕様

### 3.1 記録エントリの構造変更（最重要・破壊的）

**現状の問題**

- 「総合」と「朝昼晩」が二重管理で、時間帯別を入れると総合が上書きされる
- 1日1回しか歌わない人にも3枠が出て冗長
- マチネ／ソワレの2公演、アナウンサーの日内変動、声優の複数現場に対応できない

**変更**

固定枠を廃止し、**時刻つきの声の記録を1日に何件でも追加できる**構造にする。

```ts
type VoiceContext =
  | 'wake'          // 起き抜け
  | 'after_routine' // 発声ルーティン後
  | 'before_work'   // 本番・収録・放送の前
  | 'after_work'    // その後
  | 'other'

interface VoiceEntry {
  id: string
  date: string          // 'YYYY-MM-DD'
  at: string            // 'HH:mm' 実際の時刻。既定は現在時刻
  context: VoiceContext

  bodyFeel?: 1 | 2 | 3 | 4 | 5   // 喉の身体感覚（pp–ff 表記で表示）
  quality?: number               // 声の出来 0–10（内部は常に0–10で保持）

  pitchChest?: string       // 地声の音名 'A3' など
  pitchSoftMax?: string     // 弱声の最高音（スウェリングチェック）

  symptoms?: SymptomKey[]
  note?: string
}
```

**UI**

- 記録画面の一番上に「**＋声の記録を追加**」ボタン
- 1件目は `context: 'wake'` が既定で入る
- 1件しか記録しない人は、それがその日の値になる（総合欄は不要）
- 3件以上あると、その日の時間帯別の推移が自動で表示される

**派生値**

日次分析で使う「その日の代表値」はサーバ／クライアントで導出する。ユーザーには入力させない。

```
代表 bodyFeel = 当日エントリの中央値
代表 quality  = 当日エントリの中央値
起き抜けの値  = context==='wake' のエントリ（なければ最も早い時刻のもの）
日内変動      = 最終エントリ − 起き抜けエントリ
```

### 3.2 声の評価の分離

3つあった主観指標を、意味の違う2つに整理する。

| フィールド | 意味 | UI | 内部値 |
|---|---|---|---|
| `bodyFeel` | **喉の身体感覚**。乾いている、詰まる、軽い等の体感 | pp / p / mf / f / ff の5段階（既存表記を踏襲） | 1–5 |
| `quality` | **声の出来**。響き、鳴り、コントロール | 詳細モード: 0–10のスライダー（現行の響きスコア）<br>簡易モード: 5段階 | 常に 0–10 |

簡易モードの5段階は内部で `0 / 2.5 / 5 / 7.5 / 10` にマップする。
**内部表現は常に0–10で統一**すること。詳細度を切り替えても過去データが連続する。

### 3.3 詳細度レベル（全項目に共通の仕組み）

オンオフの2値ではなく、**項目グループごとに3段階の詳細度**を持たせる。

```ts
type Detail = 0 | 1 | 2   // 0=記録しない / 1=簡易 / 2=詳細

type FieldGroup =
  | 'voice' | 'symptoms' | 'sleep' | 'hydration' | 'meal'
  | 'body' | 'env' | 'activity' | 'exercise' | 'recovery'
  | 'mental' | 'cycle' | 'practiceNote'

type DetailConfig = Record<FieldGroup, Detail>
```

| グループ | 1 = 簡易 | 2 = 詳細 |
|---|---|---|
| `meal` | タンパク質 g/kg ＋ 概算kcal ＋ 夕食時刻 ＋ 夕食タグ | ＋ 食品別の PFC 記録 |
| `exercise` | 3択（していない／軽め／しっかり） | ＋ 種目・分・強度 |
| `voice` | bodyFeel ＋ quality(5段階) | ＋ 音名・弱声最高音・quality(0–10) |
| `body` | 体重（週1） | ＋ 体脂肪率・エネルギー可用性 |
| `mental` | 心の余裕のみ | ＋ 気持ちタグ・日記 |

**実装上の要点**

表示・非表示の判定は**1箇所に集約**すること。各コンポーネントに `if (detail >= 2)` を
散らすと保守不能になる。

```ts
// 例：これ1つを通す
const { visible, level } = useFieldGroup('meal')
```

**簡易モードでも分析は動くこと。** 詳細モードの人には分析が追加されるだけ、という関係にする。
必要な項目が欠けている分析は、その分析だけを非表示にする（pairwise deletion の方針と一致）。

### 3.4 食事

**既定を簡易にする。** 詳細記録は増量・減量フェーズの人だけが使う。

残すもの（声への効きが直接的で、入力が軽い）:

- 夕食の時刻 → 就寝までの間隔（自動計算）
- 夕食タグ（揚げ物／あっさり／炭酸／トマト系／カフェイン／アルコール）
- タンパク質 g/kg
- 概算カロリー

簡易モードのタンパク質入力は、食品を数えさせず**3択＋補正**でよい:
「しっかり摂った／ふつう／少なめ」→ 体重と目標係数から g/kg を推定して保存。
数値を直接入れたい人は入力欄に切り替えられるようにする。

### 3.5 身体：BMI を廃し、エネルギー可用性へ

**廃止するもの**

- BMI の表示
- 「参考体重レンジ（上下両側）」の表示
- 毎日の体重入力の強制

**理由**

声のプロにとって危険なのは**下側だけ**であり、上側の基準を毎日提示する利益がない。
一般のBMI基準が当てはまらないことは現行アプリ自身が注記している。

**代わりに置くもの：エネルギー可用性（EA）**

問題は体重や体型ではなく、**消費に対して摂取が足りているか**である。
エネルギーが不足すると、身体は優先度の低い機能から落としていき、
**筋・結合組織、免疫、ホルモン、回復力**が順に損なわれる。これは呼気の支えに直接効く。

```
■ 除脂肪体重 FFM

体組成計の実測（体脂肪率）があれば必ずそれを使う:
    FFM = 体重 × (1 − 体脂肪率/100)

実測がない場合の推定（Deurenberg 1991）:
    BF% = 1.20 × BMI + 0.23 × 年齢 − 10.8 × 性別 − 5.4
          性別: 男性 = 1, 女性 = 0
    ※ 推定の標準誤差は約 4.1%BF（変動係数16%）。
       鍛えている人・痩せている人ほど誤差が大きいので、
       推定値を使っている旨を必ず画面に明示する。

■ エネルギー可用性

    EA = (摂取エネルギー kcal − 運動によるエネルギー消費 kcal) / FFM(kg)

    目安として 45 kcal/kgFFM/日 前後が十分、30 を下回る状態が続くと低EA。
    ※ 単一の閾値で断定しないこと。
       「直近21日の移動平均が30を下回っている」のように、継続で判定する。
```

**摂取カロリーが分からない簡易モードのユーザー向け：複合サイン**

EA が計算できない場合は、既存データだけで組める代替サインを使う。
以下のうち **3つ以上が同時に成立した状態が2週間続いた**ら、注意を表示する。

- 体重の28日移動平均が 3% 以上減少している
- 症状の出た日の割合が直近14日で 50% を超えている
- 休養日の翌日にコンディションが戻らない回数が3回以上
- （記録があれば）月経の間隔が乱れている
- 睡眠時間は足りているのに疲労感タグが継続している

**表示の頻度**：日次では出さない。**月1回のまとめ画面でのみ**表示する。
日々の体重変動は水分でブレるので、日次表示は意味がないうえに不安を煽る。

**表現**（§7 のルールに従う）

> ✗ 「低栄養の疑いがあります」「痩せすぎです」
> ✓ 「摂取エネルギーが3週間、推定の必要量を下回っています。体重も2.4%減っています。
>    支える力に影響が出ることがあります。気になる場合は管理栄養士や医師にご相談ください。」

### 3.6 既往症の構造化と、逆流専用の分析

**自由記述をやめ、選択式にする。**

```ts
type ConditionKey =
  | 'gerd'          // 逆流性食道炎
  | 'lpr'           // 咽喉頭酸逆流
  | 'allergic_rhinitis'  // アレルギー性鼻炎・花粉症
  | 'asthma'
  | 'sinusitis'     // 副鼻腔炎
  | 'thyroid'       // 甲状腺疾患
  | 'anemia'
  | 'sleep_apnea'
  | 'vocal_lesion'  // 声帯結節・ポリープの既往
```

**目的：知らない人に気づいてもらうためのツールにする**

逆流が声に出ることを知らない人は多い。だが**未診断の人に「疑い」を示すのは規制上できない**
（§7 参照）。そこで次のように分ける。

| 対象 | 出せるもの |
|---|---|
| **診断済みと登録した人** | 専用分析。「あなたの記録では、夕食から就寝まで2時間未満の日の翌朝、喉の違和感が3.4倍の頻度で出ています」 |
| **全員** | 「健康情報」タブでの一般的な解説記事（逆流と声の関係）。個人の記録には紐づけない |
| **未診断の人** | 事実の提示のみ。「就寝2時間前以内の夕食が今週5日ありました」。疑い・診断名は出さない |

診断済みユーザー向けの専用分析（`conditions` に `gerd` か `lpr` を含む場合のみ表示）:

- 夕食→就寝の間隔ビン別 × 翌朝の喉の違和感の出現率（各ビン n≥5 で表示）
- 夕食タグ別（揚げ物／炭酸／カフェイン／アルコール／トマト系）の効果量とCI
- 就寝姿勢・上体挙上の有無（任意で追加）

**移行時の注意**：現行の自由記述メモは、移行画面で「該当する項目を選んでください」と
選択式へ誘導する。元テキストは移行完了まで保持し、完了後に削除する。

### 3.7 稽古ノート（技術的な目標の日記化）

自由記述のまま放置せず、**振り返りのループ**にする。

```ts
type GoalTag =
  | 'soft_high'      // 弱声の高音
  | 'high_range'     // 高音
  | 'range'          // 音域拡大
  | 'breath_support' // 息の支え
  | 'articulation'   // 滑舌・明瞭度
  | 'stamina'        // 持久力
  | 'evenness'       // 音色の均一

interface PracticeNote {
  id: string
  startedAt: string
  goal: string          // ★1つだけ。複数だとどれも進まない
  tags: GoalTag[]
  reviews: { at: string; text: string }[]   // 週1想定
}
```

**この機能の肝：振り返り画面に、タグに対応する客観データを自動で添付する。**

| タグ | 自動で並べる指標 |
|---|---|
| `soft_high` | 弱声の最高音の推移（4週間） |
| `high_range` | ルーティン後の音名の推移 |
| `range` | 音域幅（最高−最低、半音）の推移 |
| `breath_support` | 最長発声時間（MPT）の推移 |
| `articulation` | CPPS の推移（アナウンサーは話速も） |
| `stamina` | 発声負荷 ACWR と、翌日の回復度 |

「感覚では変わった気がしない」と書いた横に、実は半音上がっているグラフが出る——
これが最も効く瞬間になる。過去の振り返りは時系列で読み返せるようにする。

### 3.8 環境の自動取得

天気の3択（晴／曇／雨／雪）は**廃止**。気温・湿度と情報が重複している。

```ts
interface EnvSnapshot {
  source: 'auto' | 'manual'
  place?: string
  tempC?: number
  humidityPct?: number
  absoluteHumidity?: number   // 導出値。式は別資料 §9
  pressureHpa?: number
  pollenLevel?: number        // 花粉
  pm25?: number
}
```

滞在地（または位置情報）から気象APIで自動取得する。手入力へのフォールバックは残す
（海外公演・地下スタジオなど、APIが当てにならない場面がある）。
**取得した値には `source: 'auto'` を立て、画面上でも自動取得であることを示す。**

### 3.9 水分

朝昼夕間食の4分割は廃止。分析では合計しか使っていない。

**「+200ml」のカウンターボタン1つ**にする。合計だけを保持。
数値を直接入れたい人向けに入力欄も残す。

### 3.10 休養方法

「その他」の自由記述を**集計対象から外す**。表記ゆれで集計が壊れており、
現行では「東京へ行く（鈍行）。帰りは特急」が休養方法として1件計上されている。

- 選択肢のみを集計対象にする
- 自由記述は `note` として保持し、表示はするが集計しない
- 選択肢に足りないものがあれば、要望として集めて選択肢自体を増やす

### 3.11 運動

詳細度3段階（§3.3）。既定は簡易の3択。詳細を選んだ人だけ種目・分・強度を記録する。

## 4. カスタマイズの設計

**「設定画面で項目をオンオフさせる」形は採用しない。** 理由:

- 初日に大量のトグルを見せるのは、大量の入力欄を見せるのと同じく離脱を招く
- 使う前に「自分に何が必要か」は判断できない
- 組み合わせが爆発し、テストできない状態が増える

代わりに次の5つで実現する。

### 4.1 選ばせるのではなく、当てる（プリセット）

初回に聞くのは**2問だけ**。

```ts
type ProfessionKey = 'classical' | 'announcer' | 'voice_actor' | 'popular'
type GoalFocus = 'diagnose' | 'peak' | 'train' | 'log_only'
// diagnose = 不調の原因を突き止めたい
// peak     = 本番に合わせたい
// train    = 長く鍛えたい
// log_only = 記録だけしたい
```

この2つから `DetailConfig` の初期値を決める。**記録項目は10個程度から始める。**

プリセットの例:

| profession × goalFocus | 既定で開く項目 |
|---|---|
| 任意 × `log_only` | voice(1), sleep(1), symptoms(1) のみ |
| classical × `peak` | ＋ activity, env(auto), hydration, recovery, mental(1) |
| classical × `train` | ＋ practiceNote, body(1), meal(1) |
| announcer × `diagnose` | ＋ 発話時間, env(auto), hydration, symptoms(2) |
| voice_actor × `peak` | ＋ 収録種別, 叫びテイク数, recovery |
| popular × `peak` | ＋ セットリスト, モニター環境, 連戦日数 |

### 4.2 増やすのは「記録画面で、その場で」

各セクションの下に「**＋詳しく記録する**」を置く。押すとその場で項目が増え、
次回以降も表示される。**設定画面に行かせない。**

減らす方向のUIは作らない（§4.3 がその役割を担う）。

### 4.3 使っていないものは、アプリから畳む提案をする

30日間入力のない項目グループについて、月次のまとめ画面で提案する。

> 「タンパク質を30日間記録していません。畳みますか？」［畳む］［続ける］

ユーザーに管理させず、**使用実績からアプリが提案する**。これが最も摩擦が少ない。

### 4.4 日別テンプレート（実は最も効く）

その日の活動種別を選ぶと、**その日に出る入力欄が変わる**。
設定を触る必要がそもそもなくなる。

```ts
type TemplateKey =
  | 'off' | 'practice' | 'lesson' | 'rehearsal'
  | 'performance'   // 声楽家・ミュージカル
  | 'recording'     // 声優
  | 'broadcast'     // アナウンサー
  | 'live'          // ポップス/ロック

const TEMPLATE_FIELDS: Record<TemplateKey, FieldGroup[]> = {
  off:         ['voice', 'sleep', 'hydration', 'recovery', 'mental'],
  practice:    ['voice', 'sleep', 'hydration', 'activity', 'mental'],
  // ... performance は repertoire と env を追加
  // ... recording は role と screamTakes を追加
  // ... live は setlist / monitor / afterparty を追加
}
```

休養日に曲目やセットリストの欄は要らない。声優のゲーム収録日には叫びテイク数が出て、
オフの日には出ない。**テンプレートは1つの定数ファイルに集約すること。**

### 4.5 カスタマイズを「解放」と繋げる

項目を増やすことを、既存のレベル解放の仕組みと接続する。

> 「**弱声の最高音**を記録すると、むくみの早期サインが見られるようになります」
> 「**月経周期**を記録すると、周期とコンディションの関係が分析できます」

これでカスタマイズが「面倒な設定」ではなく**「新しい画面を開ける鍵」**になる。
放っておいても、必要な人だけが必要な項目を増やしていく。

## 5. データモデル（全体）

```ts
interface Profile {
  professions: ProfessionKey[]        // ★複数選択（兼業が普通の業界）
  goalFocus: GoalFocus
  voiceType?: VoiceType
  heightCm?: number
  age?: number
  sex?: 'male' | 'female' | 'na'
  rangeLow?: string
  rangeHigh?: string
  conditions: ConditionKey[]          // 構造化された既往症
  detail: DetailConfig
  consents: {
    healthData: string                // ISO日時。要配慮個人情報の取得同意
    statsUse?: string                 // 統計利用への同意（別途・任意）
  }
}

interface DayRecord {
  date: string
  template: TemplateKey

  sleep?: { hours?: number; bedtime?: string; quality?: 1|2|3|4|5 }
  hydrationMl?: number

  meal?: {
    dinnerAt?: string
    dinnerTags?: DinnerTag[]
    proteinGPerKg?: number
    energyKcal?: number
    items?: FoodItem[]                // detail === 2 のときのみ
  }

  activities: Activity[]              // 職業別の負荷計算に渡す（別資料 §2）
  exercise?: { level?: 0|1|2; items?: ExerciseItem[] }
  recovery?: { methods: RecoveryKey[]; note?: string }
  mental?: { calm?: 1|2|3|4|5; tags?: string[]; diary?: string }

  weightKg?: number                   // 週1想定
  bodyFatPct?: number                 // 任意（体組成計）
  cycleDay?: number                   // 任意

  env?: EnvSnapshot                   // 自動取得
}

// 声の記録は DayRecord から切り離し、独立したテーブルにする
// （1日N件、時刻つき）
type VoiceEntries = VoiceEntry[]
```

## 6. 移行（既存データを壊さない）

**先にマイグレーションと読み取り互換レイヤーを書くこと。** UIの変更はその後。

| 旧 | 新 |
|---|---|
| 総合の「喉の状態」 | `VoiceEntry.bodyFeel`（`context: 'other'`, `at: '12:00'` 既定） |
| 総合の「声の調子」 | `VoiceEntry.quality`（5段階 → 0–10 に線形変換） |
| 「響きスコア」 | `VoiceEntry.quality`（**あればこちらを優先**） |
| 朝／昼／晩の3枠 | `VoiceEntry` 3件に分解（`at` は 08:00 / 13:00 / 20:00 を既定） |
| 起き抜けの音名 | `VoiceEntry.pitchChest`（`context: 'wake'`） |
| ルーティン後の音名 | `VoiceEntry.pitchChest`（`context: 'after_routine'`） |
| 水分の4分割 | 合計して `hydrationMl` |
| 天気の3択 | 破棄（`env` の自動取得に置換）。過去データは参考として残してよい |
| BMI・参考体重レンジ | 表示のみ削除。`weightKg` は保持 |
| 体質・既往症メモ | 移行画面で選択式へ誘導。元テキストは移行完了後に削除 |

**注意**：分解した `VoiceEntry` には `source: 'migrated'` のフラグを立て、
時刻が推定であることを分析側で区別できるようにする。日内変動の分析では除外する。

## 7. 表現のルール（全画面共通）

コードではなく文言の規則だが、**実装時に必ず守ること**。

### 7.1 疾病の兆候を検知しない

プログラムが医療機器に該当するかは「使用目的」と「処理方法」で決まる。
**記録・統計処理・表示・共有は非該当、疾病の診断・病態の評価・兆候の検知・
リスク表示は該当**する。事業化すると、この線はより厳しく見られる。

> ✗ 「声帯のむくみが疑われます」
> ✓ 「弱声の最高音が、あなたの平常値より3半音低い日が4日続いています」
>
> ✗ 「逆流性食道炎の可能性があります」
> ✓ 「夕食から就寝まで2時間未満の日が今週5日ありました」
>
> ✗ 「低栄養の疑いがあります」
> ✓ 「摂取エネルギーが3週間、推定の必要量を下回っています」

**診断済みと登録している人への情報提供は安全圏、未診断の人に疑いを示すのは危険域。**

### 7.2 因果の言い方を固定する

> ✗ 「◯◯すると声が良くなります」
> ✓ 「◯◯した日の翌日は、平均して声が良く記録されています」

### 7.3 件数を必ず添える

「平均4.5」ではなく「平均4.5（2日）」。両方向に出た項目は結論を出さず
「まだ判断できません」と表示する。

### 7.4 要配慮個人情報

健康データは要配慮個人情報にあたる。**取得前の明示的な同意が必須**で、
オプトアウトによる第三者提供は認められない。1件でも漏えいすれば
個人情報保護委員会への報告と本人通知が義務になる。

- 同意日時を `Profile.consents` に記録する
- データの一括書き出し（JSON / CSV）とアカウント削除を実装する
- 統計利用は**別途の同意**として分けて取る

## 9. Sonnet 5 への依頼のコツ

- **Phase 1 と 2 は必ずこの順で**。UIから先に触らせるとデータが壊れる
- 表示・非表示の判定は `useFieldGroup(group)` のような**フック1つに集約**させる。
  各コンポーネントに `if (detail >= 2)` を書かせない。明示的に要件として書くこと
- テンプレート定義・プリセット定義・職業別の負荷計算は、**それぞれ1つの定数/関数に集約**させる
- 1PR1機能。「記録画面を作り替えて」ではなく「VoiceEntry のマイグレーションだけ」から
- 既存のディレクトリ構成・命名・状態管理の規約を最初に読ませる
- §7 の文言ルールは、**コードレビューの観点として毎回渡す**
