# La Voce ／ 教室プラン仕様（複数の先生 × 複数の生徒）

**指導者プラン実装仕様の §2〜§7・§10 を差し替えます。**
§8（メッセージを作らない）・§9（レッスンモード）・§11（未成年）は本書で拡張します。

---

## 0. 結論

| 要望 | 判断 |
|---|---|
| 複数の先生が複数の生徒を教える | **作る。「教室」という実体を新しく作ります** |
| 担当の先生と生徒でレッスン日程を共有 | **作る** |
| 管理者の先生が全部を見られる | **作る。ただし「全部」を2つに分けます**（§3）★ |
| 生徒が複数の先生のレッスンに通う | **作る** |
| 生徒が複数の教室（事業者）で使える | **作る。データは1つ、共有先が複数** |
| より高額なサブスク | **作る。席数で決める3段階**（§8） |

**この設計でいちばん重要なのは §3 です。**
「管理者が全部見られる」を素直に作ると、**取り返しのつかない事故になります。**

---

## 1. 新しく作る実体

```
Organization（教室・事業者）
   │
   ├── Membership   … 誰がこの教室の先生か（owner / admin / teacher / staff）
   │
   ├── Enrollment   … 誰がこの教室の生徒か
   │
   └── Assignment   … どの生徒を、どの先生が担当するか（多対多）
```

**3つとも「多対多」です。**

- 1人の生徒が、同じ教室の**複数の先生**につく（声楽＋コレペティ＋演技）
- 1人の生徒が、**複数の教室**に所属する（音大＋個人レッスン＋養成所）
- 1人の先生が、**複数の教室**に所属する（掛け持ちの講師）

### 1.1 役割（Membership.role）

| 役割 | できること |
|---|---|
| **owner** | 契約者。課金・席の増減・教室の削除。管理者の面をすべて見られる |
| **admin** | owner から管理を委譲された先生。課金以外は owner と同じ |
| **teacher** | 自分の担当生徒だけ。教室の運営の面は見えない |
| **staff** | **事務。日程と出欠だけ見える。健康に関するものは一切見えない** |

> **staff を必ず作ってください。** 音楽教室・養成所には事務の人がいて、
> 日程調整をするのはその人です。**その人に声の記録を見せる理由はありません。**
> 役割を分けておかないと、事務用のアカウントを先生として作られ、全部見えてしまいます。

## 2. 個人の先生は「1人の教室」です

**既存の指導者プラン（先生1人・生徒複数）を別物として残さないでください。**

```
個人の先生 = メンバーが1人だけの Organization
```

こうしておくと、

- 分岐が1本で済む（`if (isOrg)` を書かなくてよい）
- 個人の先生が教室プランに上がるとき、**データ移行が要らない**
- 生徒側の画面が、どちらでも同じに見える

**§10 に、既存データをこの形へ移す手順を書いています。**

---

## 3. ★ 権限モデル：「全部見える」を2つに分ける

**ここが本書の中心です。**

「管理者の先生が全部を見られる」を素直に実装すると、
**担当したことのない生徒の、声の記録・症状・睡眠・メンタルまで見えます。**

それは**要配慮個人情報**です。**この設計のまま出すことはできません。**

### 3.1 2つの面

| 面 | 内容 | 管理者(owner/admin) | 担当の先生 | 非担当の先生 | staff |
|---|---|---|---|---|---|
| **運営の面** | 在籍・担当・レッスン日程・出欠・回数・請求に関わる数 | **全員分ぜんぶ** | 自分の担当のみ | ✕ | **日程と出欠のみ** |
| **健康の面** | 声の記録・症状・睡眠・分析・稽古ノート | **担当している生徒のみ**（既定） | 自分の担当のみ | ✕ | **✕ 常に不可** |

**管理者は、運営の面ではすべてを見られます。**
**健康の面では、自分が担当している生徒しか見られません。**

### 3.2 例外は、生徒が明示的に許した場合だけ

生徒が教室ごとに選べる形にします。

```
◯◯音楽教室 との共有設定

  共有する相手
  ┌──────────────────────────────────┐
  │ ● 担当の先生だけ           （既定）│
  │ ○ 担当の先生と、教室の管理者      │
  └──────────────────────────────────┘

  共有する内容
  ☑ 声の記録    ☑ 症状     ☑ 睡眠    ☑ 活動
  ☐ 水分        ☐ 食事     ☐ 体組成
  ☐ 心の余裕  🔒 先生には見えません
  ☐ 稽古ノート  ☐ 学ぶのメモ
```

**既定は「担当の先生だけ」です。** 管理者を含めるのは、生徒が自分で選んだときだけ。

### 3.3 判定関数

```ts
type Plane = 'ops' | 'health'

async function canView(
  viewerId: string,
  orgId: string,
  studentId: string,
  plane: Plane,
  scope?: keyof ShareScope,
): Promise<boolean>
```

**実装の順番を必ずこの通りにしてください。**

```
1. viewer はこの org のメンバーか            → 否なら false
2. student はこの org に在籍しているか        → 否なら false
3. plane === 'ops'
     role が staff       → 日程・出欠のみ true
     role が teacher     → 担当している生徒のみ true
     role が admin/owner → true
4. plane === 'health'
     role が staff                        → 常に false
     担当している                          → ShareScope を見る
     担当していない かつ role が admin/owner → 生徒が
                                            shareWithAdmin=true にしている場合のみ
                                            ShareScope を見る
     それ以外                              → false
5. ShareScope[scope] が true か             → 否なら false
```

**この関数を通さないデータ取得を、1本も作らせないでください。**
指導者プラン実装仕様 §0 の権限監査（A-P1-1）を、本書の内容で作り直してから着手します。

## 4. 生徒の体験：複数の教室

### 4.1 データは1つ、共有先が複数

```
生徒の記録（1つ）
     │
     ├── ◯◯音楽教室 へ    共有範囲A ・ 担当：山田先生、佐藤先生
     ├── △△声優養成所 へ  共有範囲B ・ 担当：鈴木先生
     └── 個人レッスン（田中先生）  共有範囲C
```

**教室ごとに、共有する範囲が別々です。**
「本科の先生には全部見せるが、養成所には日程だけ」が成立します。

### 4.2 生徒の画面

```
┌───────────────────────────────┐
│ 先生とのつながり               │
│                               │
│ ┌───────────────────────────┐ │
│ │ ◯◯音楽教室               │ │
│ │ 担当：山田先生・佐藤先生   │ │
│ │ 共有：声/症状/睡眠/活動    │ │
│ │              設定を変える →│ │
│ └───────────────────────────┘ │
│ ┌───────────────────────────┐ │
│ │ △△声優養成所             │ │
│ │ 担当：鈴木先生             │ │
│ │ 共有：日程のみ             │ │
│ │              設定を変える →│ │
│ └───────────────────────────┘ │
│                               │
│ ┌───────────────────────────┐ │
│ │  ＋ 招待コードで参加する    │ │
│ └───────────────────────────┘ │
└───────────────────────────────┘
```

**「つながりを解除する」を、いつでも押せる場所に置いてください。**
解除したら、その教室からは即座に見えなくなります。**過去の分もです。**

### 4.3 いつでも撤回できること

- 共有範囲の変更は**即時反映**
- 解除しても**生徒自身のデータは消えない**
- 先生の側に**キャッシュを残さない**（一覧の再取得で消える設計に）

## 5. レッスン日程（複数の先生）

### 5.1 Lesson は (教室 × 先生 × 生徒)

```ts
interface Lesson {
  id: string
  orgId: string
  teacherId: string
  studentId: string
  startAtUtc: string
  tz: string
  durationMinutes: number
  location?: string
  isOnline: boolean
  recurrence?: { freq: 'weekly'; byWeekday: number; until?: string }
  status: 'scheduled' | 'done' | 'canceled' | 'noshow'
  teacherNote?: string        // ★先生専用。生徒に見せない
  createdBy: string
  createdAt: string
}
```

### 5.2 誰に見えるか

| 見る人 | 見える範囲 |
|---|---|
| 生徒 | **自分のレッスン全部**（教室をまたいで1つのカレンダーに） |
| 担当の先生 | 自分が担当するレッスン |
| 管理者 | **その教室のレッスン全部** |
| staff | **その教室のレッスン全部**（生徒名と時間。健康の情報は付かない） |

### 5.3 ★ 重なりの検出

**複数の先生・複数の教室になった瞬間、これが必要になります。**

```
⚠ 9/3（火）15:00 が2件重なっています
    ◯◯音楽教室 ・ 山田先生
    △△養成所 ・ 鈴木先生
```

| 検出するもの | 誰に出すか |
|---|---|
| **同じ生徒の時間が重なった** | 生徒と、両方の先生 |
| **同じ先生の時間が重なった** | その先生と、教室の管理者 |
| 1日のレッスンが4件を超えた | 生徒本人にだけ、そっと |

**警告を出すだけです。自動で動かしたり、予約を拒否したりしないこと。**

> **部屋の割り当て・空き枠の公開・予約の受付は作りません。**
> 予約管理SaaSの領域で、規模が10倍になります（指導者プラン実装仕様 §5）。
> **重なりを教えるところまでが La Voce の仕事です。**

### 5.4 管理者の日程画面

```
┌──────────────────────────────────────────────┐
│ ◯◯音楽教室 ・ 8月26日(火)                    │
│                                              │
│      山田先生        佐藤先生      鈴木先生   │
│ 14:00 田中○○ ⚠      ―            高橋○○    │
│ 15:00 田中○○ ⚠      渡辺○○      ―          │
│ 16:00 ―             渡辺○○      伊藤○○    │
│                                              │
│ ⚠ 山田先生の14:00と15:00に重なりがあります    │
└──────────────────────────────────────────────┘
```

**生徒名をタップしたとき**：担当している生徒なら状態ページへ。
**担当していない生徒なら、日程の詳細だけ**（§3.1）。

## 6. 招待と同意

### 6.1 3種類の招待

| 誰が | 誰を | 承認するのは |
|---|---|---|
| owner / admin | **先生を教室へ** | 先生本人 |
| owner / admin / teacher | **生徒を教室へ** | 生徒本人（＋未成年なら保護者） |
| owner / admin | **生徒に担当の先生を割り当て** | 承認不要（教室内の運営） |

**担当の割り当てに生徒の承認は要りません。** 教室の運営そのものだからです。
**ただし、担当が変わったことは生徒に必ず通知してください。**
新しい先生に健康の面が見えるようになるからです。

### 6.2 招待コード

指導者プラン実装仕様 §3 の仕様をそのまま使います。

```
7日で失効 ・ 1回だけ有効 ・ 0/O/1/l/I を除いた文字
```

**教室コードには、教室名を必ず添えて表示してください。**
「どこに参加しようとしているのか」が分からないまま同意させないこと。

### 6.3 ★ 同意の記録

**要配慮個人情報を、教室という新しい相手に渡します。同意の記録を残してください。**

```ts
interface ShareConsent {
  id: string
  studentId: string
  orgId: string
  scope: ShareScope
  shareWithAdmin: boolean
  guardianConfirmedAt?: string   // 未成年のとき
  agreedAt: string
  revokedAt?: string
  agreementVersion: string       // 同意文言のバージョン
}
```

**同意した内容は上書きせず、履歴として積んでください。**
「いつ、何を、どこまで許したか」を後から示せる形にします。

## 7. 未成年

**教室になると、未成年の比率が上がります**（音大受験生・養成所・児童劇団）。

| 内容 | 対応 |
|---|---|
| 共有の同意 | **保護者の確認を必須にする**（保護者のメールに確認リンク） |
| 共有できる範囲 | **既定をさらに狭く**（声・症状・活動のみ。睡眠を既定から外す） |
| 心の余裕・稽古ノート・学ぶのメモ | **共有の選択肢に出さない** |
| 1対1の非公開のやりとり | **作らない**（指導者プラン実装仕様 §8。教室になっても変えない） |
| 記録へのコメント | 可。ただし**教室内の他の先生と管理者にも見える**形にする |

> **コメントを「担当の先生と生徒だけの非公開」にしないでください。**
> 大人と未成年の1対1の閉じた場になります。
> **見られている場であることが、安全装置です。**

## 8. 課金設計

### 8.1 席で決める

**生徒は課金しません。教室が席数で払います。**

| プラン | 月額（日本） | 先生の席 | 生徒の席 | 管理者の面 | staff |
|---|---|---|---|---|---|
| **指導者** | **¥3,980** | 1 | 20 | — | — |
| **教室** | **¥12,800** | 5 | 60 | ✓ | 2 |
| **事業者** | **¥29,800** | 15 | 200 | ✓ | 5 |
| 追加の先生 | +¥1,800 / 人 | | | | |
| 追加の生徒 | +¥150 / 人 | | | | |

**年払いは2ヶ月分を引く**（価格設計仕様の方針に合わせる）。
**海外は価格設計仕様の T1〜T3 の倍率をそのまま適用**してください。

### 8.2 席の数え方

| | 数え方 |
|---|---|
| 先生 | **その教室の Membership の数**（owner/admin/teacher）。staff は別枠 |
| 生徒 | **その教室の在籍数**。休会中は数えない |
| 掛け持ちの先生 | **教室ごとに1席**（2つの教室にいれば、それぞれで1席） |
| 複数教室の生徒 | **教室ごとに1席**（同上） |

**「掛け持ちだから半額」のような計算を作らないでください。** 説明できなくなります。

### 8.3 ★ 生徒に何を付与するか

**ここは事業として重要な判断です。**

```
教室プラン ¥29,800 ÷ 生徒200人 = 1人あたり ¥149
個人の有料プラン                = ¥580
```

**教室に入っている生徒に有料機能を全部付与すると、個人課金が成り立たなくなります。**

| 生徒に付与するもの | 付与しないもの |
|---|---|
| 先生との共有 | **発見（Lv.4以降）** |
| レッスン日程 | **本番レイヤー** |
| 記録へのコメント | **職業の切り替え（2つ目以降）** |
| レッスンモード | |

**追加オプション**として、

```
生徒プレミアム一括付与   +¥300 / 生徒 / 月
```

を用意してください。**教室が「うちの生徒には全部使わせたい」と言ったときに売れます。**
これが実は、いちばん利益率の高い商品です。

### 8.4 契約の主体

- **契約者は owner の1人だけ**（請求先も1つ）
- 支払いは**ウェブ決済のみ**（アプリ配布と課金仕様の方針どおり）
- **席を減らしたときは、次の請求から反映**（日割りにしない。事務が複雑になります）
- **解約したら、先生側から見えなくなる。生徒のデータは消さない**

## 9. データモデル

```ts
interface Organization {
  id: string
  name: string
  kind: 'solo' | 'school' | 'agency'   // solo = 個人の先生
  ownerId: string
  plan: 'teacher' | 'school' | 'agency'
  seats: { teacher: number; student: number; staff: number }
  studentPremium: boolean               // §8.3 の一括付与
  createdAt: string
}

type OrgRole = 'owner' | 'admin' | 'teacher' | 'staff'

interface Membership {
  id: string
  orgId: string
  userId: string
  role: OrgRole
  invitedBy: string
  joinedAt: string
  leftAt?: string
}

interface Enrollment {
  id: string
  orgId: string
  studentId: string
  status: 'active' | 'paused' | 'left'
  joinedAt: string
  leftAt?: string
}

interface Assignment {
  id: string
  orgId: string
  studentId: string
  teacherId: string
  subject?: string          // 声楽 / 演技 / コレペティ など。自由入力
  startedAt: string
  endedAt?: string
}

interface ShareScope {
  voice: boolean            // 既定 true
  symptoms: boolean         // 既定 true
  sleep: boolean            // 既定 true（未成年は false）
  activity: boolean         // 既定 true
  hydration: boolean        // 既定 false
  meal: boolean             // 既定 false
  body: boolean             // 既定 false
  mental: boolean           // ★既定 false。変更しないこと
  notes: boolean            // 既定 false
  articleNotes: boolean     // 既定 false
}
```

**`Assignment` に `endedAt` を持たせています。**
担当が外れた先生は、**その時点から健康の面が見えなくなります。**
**過去の分も見えなくなること。** 「担当だった期間の分は見られる」を作らないでください。
生徒に説明できなくなります。

## 10. 既存データの移行

**4段階で。既存の先生と生徒のつながりを壊さないこと。**

```
① Organization / Membership / Enrollment / Assignment を作る（まだ使わない）

② 既存の teacher-student の組から、先生ごとに
     Organization(kind:'solo', plan:'teacher') を1つ作り、
     Membership(role:'owner') と Enrollment と Assignment を埋める
     ★既存の ShareScope を、そのまま ShareConsent へ写す

③ 読み取りを新しい canView() に切り替える
     1バージョンのあいだ、旧経路と結果を突き合わせて記録する

④ 旧経路を消す
```

**③で結果が食い違ったら、必ず止めて調べてください。**
権限の食い違いは、そのまま情報漏えいです。

## 11. 画面

| 画面 | 誰が見る | 中身 |
|---|---|---|
| 教室ダッシュボード | owner / admin | 在籍数・今日のレッスン・要注意の生徒（担当分のみ）・席の使用状況 |
| 先生の担当一覧 | teacher / admin / owner | 指導者プラン実装仕様 §5 のまま |
| 生徒の個別ページ | 担当の先生 | 同 §6 のまま |
| 日程（週表示） | owner / admin / staff | §5.4 |
| 先生の管理 | owner / admin | 招待・役割の変更・担当の割り当て |
| 生徒の管理 | owner / admin | 招待・休会・退会・担当の割り当て |
| 席と請求 | **owner のみ** | 席数の増減・支払い方法・領収書 |
| つながり | 生徒 | §4.2 |

**教室ダッシュボードの「要注意の生徒」は、担当している生徒だけです。**
管理者が全生徒の警告を見られる形にしないこと（§3）。

## 12. スコープ外

| やらないこと | 理由 |
|---|---|
| 部屋・設備の予約 | 予約管理SaaS の領域 |
| 空き枠の公開と、生徒からの予約申し込み | 同上 |
| レッスン料の決済・請求書・返金 | 会計です。別事業になります |
| 先生への報酬計算・給与 | 同上 |
| 出席簿の法定保存 | 教育機関の要件。専用製品があります |
| アプリ内メッセージ・DM | 指導者プラン実装仕様 §8。**教室になっても作りません** |
| 複数拠点の階層（教室の中に校舎） | 需要が出てから。いまは教室を並列に作れば足ります |

## 13. 実装の順番

**「ここまでで売れます」を §13-6 に置いています。**

## 14. 禁止事項

- ❌ **管理者に、担当していない生徒の健康データを見せない**（§3）
- ❌ **staff に健康データを見せない。** 例外を作らない
- ❌ `canView()` を通さないデータ取得を作らない
- ❌ 担当を外れた先生に、**過去の分**を見せ続けない（§9）
- ❌ **アプリ内メッセージ・DM を作らない**（教室になっても同じ）
- ❌ 記録へのコメントを、担当の先生と生徒だけの非公開にしない（§7）
- ❌ 空き枠の公開・予約の受付を作らない（§12）
- ❌ 重なりを検出したときに、**自動でレッスンを動かさない**
- ❌ 席の計算に「掛け持ち割引」を作らない（§8.2）
- ❌ 生徒に有料機能を全部付与しない（§8.3）
- ❌ 同意の記録を上書きしない（履歴で残す）
- ❌ 解約時に生徒のデータを消さない

## 15. Claude Sonnet 5 への依頼のコツ

- **§13 の 1 を単独で出させ、テストを見せてもらってから 2 へ進む**
- `canView()` は **サーバー側だけ**に置く。画面側で権限を判定させない
- **「管理者だから全部見えていいですよね」という提案が来たら、§3 を根拠に必ず断ること**
- §10 の③で、**旧経路と新経路の結果の突き合わせログ**を必ず実装させる
- 日時は **UTC ＋ tz**（国際展開仕様 §2.3）。レッスンは時刻が本質です
- 席数の判定は**サーバー側**で。画面で数えさせない
- **§12 のスコープ外を、実装前に読ませてください。**
  予約管理に広げる提案が来たら断ること
