# La Voce 改善タスク指示書

作成日: 2026-08-26
対象: https://la-voce.vercel.app （実験公開中・全機能無料）
このドキュメントの役割: 実装を担当するAIエージェント（Sonnet）向けの、優先度付き改善指示。

---

## 0. 実装者への前提共有

### このアプリは何か

声のプロフェッショナル（声楽家・オペラ歌手・ミュージカル俳優・声優・ボイストレーナー）向けの、
**「歌が上手くなる」ではなく「声を壊さない」** ことに振った縦断的コンディション記録アプリ。

主要画面:

| タブ | 内容 |
|---|---|
| ホーム | 今日のスコア、連続記録、次のアンロックまでの進捗 |
| 今日の記録 | 声の記録（音名・響きスコア・CPPS測定）＋ 一日の記録（睡眠・食事・体重・環境・症状・メンタル） |
| 分析 | 声の調子スコア、偏差値、声の予報、音域到達マップ、ウォームアップ効率、症状カレンダー、栄養、ACWR ほか |
| レッスン | 指導者向け。生徒のレッスンカレンダーと生徒一覧 |
| おうち | ポイントで部屋・庭・服を買うゲーミフィケーション |
| ノート | 稽古ノート、目標設定 |
| もっと | 質問票（RSI/VFI/SVHI-10/EASE）、受診用サマリー、レッスンモード、AIアドバイス、設定、LINE連携 |

### 絶対に壊してはいけない既存の良い設計（ガードレール）

改善作業中、以下は **維持すること**。これらはこのアプリの中核的価値であり、
リファクタや「簡潔化」の名目で削らないこと。

1. **医学的断定を避ける免責文言** — 「医学的診断ではない」「自分自身の推移で見る参考値」という
   一貫したトーン。健康系プロダクトとしての信頼の根拠。
2. **音名表記のルール説明** — 国際式（ミドルC = C4）とヤマハ式のズレの注意書き。
3. **裏声ではなく地声で記録する指示** — ドメイン知識に基づく重要な設計判断。
4. **絶対湿度での環境快適帯** — 相対湿度ではなく絶対湿度で見る判断。意図的なもの。
5. **ポイントは「記録を続けたか」だけで貯まる** — 体調の良し悪しで報酬が変わらない設計。倫理的に正しい。
6. **標準化質問票（RSI / VFI / SVHI-10 / EASE）** — 最大の差別化要素。
7. **CPPSの録音データを保存せず即時破棄する処理** — プライバシー設計の中核。
8. **段階的アンロック（あと◯日で開きます）** — 継続動機の設計。

## P0: 最優先（信頼を直接損なっている / 公開段階で必須）

### P0-1. 少数データでの断定的な文言を抑制する

**現状の出力例（分析タブ「複数の条件を組み合わせて見えてきたこと」）:**

> 食事では、喉の調子が良かった日（3日）に「白米（ご飯）」を食べていることが多いです（9日）。
> 反対に、喉の調子が悪かった日（1日）には「白米（ご飯）」を食べていることが多いです（3日）。

**問題:**

- 良い日にも悪い日にも同じ食品が挙がっており、情報量がゼロ。
- 読んだユーザーに誤った因果を刷り込むリスクがある。
- 免責文を足しても解決しない。**出力しないのが正解**。

**対応:**

- 相関・傾向を **文章で語る** すべての箇所に、共通の最小件数ゲートを実装する。
- 推奨閾値: 各群 n >= 10、かつ両群が揃っていること。満たさない場合は文章を生成せず、
  代わりに「あと◯件の記録で、食事と声の傾向の分析が始まります」という進捗表示に置き換える。
- 閾値は定数として1箇所に集約し、後から調整できるようにすること（例: `MIN_N_FOR_NARRATIVE = 10`）。
- 対象箇所（確認して網羅すること）:
  - 「複数の条件を組み合わせて見えてきたこと」の全文
  - 「休養方法ごとの声・メンタルの傾向」
  - 「滞在地ごとの声・メンタルの傾向」
  - 「よく一緒に出る症状」
  - 「気持ちタグの傾向」
  - 「時間帯別の声の傾向」の「調子が良い傾向」バッジ

**受け入れ条件:**

- 記録8日程度のアカウントで分析タブを開いたとき、断定的な相関文が1つも表示されない。
- 代わりに、あと何件で何が見えるようになるかが表示される。
- 群の件数が閾値を満たした場合のみ、従来どおり文章が出る。

### P0-2. 発声負荷（ACWR）の警告を、データが揃うまで出さない

**現状:**

- 分析タブ最上部に「⚠️ 今日の一言 / 今日の発声負荷比は2.2。喉を痛めやすい急増な状態です。
  明日を休養にすると1.8に戻ります」と警告が表示される。
- 一方で「発声負荷バランス（ACWR）」パネル自体は「あと20日で解放されます（8/28日）」とロック中。

**問題:**

- ACWRは **急性7日 / 慢性28日** のローリング平均比が前提。慢性側が8日しかない状態の比率は
  数学的に信用できない。
- ロックされているはずの指標が、警告としてだけ先に露出しており、設計として不整合。
- 「喉を痛めやすい」という不安を煽る側の表示が、最も精度の低いタイミングで出ている。

**対応:**

- トップの「今日の一言」の発声負荷比の警告を、**慢性側28日分が揃うまで出さない**。
- 揃っていない期間は、警告の代わりに中立な文言を出す。
  例: 「発声負荷バランスの計算には、あと20日分の記録が必要です。」
- ACWRパネルのロック状態と、トップ警告の表示条件を **同一のフラグで制御** すること
  （現在は別々に判定されている可能性が高い）。
- 併せて「今日の一言」の他の警告文についても、根拠となる指標がロック中でないか確認すること。

**受け入れ条件:**

- ACWRパネルがロック中のとき、トップに発声負荷比に基づく警告が出ない。
- 28日分揃った時点で、パネルのアンロックと警告の有効化が同時に起こる。

### P0-3. データの書き出しとアカウント削除を実装する

**現状:**

「もっと」→ アカウント の項に「データの書き出し・アカウント削除機能は準備中です。」とだけ表示。

**問題:**

- 健康関連データ（症状・体重・食事・メンタル）を扱っている。
- UIが9言語対応しており、EU圏ユーザーの利用を想定した設計になっている。GDPR上、
  データポータビリティ権（第20条）と削除権（第17条）への対応は必須。
- 信頼を売りにしているプロダクトで、この欠落は目立つ。

**対応:**

- **データ書き出し**: 全記録をJSONまたはCSVでダウンロードできるようにする。
  最低限、日々の記録・質問票の回答履歴・目標／ノートを含めること。
  声の記録と一日の記録は日付をキーに結合した形が望ましい。
- **アカウント削除**: 削除リクエストから実データ削除までのフローを実装。
  - 削除前に「書き出しを先に行いますか？」を提示する。
  - 二段階確認（テキスト入力による確認など）を入れる。
  - 指導者アカウントの場合、生徒との共有関係がどうなるかを明示する。
- 生徒アカウント削除時に、指導者側の「レッスン」タブから該当生徒が消えることを確認すること。

**受け入れ条件:**

- 設定画面から書き出しと削除の両方が実行できる。
- 削除後、同一メールアドレスで再登録した際に旧データが復活しない。

## P1: 重要（有用性の上限を決めている）

### P1-1. 「30秒で終わる最小記録セット」を定義する ★最重要の設計課題

**問題の構造:**

- 現在、今日の記録は睡眠・食事・体重・タンパク質・カロリー・環境・症状・音名・響きスコア・
  メンタル・活動内容と項目が多い。
- ところが声のプロは **本番期に最も忙しく、そこが最もデータの欲しい期間**。
- 結果として、忙しい日ほど記録が抜け、**分析上いちばん価値のある本番前後のデータが欠損する**
  という構造的な問題がある。
- 「全部埋めないと価値が出ない」という印象が、離脱の主因になり得る。

**対応:**

- 記録項目を3層に明示的に分類する。
  - **コア（必須・30秒以内）**: 喉のコンディション（1-5）、声の質（1-5）、活動内容、
    起き抜けの音名 の4項目程度。
  - **推奨**: 睡眠時間、心の余裕、症状の有無、水分。
  - **詳細（任意）**: 食事・栄養・体重・環境・滞在地・響きスコア・CPPS。
- **コアだけで主要な分析が動くこと**を保証する。具体的には以下が、コア項目のみで機能すること:
  - 声の調子スコア（欠損項目は重み再配分し、何を除外したか注記する）
  - コンディション偏差値
  - 声の予報
  - 音域到達マップ
  - 段階的アンロックの日数カウント
- 記録画面に「かんたん記録（30秒）」と「しっかり記録」の切り替えを設ける。
  デフォルトは「かんたん記録」。
- 「かんたん記録」でも連続記録とポイントが通常どおり加算されること。ここを減点にすると
  逆効果になる。
- 「前日をコピー（食事・身体データ・環境）」は既に存在しており良い機能なので、
  かんたん記録モードからも1タップで呼べるようにする。

**受け入れ条件:**

- 4項目の入力のみで保存でき、翌日の分析タブに主要指標が表示される。
- 詳細項目が未入力であることが、ユーザーに「不完全な記録」として罪悪感を与える表現になっていない。

### P1-2. CPPS測定の録音条件をガイドする

**現状:**

「あー」を5秒のばして録音 → スペクトルの明瞭さ（CPPS）を数値化 → 録音は保存せず即時破棄。
「このアプリ独自の簡易計算のため、自分自身の推移で見るための参考値」と注記あり。

**問題:**

- スマートフォンのマイクは、口元との距離・環境ノイズ・機種によってCPPSが大きくブレる。
- 「自分の中での推移」で見るとしても、**録音条件が揃わなければ推移そのものがノイズ**になる。
- 現状の注記は計算方法の限界にしか触れておらず、測定条件には触れていない。

**対応:**

- 測定画面に、測定前チェックを表示する（3点程度、簡潔に）:
  - 口とマイクの距離を毎回そろえる（例: 約20cm）
  - 静かな場所で測る
  - 毎回同じ端末で測る
- 端末情報（User Agent等）を測定値と一緒に保存し、**端末が変わった記録には推移グラフ上で
  マーカーを付ける** か、系列を分ける。
- 可能であれば、録音時に環境ノイズレベルを推定し、閾値を超えたら
  「まわりが少しうるさいようです。測り直しますか？」と促す。
- CPPSの推移グラフを出す場合、条件が揃っていない可能性を1行で注記する。

**受け入れ条件:**

- 初回測定時にガイドが表示される（2回目以降は折りたたみ可）。
- 端末が変わった場合に、その旨がユーザーに分かる。

### P1-3. 声の予報の「的中率」の見せ方を再検討する

**現状:**

「3.3 / 5、予測区間 2.4〜4.3、33% 直近6日の的中率」「まだ記録6件（14件で個人化が始まります）」

**問題:**

- 的中率を正直に開示している姿勢自体は良く、維持したい。
- ただし33%という数字は、ユーザーに「当たらないアプリ」という第一印象を残す。
- 現在の「的中」の定義が厳しすぎる可能性が高い（完全一致に近い判定と推測される）。

**対応（いずれか、または組み合わせ）:**

- 的中の定義を **予測区間に実測が入ったか** または **±1以内か** に変更し、
  定義をツールチップ等で明示する。
- サンプル数が少ないうち（例: 14件未満）は的中率を表示せず、
  「あと8件の記録で、予報の精度が表示できるようになります」に置き換える。
- 予報の主目的が「当てること」ではなく「前夜の行動と今日の声の関係を意識させること」で
  あるなら、その意図が伝わる文言を1行添える。

**受け入れ条件:**

- 的中の定義がユーザーから確認できる。
- 記録件数が少ない段階で、低い的中率が単独で目立つ表示になっていない。

## P2: 改善余地（優先度は下がるが効果あり）

### P2-1. 偏差値の表示を、件数に応じて調整する

- 現状「今日は偏差値46。この8日間で上から75%、6番目に良い日です。」
- 相対値として提示している点は正しいが、8件での偏差値は分布の仮定が成立しにくい。
- 対応案: 件数が少ないうちは偏差値を出さず、「8日中6番目」という順位表示のみにする。
  一定件数（例: 30件）を超えてから偏差値を併記する。

### P2-2. 指導者経由の配布導線を強化する

- 「レッスン」タブに生徒招待機能があるが、現在「（テスト機能）」表記。
- ボイストレーナー・指導者は、**生徒に配ってくれる増幅装置**になり得る最重要チャネル。
- 対応案:
  - 招待フローを正式機能に格上げし、招待リンクの共有をワンタップにする。
  - 指導者側に「生徒の記録が途切れている」通知を出す（生徒の継続率が上がる）。
  - 「※生徒が公開範囲を変更・解除すると、この画面の表示もすぐに切り替わります」という
    プライバシー配慮は良い設計なので維持すること。

### P2-3. 職業音声酷使者（教師・コールセンター等）向けの表示切り替え

- 現在のUIは歌手前提の語彙（音名・パッサッジョ・本番・公演の出来）が多い。
- 対応案: プロフィールに職種を持たせ、歌唱系でないユーザーには
  音名・パッサッジョ・音域到達マップ等を非表示にし、話声位・声の疲労・症状を前面に出す。
- 優先度は低い。まずは歌手・声優・指導者に集中してよい。

### P2-4. LINEリマインドの活用を広げる

- 既に連携コード方式のLINE朝リマインドが実装済み。
- 対応案: 「本番」を登録した日は、本番翌日に EASE / 声の状態の記録を促すリマインドを送る。
  ピーキング曲線・ツアー耐久曲線の精度に直結し、既存の分析機能の価値が上がる。

## 推奨する実装順序

1. **P0-1**（少数データの文言抑制） — 影響範囲が限定的で、信頼への効果が最も大きい
2. **P0-2**（ACWR警告の抑制） — 小さな修正。P0-1と同じ「早すぎる断定をやめる」方針
3. **P1-1**（最小記録セット） — 設計変更を伴うため、P0-1/P0-2の後にまとめて着手
4. **P0-3**（書き出し・削除） — バックエンド作業。P1-1と並行可
5. **P1-3**（的中率の見せ方） — 小さい
6. **P1-2**（CPPS録音条件） — 中規模
7. **P2各項目**

## 補足: 実装時の注意

- P0-1 と P0-2 は、いずれも **「データが足りないときに何も言わない」** という共通方針の実装。
  可能であれば、指標ごとに「この指標が意味を持つ最小件数」を宣言的に持つ共通レイヤーを作り、
  表示側がそれを参照する形にすると、今後の指標追加時にも同じ問題が再発しない。
- 文言を消すだけにせず、必ず **「あと◯件／◯日で何が見えるか」** に置き換えること。
  既存の段階的アンロックのトーンと揃い、離脱ではなく継続の動機になる。
