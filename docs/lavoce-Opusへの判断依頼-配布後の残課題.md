## 1. ★「その他」の職業に、曲目カードで何を出すか

### いまの状況

曲目カードには、職業ごとに「もう一段の情報」を添えています
（`lib/occupation.js` の `repertoireExtraFor`）。

```
歌唱言語 … classical / musical / pops
役の情報 … voiceActor / actorStage / actorScreen
案件の情報 … narrator / announcer / mc
何も足さない … rakugo / other        ← ★ここ
```

「その他」には、いま**何も足していません**。これは 2026-08-29 に私が置いた
既定値で、設計憲章の「その他には、みんなに共通の内容だけを出す」に
沿わせたものです。

### 選べる道

```
案A そのまま。「その他」には追加項目を出さない
案B 共通の最小セットを作る（例：作品名・言語・ひとことメモ）
案C 「あなたのお仕事では、何を残しておきたいですか」と本人に選ばせる
```

### 私の案：**案A（そのまま）**

「その他」を選ぶ人は、11分類のどれにも当てはまらなかった人です。
その人たちに共通する項目は、定義上ありません。案Bは
「たぶんこれだろう」を全員に押し付けることになります。

### ★なぜ人が決めるべきか

「何も出さない」は、本人からは**機能が足りない**ように見えます。
それを許容するかどうかは、誰に使ってほしいかという製品の判断であって、
コードから導けません。

## 10. ★曲目カードの「保存のタイミング」を揃えるか

### いまの状況

**1枚のカードの中に、保存のタイミングが4つあります。**

| 操作 | 保存のタイミング |
|---|---|
| 曲名・分 | その日の記録へ（日の保存で確定） |
| 最高音・テッシトゥーラ・3択 | **「登録する」を押して確定** |
| 歌唱言語・声の質・原稿の種類・話す速さ・生か | **★タップで即DBへ** |
| 作品名 | **★フォーカスを外した瞬間にDBへ**（この欄だけ） |

利用者から見ると、どれも同じ1枚のカードです。境目は見えません。

### ★これが、2日ぶんの混乱の原因でした

即時に保存する操作には、**成功したことを示す合図がありません**。
チップの色だけです。しかもその色は `record`（保存された結果）から
作られるので、**保存が成功して初めて色が付きます。**

```
書き込みが弾かれる → 色が付かない → 「押しても反応しない」
```

実際に `tessitura_note` の NOT NULL で弾かれ続け、原因が分かるまで
2日かかりました（3a647a2 で解決）。
★「登録する」側は、押せばボタンの状態が変わるので、同じことは
　起きませんでした。**合図の有無が、そのまま差になりました。**

### ★私が提案する原則（決めていただきたいのは、これを採るかどうかです）

```
・自由記述は、明示的な確定が要る（登録する）
・離散的な選択は、タップで確定してよい
・★即時に書くものは、書けたこと／書けなかったことを必ず見せる
```

この原則は、いまコードのコメントにも書いてあります
（`handleSaveRole` の直前、歌唱言語チップの直前、作品名の直前）。
**採らないと決めた場合は、そのコメントも消してください。**

### 決めていただきたいこと（2つ）

#### 10-a｜即時保存に、「保存できた」合図を付けるか

```
案A 付ける（チップの横に一瞬チェックを出す、など）
    ★「選ばれている」と「保存できた」を、別の見た目にする
案B 付けない（色だけで足りる）
```

**私の案：案A。** ★いまは「選ばれている」と「保存できた」が
同じ見た目です。区別が付かないと、失敗したときに気づけません。

#### 10-b｜作品名の onBlur を、ほかの自由記述と揃えるか

```
案A 揃える（「登録する」を通す）
案B このまま（フォーカスを外したら保存）
案C 逆に、ほかの自由記述も onBlur にする
```

**私の案：案A。** 4つめの流儀を1つ減らせます。
案Cは、打っている途中の「C」が保存され得るので採りません。

### ★なぜ人が決めるべきか

これは**「どこまで丁寧に知らせるか」の匙加減**です。
合図を増やすほど安全になりますが、画面は賑やかになります。
静かな画面であることは、このアプリが大事にしてきたことでもあります
（設計憲章の「目立たせない」）。その釣り合いは、私には決められません。

### すでに直したこと（判断は不要です）

★失敗したときに画面へ出す、は**バグとして直しました**（判断待ちにしていません）。
`handleSaveRole` と `handleSaveProject` は、失敗しても `console` にしか
出ていませんでした。同じ事故が別の制約で起きる一歩手前でした。

## 12. ★作品名を「登録する」に合流させる前に、構造を直す必要があります

### いまの状況

判断の回答 §8-3 は、こう決めています。

> ★作品名を、最高音・テッシトゥーラと同じ「登録する」のグループに入れてください。
> 単に onBlur をやめるのではなく、既にあるボタンに合流させます。
> 新しい部品は増えず、4つ目の流儀が1つ減ります。

**★そのままでは実装できません。**

合流先の「登録する」ボタンは、この中にあります。

```jsx
{name && (!hasPitch || editingPitch) && (() => { … 「登録する」 … })()}
```

`hasPitch` は「最高音・テッシトゥーラ・3択のどれかが入っているか」です。
つまり**音の高さを登録し終えた曲では、このボタンは画面にありません**
（「直す」を押したときだけ戻ってきます）。

一方、作品名（声優の役の情報）は、音の高さとは無関係に出ています。

```
音の高さを登録済みの曲で、作品名を「登録する」に合流させると
　→ ★作品名を入力する手立てが、どこにも無くなります
```

**②で最高音の欄が消えていた不具合と、同じ形です。**
「行があるか」と「音の高さが入っているか」を混ぜた結果でした。
今度は「音の高さが入っているか」と「作品名を編集できるか」を混ぜることになります。

### 選べる道

```
案A 作品名にも、音の高さと同じ「直す」を用意する
    → 登録済みの曲でも、押せば欄が開く。既にある仕組みをそのまま使える
    ★私の案。新しい部品が増えず、②と同じ形で揃います

案B 役の情報の枠に、独立した「登録する」を1つ置く
    → 4つ目の流儀は消えるが、ボタンが1つ増える
    　（判断の回答 §8-3 の「新しい部品は増えず」に反します）

案C onBlur のまま残す
    → 4つ目の流儀が残ります
```

### ★なぜ人が決めるべきか

案Aは、**役の情報の欄が「音の高さの欄と同じ開き方」になる**ということです。
利用者から見た画面の構成が変わります。実装の都合ではなく、
**画面の組み立ての判断**なので、こちらでは決められません。

★いまは案C（onBlur のまま）で止めています。コードにその理由を書いてあります。
　★真似して onBlur を増やさないよう、注意書きも添えました。
