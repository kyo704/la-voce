## 001 ｜ /api/advice ― 記録を外へ出す経路が、サーバ側で閉じていなかった

**発見**
2026-09-03、私（Claude）が `/api/advice` の中身を読んでいて気づきました。
きっかけは、同意の撤回が強制されていなかった件の調査です。★**同じ形を探していて出ました。**

**内容**
`app/api/advice/route.js` は `entries` を読み、`buildSummary` が喉・声・睡眠・水分・
気温・湿度・活動・公演の出来・心の余裕・喉の症状・食事メモ・メモを1行の文にまとめ、
`lib/anthropic.js` が `api.anthropic.com` へ送ります。
この経路を止めていたのは★**画面の定数だけ**でした（`VocalTracker.jsx:393` の
`AI_ADVICE_ENABLED = false`）。★**あれはボタンを隠すだけで、経路は生きています。**
ログイン済みの方が URL を直に叩けば通る形でした。

**範囲**
いつからか：この経路が書かれたときから。★**正確な日は特定していません。**
誰が：ログインできる方であれば、誰でも。★**自分の記録だけ**が対象です
（`.eq("user_id", user.id)` と RLS の二重で、他人の記録は引けません）。

**確認**
★**一度も外へ出ていません。** 出どころが2つあり、互いに独立しています。
- 送り手側：本番の Vercel に `ANTHROPIC_API_KEY` が**一度も設定されたことがない**
  （運営者が管理画面で確認）
- 受け手側：Anthropic の Console が「今月の使用額 $0.00／過去7日間にアクティビティなし」、
  新規の口座で残高の追加もなし（運営者が確認）

★**「失敗した」ではなく「一度も送っていない」です。** `route.js:105-110` が鍵の有無を
`fetch` より前に見て 500 を返すため、`lib/anthropic.js:4` の `fetch` に**到達しません**。

★**確認できなかったこと**：この経路が何回叩かれたか。
★**ただし、叩かれていたとしても外へは出ていません**（上の2つの出どころによる）。

★**正確に言うと**：記録は**読まれています**。`entries` の読み出し（`88-93行`）は
鍵を見る**前**にあります。読んだものはサーバの中に留まりました。
★**「読んでいない」と言うと嘘になります。「外へ出していない」が正確です。**

**処置**
2026-09-03、`adviceEnabled()` をサーバ側に置きました（`route.js:60-71`）。
`AI_ADVICE_ENABLED === "true"` のときだけ開き、★**認証より前**に判定するので、
閉じているあいだは記録を1行も読みません。★閉じるほうへ倒しています
（未設定・空・`"false"`・`"1"`・`"yes"` は、すべて閉）。
commit `5483cf3`。

**判断**
★**届け出ていません。** 外へ出た記録が1件も無いためです。
★この判断は「出ていないことが確かめられた」ことに乗っています。
出どころが2つあり、送り手側と受け手側の別々の系から一致しました。

**その後**
- 同じ形（画面の定数が門の代わり）を探し、★**Stripe の3ルートで見つけました**（記録 002）。
- 検査 `advice-route-gated.test.js`（16本）が、門が認証より前にあることを見張ります。
- 台帳 `lib/outboundRoutes.js` に、この経路と「一度も通っていない」記録を残しました。

## 002 ｜ 決済の経路が、鍵なしで通信していた

**発見**
2026-09-03、記録 001 の「同じ形を探す」作業のなかで見つけました。

**内容**
`lib/stripe.js` は `new Stripe(process.env.STRIPE_SECRET_KEY)` を作りますが、
★**鍵が未設定でも投げません。** 読み込みは通り、★**呼んだときに初めて**
`StripeAuthenticationError` になります。つまり★**通信そのものは起きます。**
そして `app/api/stripe/checkout/route.js` には鍵の見張りが**どこにもありませんでした**。
その結果、
```
stripe.customers.create({ email: user.email, metadata: { supabase_user_id: user.id } })
```
が**そのまま `api.stripe.com` へ届き、そのあと拒否されます**。
★**メールアドレスと利用者IDが外へ出てから拒否される形**でした。

★記録 001 との違い：あちらは `fetch` の**手前**で止まるので1バイトも出ません。
こちらは**出てから**止まります。★**同じ「閉じている」でも、中身が違います。**

**範囲**
いつからか：`bd10c1e`（2026-08-23、最初の一括アップロード）から。
誰が：★**画面に入口はありません。** `app/billing/page.js:25` の早期 return により、
`REQUIRE_SUBSCRIPTION` が有効でないあいだは案内だけを返し、
`<CheckoutButton />` に**到達しません**。★**URL を直に叩いた場合のみ**です。

**確認**
★**これまでに叩かれたことがあるかは、分かっていません。**
Vercel のアクセスログで数えられますが、まだ数えていません。
★**「たぶん誰も試していない」とは書きません。**

いまが閉じていることは、運営者が実地で確かめられました（2026-09-03）。
- 画面：`/billing` にボタンが1つも無い
- 経路：`fetch('/api/stripe/checkout', {method:'POST'})` → **503**

**処置**
2026-09-03、`stripeConfigured()` を `lib/stripe.js` に置き、
`checkout` / `portal` / `webhook` の★**3つすべて**で、何かをする前に見ます。
未設定なら 503。commit `3082fe7`。

**判断**
★**届け出ていません。** 出たとしても、メールアドレスと利用者ID（uuid）で、
体調の記録は含まれません。かつ、相手は決済代行として契約している Stripe Japan, Inc. です。
★**ただし「出た件数が分かっていない」ことは、この判断の弱いところです。** 明記します。

**その後**
- 台帳 `lib/outboundRoutes.js` に、実地の確認と「まだ分かっていないこと」を残しました。
- 検査 `stripe-gated.test.js`（28本）が、見張りが何かをする前にあることを見張ります。
- ★**私はこの経路について、コードの読みだけで2度まちがえました。**
  「入口は無い」→「全員に出る」→「早期 return で到達しない」。
  ★動くものを確かめた記録のほうが強いので、台帳の一次資料はそちらにしています。

## 003 ｜ profiles の行が、つながっている相手から読めていた

**発見**
2026-09-03、`supabase/migration_org_member_names.sql` の**確かめ方③**で見つかりました。
「`profiles` は、あいかわらず自分の行しか読めないこと」を確かめる照会です。
+g4t2 として `select count(*) from public.profiles` が★**2**を返しました（1であるべき）。

★**この照会は、別の機能を入れる前の安全確認として書いたものです。**
★**本来の目的とは違うものを見つけました。**

**内容**
ポリシー `profiles_connected_display_name`（SELECT）
```
USING: are_connected(auth.uid(), id)
```
★**名前は「display_name だけ」と読めます。** ですが RLS は**行単位**で、列は絞れません。
★**行が読めれば、その行の全部が読めます。**
`allergies` / `regular_medications` / `conditions`（既往症）/ `health_notes` /
`is_under_18` / `cycle_show_on_home` / `line_user_id` / `occupation`（自由記述）…

★**このポリシーも `are_connected` も、リポジトリのどこにもありません。**
手で当てられ、一度も写されていません。

**範囲**
いつからか：★**分かっていません。** リポジトリに無いので git に記録がありません。
★**少なくとも 2026-09-02 より後ではありません**（その日、教室のメンバーの名前が
読めなかったため、教室の在籍は対象外だと分かります）。
誰が：`are_connected()` が真を返す組。★**先生と生徒のつながり**が含まれることは、
+g4t2（先生役）が +g4s1（生徒役）の行を読めたことから確かです。

**確認**
★**PostgREST のログを見ました。`profiles` への読み出しは、見られる期間には出ていません。
ただし見られるのは直近24時間だけです。ポリシーが存在した期間の全部には、まったく届きません。
★これは「証拠が無い」のではなく、「証拠を取れる期間が無い」です。
「漏れは起きなかった」ではありません。**

**処置**
2026-09-03、運営者がポリシーを落とされました。
```
drop policy if exists "profiles_connected_display_name" on public.profiles;
```
落としたあと、`profiles` に残るのは「Users can view own profile」（SELECT）と
「Users can update own profile」（UPDATE）の2本のみであることを確認済み。

置き換えとして `get_connected_names(uuid[])` を用意しました（commit `99d208e`、★未実行）。
★`are_connected` は**書き写さず、呼びます**。返す列は
`id` / `display_name` / `vocal_profession` の3つだけです。
呼ぶ側3か所（`9733` / `9937` / `10284`）も置き換え済み。

★**ポリシーを落としてから関数を入れるまでのあいだ、先生・生徒の名前は出ません。**
「先生」「名前を読み込めませんでした」と表示されます。★**内部のIDは出ません**
（2026-09-02 に塞ぎ済み）。★**壊れた画面は数分で直せます。読まれた行は戻せません。**

**判断**
★**まだ決まっていません。** 「範囲」の「いつから」が分かっていないためです。
★**分かっていることと、分かっていないことを、そのまま弁護士へ渡します。**
★**「ログに出ていないので漏れていない」とは言いません。**

**その後**
- 常設の棚卸しを作りました：`supabase/AUDIT_policies_by_using_clause.sql`。
  ★**名前を見ない。USING 句を見る。**
- 命名の規則を決めました（`docs/lavoce-くり返す失敗の形.md` 6-2）。
  ポリシーの名前は★「誰がその行を見てよいか」を書く。★列の名前は書かない。
- ★**同じ誤解が、今日3件目です**（`lessons`・`entries`・`profiles`）。
  4件目を探すため、本番の姿を丸ごと写し取る照会を用意しました
  （`supabase/AUDIT_full_schema_vs_repo.sql`）。
- 検査 `profiles-cross-user.test.js`（23本）が、他人の `profiles` を直に読む書き方が
  戻ってこないことを見張ります。
